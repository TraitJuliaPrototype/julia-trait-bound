# W-88, open issue 102: a function kept before its signature is known

Open issue 102 was decided on 2026-10-28 (mine, flagged): `Callable` without a signature keeps a function whose argument types a later bound fixes ([traits §7.5](../reference/traits.md#75-functions-kept)). It had two cases: TDE's `DiscreteCallback(condition, affect!)`, and Tables' `ByRow(f)`.

## What is built

- **The forms:** `Dynamic{Callable}`, `Compiled{Callable}`, `Kept{Callable}` hold the user's function with its attribute. Constructors and casts work as at a signature: a constructor never casts.
- **At the first bound with a signature** the function is entered with its attribute. A `Dynamic` one is checked as a function kept at another signature (traits §6.5), then erased to a pointer: the code that calls it is compiled once per signature. A `Compiled` one is passed as itself.
- **Stored at a signature** (`Kept{Callable{A, S}}`) it keeps its attribute, by conversion.
- **Called directly** it is the function's own call. Without a signature there is nothing to check (mine).
- **In a field** of a trait module, `Callable` means `Kept{Callable}`.
- **TDE:** `DiscreteCallback` and `ContinuousCallback` keep `condition::Callable` and `affect!::Callable`. The `Any` fields and `_keep_fn` are gone. `enter_callbacks` builds `FunctionCallback{U, T, P}(cb.condition, cb.affect!)`; the fields at the signatures take the kept functions by conversion, with their attributes.
- The constructors keep `@nospecializeinfer`, so a new callback compiles no constructor. Whether that annotation can go is open issue 103's measurement.

Checks: TraitWorld's suite (`carry.jl`, 17 new tests), TDE's suite (105 tests) and its session (the nine `RESULT` lines equal `experiments/w81/x1/session-x1-one-function.log`), the forks' session check (digests equal at 26 steps), TraitMakie's suite. Logs: `experiments/checks/logs/w88-102/`.

## Why `ByRow` waits

E-216 found that a new closure's `transform(df, :a => ByRow(f) => :b)` costs 24–25 ms, against the kernel's 6.1–6.8 ms. The rest is `ByRow{F}`'s method and DataFrames' mini-language, compiled per closure type. `ByRow` holding a `Dynamic{Callable}` would make them compiled once. Two things block it.

1. **DataFrames' plain pipeline reads the function.**
   - Column names: `funname(row::ByRow) = funname(row.fun)` uses `nameof`, and `f_g` for a `ComposedFunction`.
   - A fast path tests `fun.fun isa ComposedFunction{<:Any, typeof(collect)}`.
   - Upstream's test: `Base.broadcastable(ByRow(+)) isa Base.RefValue{ByRow{typeof(+)}}`.
   - Plain code has no public way to read the function a kept value holds. `rewrap(g, f)` gives a cast of `g`'s result, not the result.
2. **`ByRow` is a plain struct.** A struct parameter bounded by `Callable` without a signature is not defined (traits §7.4 takes a signature).

Working around either (a field of type `Any`, or reading TraitWorld's internals in the fork) is what the annotation audit removed. So it is open issue 111.

## The proposal

- **`ByRow` as a struct parameter bounded by `Callable` without a signature**, defined in `ColumnCore` and exported by Tables: `struct ByRow{F <: Callable} <: Function; fun::F; end`.
  - Its constructor is the bound, as for any bounded parameter. A function of the trait world (Base's `+`, `sum ∘ collect`) is kept as itself where the code knows its type, so `ByRow(+)` is `ByRow{typeof(+)}` and the fast paths see the `ComposedFunction`. A user's function is `Dynamic{Callable}`, by `Callable`'s default.
  - The read back under `Compiled` has no signature to be a function argument at (open issue 104). It reads as the function itself.
- **A public read of a kept value's object for plain code,** for example `object(k)`. The fork's `funname` and fast paths use it. A kept value already holds the user's object (traits §7.1). Plain code reading it does not let trait code depend on the user's type.
- **Undecided:** `ByRow(+)` typed at the prompt is `Dynamic` by the first-seen rule, since the prompt knows no types. A singleton function of the trait world could be `Compiled` wherever it is seen: its code is compiled once per type anyway.

## What to measure when it is built

- E-216's new-closure cost, before and after: the kernel alone and a whole `transform`, five closures, two runs.
- The criterion: results equal to upstream's (element types and column names included), and a whole `transform` cheaper than upstream's 25 ms.
