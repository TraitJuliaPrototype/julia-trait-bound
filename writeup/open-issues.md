## 2. Design

135. **A package cannot take its own constructor out of the method table while Julia writes its image** (W-95, E-251; [lowering L-50](../attic/writeup/reference/lowering.md#18-deviations)). A bounded method of a type's constructor at the signature of the type's default constructor (`S(x::Bounded)` beside Julia's `S(x)`) takes that constructor as its fallback ([lowering §8.1](../attic/writeup/reference/lowering.md#81-the-rewrite)). In a session TraitWorld takes the constructor out of the method table and calls it by `invoke` with its method. In a package it cannot: while Julia writes a package image it refuses to delete a method (`Method deletion is not possible during Module precompile`, `julia-1.13/src/gf.c:2931`) and to overwrite one (`gf.c:2297`). So in a package such a bounded method is refused at its definition; the struct declares inner constructors with typed arguments instead. Blocked by Julia's precompilation checks, not by a rule of the references. *Proposal:* relax those two checks for methods whose module is in the worklist (the package being precompiled defined them in this process); the image writer already writes a disabled method entry as dead (`staticdata.c`). *Deferred (the user, 2026-10-29: "135 should wait."):* it waits for unification (W-83): under its level 2 a bounded constructor is a method at its bound, not at the default constructor's signature, so nothing has to be taken out ([the plan](plans/2026-10-29-unification-evidence.md) §5).

148. **The name `All` collides with DataAPI's `All`** (W-107; found 2026-11-07). The user's spelling for intersections is `All{X, Y, Z, …}` (Q5 (a); [traits §3.6](reference/traits.md#36-intersections)).    - **Recommendation:** (b): trait code gets the user's spelling, plain Julia keeps its names, and the clash is local to modules that use both.
   - **Taken for now:** (b), mine (2026-11-07): TraitWorld `unified` ae4d250 exports `All` ([traits §3.6](reference/traits.md#36-intersections)); for the user to confirm (§1).

103. **Kept-value constructors compiled per value type** (candidate 6). `Kept{Callable{A, S}}(f)` compiles once per closure from plain code (4 specializations for 3 closures), so TDE wraps every keep in `@nospecializeinfer`. 111. **`ByRow(f)`: a function kept before its signature is known, inside plain code that reads it** (W-88, open issue 102's second case; [the note](plans/2026-10-29-w88-102-kept-function.md)). `Tables.ByRow{F}` keeps the user's function at its own type, so `ByRow`'s method and DataFrames' mini-language are compiled per closure (E-216: a new closure's whole `transform` 24–25 ms against the kernel's 6.1–6.8 ms). Undecided: a singleton function of the trait world typed at the prompt (`ByRow(+)`), `Dynamic` by the first-seen rule there.
112. **The old API's untyped node graph undoes the late-load protection** (W-70, E-226). It concerns the old recipe API's recipe children only: the workload's path makes the core's primitives directly and recompiles nothing after a late load (E-227). A child recipe's arguments are nodes of its parent's graph, which resolve to `Any` in plain code, as upstream's ComputePipeline does. The child's creation then compiles abstract instances (among them `hist.jl`'s `Histogram` conversion), which DataFrames' `AbstractVector` subtypes invalidate at a late load: 41 CodeInstances, 126 ms. No rule blocks a fix. *Proposal:* typed derived values in the `PlotCore` slice of the workload's path ([the fresh-ideas memo](plans/2026-10-28-fresh-ideas-makie.md): inputs kept, derived values declared), not a patch to the compatibility layer. It waits for unification (W-83), by the plan's rule.
113. **Facts inference loses a bounded function's result where a function kept at another signature enters it** (W-34, E-229). An `ODEProblem` whose function is `Dynamic`, kept in a `Kept{ODEProblemTrait}`, was refused as a family member: `jacobian!` inferred `Any`, declared `Nothing`. Plain inference of the same body gives `Nothing`. Under facts, the generated entry of `_ad_jacobian!(fd::Callable{CoreDualSig{N}, Nothing}, …)` is inferred at `fd::Any` (`enter_callable(…, ::Any, ::Any, …)`), then a dynamic `checked_call` (`TraitWorld.factscode`). 114. **Plain code cannot ask a kept value for its attribute or its object.** TraitReport's session check (09d7f9b) could test only that a sorted column is a `Kept{Column}`, not whether it is `Dynamic`: `TraitWorld.is_dynamic(::HeldValue)` exists but is neither exported nor in the reference; TraitTables' own test reads `getfield(c, :compiled)`. 109. **`BoundedText` gives a bound per value; a writer needs one per type.** CSV's writer sizes its row blocks by a byte bound per column; for cell types it has no width for, it renders 64 sampled cells. With `textbound` over every cell (`forks/scripts/bt_write.jl`, `bt_bounds.jl`, `forks/logs/bt/`; forks a6d0716): the bytes written equal upstream's; for bits types (`Char`, `Rational{Int64}`, `ComplexF64`) the loop folds to a constant and costs nothing; for variable-width types it is a pass over every cell (`BigInt` 1.9 ms per 10⁴ cells against the sample's 19 µs, `Symbol` 31 against 2.5 µs). The writer therefore keeps the sample. Blocked by [traits §8.1](../attic/writeup/reference/traits.md#81-basetraits-traits-for-bases-concepts): `textbound(x)` takes a value. *Proposal:* a bound per type where the type has one (fixed-width types: integers, floats, `Bool`, `Char`, dates, and types built from them, such as `Rational{Int64}`), for example `textbound(::Type{T})` returning an `Int` or `nothing`, with the bound per value for the rest; a writer uses the type's bound without visiting cells, and samples or visits only where there is none. Related: LinearAlgebra's `factorize` returns, besides factorizations, `Diagonal`, triangular and `Bidiagonal` matrices, which are not `Solvable` though each has `ldiv!` (a prompt solver in `experiments/w34-sciml/move3/stageC.jl` was refused at its declaration for that, and uses `lu`).
110. **Two traits for reading items by position: `Column` and `Indexable`.** The DataFrames port's `CellVector` is `asvector` for a `Column`, written again: `Column`'s `cell(c, i)` reads row `i` counted from 1, `Indexable`'s `c[i]` is Base's index, which for an `AbstractVector` may start elsewhere (OffsetArrays). So a column is not `Indexable` by its own operations, and `asvector` cannot serve the kernels. Blocked by [traits §8.1](../attic/writeup/reference/traits.md#81-basetraits-traits-for-bases-concepts) (the index's meaning is Base's) and T-8 (a generic implementation of a trait with parameters, which `@implement Indexable C where {C: Column}` would be). *Proposal:* `Indexable`'s index means a position counted from 1, Base's types conforming through `firstindex`, as `Column`'s family does; then `Column{T} <: Indexable{T}` with `cell` its `getindex`, and `CellVector` is `asvector`. Until then `CellVector` stays.

67. **To revisit: readable stack traces against inlining** (found while testing W-40, 2026-10-27; the user: "Did you identify a trade-off between printing in stack traces and performance?     - **What E-145 found** ([`experiments/fallback/README.md`](../experiments/fallback/README.md)): with the table behind the split, a split over the observed hot types is 3× faster only for one multiply on data in the cache, in skewed or phase-changing mixes; 1.4× to 2.1× for a heavier body; 0.8× to 1.8× on large data, where a split over random types costs. To revisit when a demonstrator shows a hot site whose types are outside the declared four.
    - **Why recompiling in the background removes the objection to guarded devirtualization.** The objection (postponed 2026-10-19, [the speed plan](plans/2026-10-19-principled-speed-plan.md) §2) was the permanent cost: a failed guard leaves the site on the slow path until its caller happens to compile again. With recompilation in the background the cost is bounded: the fallback's cost until the new code is ready, then the observed types at inlined speed.
    - **Why it keeps the guarantees** (reasoning). The swap is not an invalidation: the old and the new code are valid in the same worlds and compute the same results. Each new branch is a fact with its edge, and the choice of types records nothing, as the split's candidate list records nothing today. So "identical or error" and G2 hold as for the split.
    - **What it needs from Julia** (reasoning, to verify):
      - a counter at the fallback;
      - a compile request for the caller's MethodInstance with extra candidates, on a background thread (whether Julia's code generation can run there alongside the program is to verify);
      - a way to make the new code the one that runs: a newer CodeInstance for the same MethodInstance and worlds that dispatch prefers, and an atomic update of the entry that callers go through. Callers that call the old code directly, or inlined it, keep it until they compile again;
      - for package images: what was learned is lost at exit unless it is recorded, for example as a workload for the next build;
      - a closed (`--trim`) build knows every implementation and needs none of this.
    - **What it costs:**
      - speed depends on what the session has run, as in every tiered JIT;
      - the code that runs changes after the start, so reflection must say which version runs;
      - a background compile needs a thread, in programs that may not otherwise use one.
    - **For ordinary run-time sites** (trait code calling plain Julia, [the review](reviews/2026-10-20-heterogeneous-collections.md) F6): the same mechanism, fed by the types a site sees, is type feedback. It is the remedy for callees whose methods sit only at `Any`, where a split over the method table has nothing to split on. Its limit there: the fallback's result is `Any`, so code after the call stays untyped unless the observed branches are the whole story.
