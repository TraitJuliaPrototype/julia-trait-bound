**Keys and fields**
1. A field declared with an abstract type in a trait that does not require concreteness: its key is abstract, so every read is followed by a dispatch.
2. Fields stored inline that are not isbits (an immutable struct holding references): read through `getfield`, or loaded inline by a runtime.
3. A layout that copies the fields, opt-in per trait, for GPU kernels and other isbits-only targets; valid only for traits without writable fields.
4. Forwarding for a whole family of user types, `@implement X Series{T} by data where {T}`: planned ([traits §5.7](reference/traits.md#57-families)), not prototyped.
5. Mutable and immutable state families: `u` writable in one and `const` in the other. Either two traits, or field constness that depends on the family (solvers.md §11.7).

**Parameters and types**

6. Input parameters (several values per type), associated type constructors beyond one family, and results bounded by their own trait (`view`, Swift's `SubSequence`).
7. Whether an operation may return a small `Union` of concrete types, and what concrete mode reports for it (makie-rewrite.md §8.4). The reporting half is the pending decision §1.18.
8. Numeric traits: numbers that conform after the fact or forward to a field, and promotion across receiver types. Definition checking of code that computes with an element type needs a numeric archetype or a bound (solvers.md §11.6).
9. Automatic-differentiation tags as part of a key; units (solvers.md §11.4, §11.11).
10. `Callable` bounds whose argument types are chosen by the callee, a type-level function of the algorithm's configuration (solvers.md §11.9).

**Bounds, dispatch, arguments**

11. How `Vector{<:ColTable}` takes a user's vector: element by element into a new vector of trait objects, or as a whole. The copy costs one pass and loses aliasing (writes no longer reach the user's vector); collection traits (item 31) would let a vector cross as a whole, through a view.
12. Bounds over several arguments at once, `lines(x, y)`, where today a conversion builds one value from both; this ties to promotion (makie-rewrite.md §8.1).
13. "Live" bounds: an argument that is a value or a source of values (`Live{X}`, makie-rewrite.md §8.3).
14. The joint-method rule for wide families such as `plot(x)` over data traits (makie-rewrite.md §8.9).

**Dynamic values and functions**

16. Opening a `Dynamic` at the conforming value's own concrete type, a checked downcast, for callbacks that change parameters (solvers.md §11.2). `compiled_for(d)` opens it at its key; a downcast to the user's type is a plain assertion. Related: a trait-typed assertion in a body (item 36).
17. How a closure created inside a trait module is stored as a dynamic function: by dispatch, or by a pointer (makie-rewrite.md §8.5).

**From the review of heterogeneous collections (2026-10-20):**
31. **Collection traits in TraitWorld** (the user, 2026-10-20: "TraitWorld needing collections sounds right to me. Vector{AbstractType} is a poor substitute for an Iterable trait"). Trait code that loops over heterogeneous data should be bounded by a collection trait with a declared item bound (an `Iterable` whose items are `Dynamic{X}`), not take a `Vector{AbstractFoo}` or a `Vector{Any}`. Then the item type is known from the bound, each operation on an item is the `Dynamic` split rather than a call at `Any`, and a user's existing vector crosses through a lazy view that wraps each element when read: no copy, and the user's vector stays the one read and written (item 11). This is the shape of Rust's `impl Iterator<Item = &dyn Shape>` and Swift's `some Sequence<any Shape>`. To decide:
    - which traits: iterable, indexable, mutable indexable, keyed (for `Dict{String,Any}`), and their associated types;
    - when an element that does not implement `X` fails: eagerly when the view is made (a pass over the data), or lazily when it is read (after part of the work is done). Rust checks at the producer; Swift, at its boundary with Objective-C, checks an `NSArray` of class elements bridged to `[T]` lazily, on read ([other languages §11](design/other-languages.md));
    - who provides the view: an explicit adaptor in TraitWorld (sketch name `DynamicView{X}(v)`), or conformance of Base's containers to the traits, which raises who owns that declaration;
    - what wrapping on read costs: making a `Dynamic` must become cheap (157 ns and 32 B in the review, a scan of the candidate registry; 5 ns since the branch `basetraits`, below);
    - the measurement: the review's experiments rewritten as idiomatic trait code against such a bound, compared with plain Julia, Rust's `dyn` and Swift's `any`: measured, below.
    - **Decided (2026-10-20, the user; open issues §1, closed items 21–25):** BaseTraits as a module of TraitWorld, its names exported; the traits `HasLength`, `Iterable{T}`, `Indexable{T}`, `MutableIndexable{T}`, `Resizable`, `Keyed{K, V}`, Base's containers conforming by Base's methods; `Dynamic` holds the user's object, the split's candidates in declaration order; a user's container crosses implicitly, by the bound, and a non-conforming item fails when read ([traits §10.3](reference/traits.md#103-a-users-container-seen-with-dynamic-items)). The crossing's finer rules are the BaseTraits agent's, to confirm (§1, item 26).
    - **Measured (E-134, E-143, E-144; `experiments/hetero-idiomatic/README.md`):** making a `Dynamic` 5 ns (was 157); wrapping on read allocates nothing for the split's candidates. Within four types the idiomatic code recovers the tails in both settings: `filter!` 3.3–3.8 ns over the view (1.6–1.8 over a copy) against 41–43 interop and 2.2–2.4 plain; the `Dict{String,Any}` loop 4–5 ns against 274–276 interop and 2.4 plain. Beyond four the view costs about twice the copy (64 types: 162–181 against 78–84 ns, plain 99–106): two run-time sites per item outside the split. Item 32's question applies to both.
    - **Still open:**
      - which traits and algorithms come next (numbers, strings, IO; `count`, `map`, `sum` under their own names, since only Base may add bounded methods to Base's functions);
      - two traits that declare the same function at the same arity (`Indexable` and `Keyed` both declare `getindex`): a value carrying both is ambiguous at that operation;
      - generic algorithms over any item type need `where` variables in bounds (T-16) and cannot take a `Callable` at the item type (its argument types are constant); `retain!` takes `f` as an ordinary argument;
      - items of one concrete conforming type (`Iterable{T}` with `T` conforming, compiled per item type), Rust's `impl Iterator<Item = T> where T: Shape`: needs `where` variables in bounds;
      - a `Callable{Tuple{Dynamic{X}}, S}` in `DynamicCall` mode boxes the `Dynamic` per call (14–18 ns, 16 B); passing the held object instead is a TraitWorld change, not made;
      - `Dynamic{X}(x)` at a run-time site in plain code (a comprehension over a `Vector{Any}`) costs 102–108 ns, because Julia's per-site cache refuses calls whose function is a type (`src/gf.c`, `call_cache_exact`; the per-site cache's loop in `jl_lookup_generic_` would need entries matched on the function object itself). `collect(DynamicItems{X}(v))` costs 2 ns per element.
37. **Recompiling in the background with the observed types** (Optional, [compiler §1.6, §3.3](reference/compiler.md#33-further-work-on-mechanism-3)). The user (2026-10-20): "Guarded devirtualization was mostly problematic because it causes a permanent slowdown. If we can have a slow fallback but then recompile in parallel and swap compiled code back in once it is available, then that would of course be amazing."
    - **What E-145 found** ([`experiments/fallback/README.md`](../experiments/fallback/README.md)): with the table behind the split, a split over the observed hot types is 3× faster only for one multiply on data in the cache, in skewed or phase-changing mixes; 1.4× to 2.1× for a heavier body; 0.8× to 1.8× on large data, where a split over random types costs. To revisit when a demonstrator shows a hot site whose types are outside the declared four.
    - **Why recompiling in the background removes the objection to guarded devirtualization.** The objection (postponed 2026-10-19, [the speed plan](plans/2026-10-19-principled-speed-plan.md) §2) was the permanent cost: a failed guard leaves the site on the slow path until its caller happens to compile again. With recompilation in the background the cost is bounded: the fallback's cost until the new code is ready, then the observed types at inlined speed.
    - **Why it keeps the guarantees** (reasoning). The swap is not an invalidation: the old and the new code are valid in the same worlds and compute the same results. Each new branch is a fact with its edge, and the choice of types records nothing, as the split's candidate list records nothing today. So "identical or error" and G2 hold as for the split.
    - **What it needs from Julia** (reasoning, to verify):
      - a counter at the fallback;
      - a compile request for the caller's MethodInstance with extra candidates, on a background thread (whether Julia's code generation can run there alongside the program is to verify);
      - a way to make the new code the one that runs: a newer CodeInstance for the same MethodInstance and worlds that dispatch prefers, and an atomic update of the entry that callers go through. Callers that call the old code directly, or inlined it, keep it until they compile again;
      - for package images: what was learned is lost at exit unless it is recorded, for example as a workload for the next build;
      - a closed (`--trim`) build knows every implementation and needs none of this.
    - **What it costs:**
      - speed depends on what the session has run, as in every tiered JIT;
      - the code that runs changes after the start, so reflection must say which version runs;
      - a background compile needs a thread, in programs that may not otherwise use one.
    - **For ordinary run-time sites** (trait code calling plain Julia, [the review](reviews/2026-10-20-heterogeneous-collections.md) F6): the same mechanism, fed by the types a site sees, is type feedback. It is the remedy for callees whose methods sit only at `Any`, where a split over the method table has nothing to split on. Its limit there: the fallback's result is `Any`, so code after the call stays untyped unless the observed branches are the whole story.
