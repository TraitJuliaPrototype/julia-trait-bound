## Summary

- **SciML's architecture achieves twelve goals** (§1): open sets of problem kinds, algorithms, state and number types; one front end; interactive stepping; events; introspection and symbolic access; rebuilding a problem; refinement by extensions; peak speed by specializing on everything; and latency by un-specializing by hand (`AutoSpecialize`). It pays with types that carry what the code never reads, 63 cross-package methods that are pirates by the letter, hand-written type erasure with listed exceptions, and compiled code that loads discard.
- **Rust reaches the same goals with four moves** (§2): the open sets are traits with associated types and associated constants; the front end is one generic function the owner writes, which nobody overloads; extension from another crate is an `impl` for a local type, never a method on the entry; specialization and erasure are chosen per position (`impl Trait` against `dyn Trait`), and the capability questions (`isinplace`, `has_jac`) disappear into declared signatures, supertraits and provided methods. Swift differs in compiling generic code once by default, in allowing retroactive conformances (and regretting it), and in protocols that require properties.
- **The principles for the design as it stands** (§3): extension by implementation, never by overloading the entry; traits for the open sets, types for the library's own enumerations; trait functions become signatures, parameters and subtraits; specialization per position by attribute, not per problem by a level; values cross by their bound, code never crosses; declared fields and operations instead of `getproperty` switches; capabilities per type, with defaults where SciML asks per value; an extension adds implementations and methods for its triggers' types only.
- **The shortest route** (§4): five moves, in order, each keeping results equal by G1. (1) The right-hand side as a trait with the function kept at a `Callable` bound: the bound does what `AutoSpecialize` does by hand, for every case. (2) Callbacks and the integrator view: the callback axis leaves the integrator's type. (3) The front end's ownership: the body in the owner, extension by typed methods on owned algorithm types and by a bounded method with an owned trait, which removes the pirates that joint owners hold today. (4) Symbolic access as traits, the `getproperty` sugar kept plain. (5) The solution as a trajectory. Algorithms, caches, steps, controllers, `remake` and the keyword front ends stay plain.
- **Pushback** (§5): an algorithm trait generic over the problem is not expressible (no input parameters, no generic associated types), and the design's substitute, dispatch on the algorithm's type, fits SciML's closed family; associated constants are type parameters or plain methods; a capability query on a kept value is a trait cast, which is Optional; the dual signatures need the tuple of `Callable`s (W-29); `AutoDespecialize` needs the checked downcast (open issue §2.16); the bounded method on a foreign function is limited by lowering L-3; the `getproperty` question is open issue 50.

Two further goals are adjacent and left aside: differentiating through `solve` (`sensealg`, the ChainRules, Zygote, Mooncake and Enzyme extensions), and ensembles.

**The pattern behind the costs.** SciML has one tool for an open set, the abstract type with methods, and one tool for speed, the type parameter. Every goal is reached with those two. The open sets then have unchecked contracts (G-A, G-I), extension lands on the entry function (G-B), and speed and latency fight over the same type parameters (G-E against G-F), so latency is bought back by hand with wrappers that have exceptions.

## 2. The same goals in a trait-idiomatic language

### 2.1 Rust

The shape, written out *(general knowledge; the orphan rule, `dyn`, specialization's status and matklad's advice are in [other-languages §5–§6](../design/other-languages.md#5-who-may-implement-ownership-and-stakeholders))*.

```rust
// The open sets are traits with associated types and constants.
pub trait OdeProblem {
    type State;                       // Vec<f64>, an SVector, a GPU buffer
    type Scalar;                      // f64, Dual<f64, N>
    type Params;
    fn u0(&self) -> &Self::State;
    fn tspan(&self) -> (Self::Scalar, Self::Scalar);
    fn params(&self) -> &Self::Params;
    fn rhs(&self, du: &mut Self::State, u: &Self::State, p: &Self::Params, t: Self::Scalar);
    fn jacobian(&self, j: &mut Jac<Self::Scalar>, u: &Self::State, p: &Self::Params, t: Self::Scalar) {
        finite_differences(self, j, u, p, t)          // a provided method: the default
    }
}
pub trait Algorithm<P: OdeProblem> {
    type Integrator: Integrator<P>;
    const ORDER: u8;
    const ADAPTIVE: bool;
    fn init(&self, prob: &P, opts: &Options<P::Scalar>) -> Self::Integrator;
}
pub trait Integrator<P: OdeProblem> {
    fn step(&mut self) -> Result<(), SolveError>;
    fn done(&self) -> bool;
    fn u(&self) -> &P::State;
    fn t(&self) -> P::Scalar;
    fn set_proposed_dt(&mut self, dt: P::Scalar);
    fn add_tstop(&mut self, t: P::Scalar);
    fn terminate(&mut self);
}
pub trait Callback<P: OdeProblem> {
    fn condition(&self, integ: &dyn Integrator<P>) -> bool;
    fn affect(&mut self, integ: &mut dyn Integrator<P>);
}
// The front end: written once, by the owner. Nobody overloads it.
pub fn solve<P: OdeProblem, A: Algorithm<P>>(prob: &P, alg: &A, opts: &Options<P::Scalar>) -> Solution<P> {
    let mut integ = alg.init(prob, opts);
    while !integ.done() { integ.step()?; }
    integ.into_solution()
}
```

How each goal is met:

- **G-A, G-B: open sets by `impl`, in any crate that owns one side.** A new algorithm in crate B is `impl<P: OdeProblem> Algorithm<P> for Tsit5 { … }`: a local type, a foreign trait, allowed by the orphan rule. A new problem type in crate C is `impl OdeProblem for Network`. Neither crate touches `solve`. What DiffEqBase does today, a method of a foreign function on a foreign type (`solve(prob::AbstractDEProblem, …)`), is exactly what the orphan rule refuses: that code must live in the crate that owns the trait or the type ([other-languages §5](../design/other-languages.md#5-who-may-implement-ownership-and-stakeholders)). The default algorithm is a function of the umbrella crate (`solve_default(prob)`), or an *extension trait* the umbrella owns and implements for the core's problem types; it is never an `impl` on nothing.
- **G-C: one front end, one definition.** `solve` is generic over its bounds and checked at its definition against them. Keyword arguments are an `Options` struct with `Default` and a builder. A solver that supports stepping is one whose `Integrator` type exists; one that does not is a different trait (`DirectSolver`), not a `has_step` predicate that returns `false`.
- **G-D: state and number types are associated types.** `State` and `Scalar` are chosen per problem implementation; `solve` is monomorphized per `(P, A)`. A dual number is just another `Scalar`; a GPU buffer another `State` behind an `ArrayOps` bound. There are no promotion rules: the problem states its types.
- **G-E against G-F: chosen per position, in the signature.** `fn solve<P: OdeProblem>` is SciML's `FullSpecialize`: compiled per problem type, per closure. The latency form is `dyn`: `&dyn OdeProblem<State = Vec<f64>, Scalar = f64, Params = Vec<f64>>`, or `Box<dyn Fn(&mut [f64], &[f64], &P, f64)>` for the right-hand side alone. That is `AutoSpecialize`'s `FunctionWrappersWrapper`, written in the type, with the associated types fixed, as SciML's no-recompile mode fixes them to `Vector{Float64}` and `Float64` (`norecompile.jl:9–13`). The choice is the callee's, in its signature, and Rust practitioners advise `dyn` for closures by default ([other-languages §6](../design/other-languages.md#6-static-and-dynamic-positions-and-their-defaults)). A closed set in one crate is an `enum` with a `match`: SciML's `DefaultODEAlgorithm` with its integer-switched `DefaultCache` is that enum written by hand (the solvers exploration §1).
- **Trait functions become associated constants and signatures.** `alg_order` is `const ORDER: u8`; `isadaptive` is `const ADAPTIVE: bool`, folded at compile time. `isinplace` does not exist: the trait fixes one signature of `rhs`. A library that wants both forms declares two traits or two methods; a type implements the one it has. `has_jac` does not exist either: a provided method with a default body (finite differences), or a supertrait `trait WithJacobian: OdeProblem` that an implicit solver requires in its bound. There is no query on a value for a capability the type does not declare, except `dyn Any` with a checked downcast.
- **G-G: capabilities per type.** A record with optional fields is un-idiomatic. Either the capability is a supertrait the type implements, or the method is provided with a default. The one per-value form is `Option<&dyn Fn…>` returned by a method.
- **G-H: no `getproperty`.** Fields are private; a trait requires accessor methods with declared result types (`fn t(&self) -> P::Scalar`). `integrator.ps[k]` is `integrator.params().get(k)` or an `Index` impl. Symbolic access is a trait `IndexProvider { fn variable_index(&self, sym: &Sym) -> Option<usize>; … }` that the model implements and the problem, integrator and solution forward to.
- **G-I: the integrator interface is a trait with required methods.** An integrator that lacks one does not compile. Fallbacks that throw do not exist.
- **G-J: callbacks are trait objects.** `Vec<Box<dyn Callback<P>>>` in the integrator; each callback sees `&mut dyn Integrator<P>`: the integrator's type does not depend on the callbacks, and a callback's code is compiled once, calling the integrator through its table.
- **G-K: rebuilding.** Struct update syntax, `OdeProblemData { u0, ..prob }`, for the same type; a builder for a change of type parameter *(type-changing struct update is unstable; general knowledge)*.
- **G-L: no extensions, no refinement.** An `impl` for a foreign type lives in the trait's crate or the type's crate, behind a cargo feature. It adds; it never changes dispatch at an existing signature, since overlapping impls are refused and specialization is unstable ([other-languages §5](../design/other-languages.md#5-who-may-implement-ownership-and-stakeholders)). What SciML's ForwardDiff extension does with `anyeltypedual` fallbacks, winning at signatures without a dual, cannot be written.

What Rust needs for this that is not trivial: generic traits (`Algorithm<P>`), associated types with bounds (`Integrator<P>`), and, where the integrator borrows the problem, generic associated types *(stable since Rust 1.65; general knowledge)*. The solver's step is compiled per `(P, A)`; the right-hand side is a direct call under `impl` and an indirect call under `dyn`.

### 2.2 Swift, where it differs

- **Generic code compiles once by default**, with witness tables; specialization is an optimization (`@inlinable`, cross-module optimization) ([other-languages, "At a glance"](../design/other-languages.md#at-a-glance)). So a Swift `solve<P: Problem, A: Algorithm>` has `AutoSpecialize`'s latency by default and `FullSpecialize`'s speed only where the optimizer specializes. The two goals G-E and G-F are not a choice the API makes; they are the compiler's.
- **Protocols require properties**, `var t: Double { get set }`, computed or stored. That is the declared field of our traits, with the difference that ours is stored and read at its offset ([traits §3.3](../reference/traits.md#33-fields)). `static var order: Int { get }` stands for the associated constant.
- **Retroactive conformances are allowed**, so DiffEqBase's shape, a conformance of SciMLBase's type to a protocol in a third module, is expressible. Swift's ABI lead regrets it, and Swift 6 warns ([other-languages §5](../design/other-languages.md#5-who-may-implement-ownership-and-stakeholders)).
- **`any P` and `some P`** are Rust's `dyn` and `impl`, spelled since Swift 5.7 so that the existential's cost is visible ([other-languages §1](../design/other-languages.md#1-a-trait-is-an-abstract-type-with-behaviour)). `@dynamicMemberLookup` with key paths is the type-checked form of a `getproperty` overload.

## 3. The principles for the design as it stands

Each principle states the rule of the references it rests on. None proposes a change.

1. **Extension is by implementation, never by overloading the entry.** The owner writes `solve`, `init`, `__solve`, `__init` once. A package that adds an algorithm defines methods naming its own algorithm type: a stakeholder's method ([traits §10.1](../reference/traits.md#101-who-may-implement)); dispatch takes the typed method first ([§5.5](../reference/traits.md#55-dispatch-types-first-then-traits)). A package that adds a problem type implements the problem trait for it. A package that wants a `solve(prob)` without an algorithm, the umbrella, declares a trait it owns, implements it for the problem types it serves, and adds a bounded method to CommonSolve's `solve` with that trait: the extension-trait form, which [§5.5](../reference/traits.md#55-dispatch-types-first-then-traits) allows ("to another package's function where the package owns a trait the bound names"). Every cross-package method then carries a type or a trait its definer owns. The 57 pirates by the letter that joint owners hold today (G1, G2, G6, G7, G14–G17 of [the inside-out plan §2.2](../plans/2026-10-21-ndport-inside-out.md#22-per-group)) are exactly the methods that violate this; the plan's class (c) ("avoidable by an implementation") is empty only under SciML's present structure.
2. **Traits for the open sets, types for the library's own enumerations.** The problem (its right-hand side, Jacobian, mass matrix), the callback, the index and value providers, the trajectory, and the integrator as a callback sees it are traits: anyone implements them from outside. Algorithms, caches, controllers, interpolants and the solver's own integrator are types in an abstract tree, selected by dispatch: nobody outside joins them ([traits §14](../reference/traits.md#14-membership), "Abstract types stay"; [the earlier exploration §4.1](ndport-principled-traits.md#41-what-is-a-trait-what-is-a-type)). This is the split Rust makes between a trait and an enum, with Julia's dispatch doing the enum's `match`.
3. **Trait functions become signatures, parameters and subtraits.** `isinplace` is the declared signature of `rhs!`. `uType`, `tType`, `pType` are the trait's parameters `U`, `T`, `P`, defined by fields or stated ([§3.4](../reference/traits.md#34-parameters-and-associated-types)). `has_jac` is membership in `ODEJacobian <: ODERHS`, with the solver's default (finite differences) as the trait's default operation where the subtrait is absent ([§3.2](../reference/traits.md#32-defaults)). `alg_order` and `isadaptive` stay plain methods on the algorithm's concrete type, since the family is closed. A model-static number an open implementer must supply (a dimension) is an explicit type parameter, never a hidden one (meta plan, choice 10).
4. **Specialization is chosen per position by attribute, not per problem by a level.** The six specialization levels are points on one axis, applied to three fields (`f`, `p`, the callbacks). The design has the axis per position: the function is kept at a `Callable` bound, `Dynamic` by its default, the function itself under `compiled_for(f)` ([§5.8](../reference/traits.md#58-callable-functions-at-a-declared-signature), [§7.4](../reference/traits.md#74-a-struct-parameter-bounded-by-a-trait)); callbacks are kept values ([§7](../reference/traits.md#7-kept-values-dynamicx-compiledx-keptx)); the model, where it is its own type, enters `Dynamic` under `@default_with_dynamic_self` ([§6.3](../reference/traits.md#63-defaults-a-traits-default-and-annotations)). The caller overrides per value. It is a choice of speed, never of results ([§6.1](../reference/traits.md#61-the-attribute)).
5. **Values cross by their bound; code never crosses.** The user's function enters once, at the problem's constructor, and is seen at its declared signature from then on ([§6.2](../reference/traits.md#62-how-plain-values-enter-the-trait-world), [§6.5](../reference/traits.md#65-values-carry)). No `promote_f`, no `Void`, no wrapper installed "shortly before solving", no listed exceptions: a `SubArray` state, an `Any` element type and a given Jacobian are not special, because the bound converts nothing. The signature is checked at every call, and the result asserted ([§5.8](../reference/traits.md#58-callable-functions-at-a-declared-signature)).
6. **Declared fields and operations, not `getproperty` switches.** What the integrator view, the problem and the solution expose as data is a declared field, read at its offset ([§3.3](../reference/traits.md#33-fields)); what is computed (`ps`, `observed`) is an operation with a declared result. A `getproperty` switch is sugar for scripts. It stays in plain code, on the concrete type, in the package's ordinary module around its trait module ([§2](../reference/traits.md#2-trait-modules)). Trait code on a hot path reads declared fields and never goes through the sugar, because no constant propagation crosses the modes ([facts §6.3](../reference/facts.md#63-calls-between-the-modes)). This narrows [open issue 50](../open-issues.md) to the plain callers of a wrapped package; it does not decide it.
7. **Capabilities per type, with defaults where SciML asks per value.** A record whose optional field is given conforms to the subtrait, as a family member over its parameters; one whose field is `nothing` does not. Membership is per type ([§14](../reference/traits.md#14-membership)); the per-value question on a kept value is a trait cast, which is Optional ([§6.9](../reference/traits.md#69-trait-casts); [the earlier exploration §10.5](ndport-principled-traits.md#105-membership-decided-per-value)). The solver asks nothing: it calls `jacobian!`, which is the type's own or the default.
8. **An extension adds implementations and methods for its triggers' types only.** That is the rule for implementations ([§10.1](../reference/traits.md#101-who-may-implement)); carried to plain methods it is the discipline Rust enforces by coherence. The extension methods that P6-3 found winning at facts (`forwarddiff_compat_chunk_size(::Int)`, `anyeltypedual` fallbacks) are the ones that break it; the rest of SciMLBase's 20 extensions (`rrule` on `solve` with SciMLBase's problem types, `promote_dual` on duals) keep it.
9. **The integrator's type is the irreducible product.** Algorithm, state `U`, element `T`, parameters `P`, and for implicit methods the chunk and the linear solver (the solvers exploration §3). Everything else is cut by a position: the function by `Callable`, callbacks by `Vector{Callback}`, the options' functions (norms, `isoutofdomain`, `unstable_check`, progress) by `Callable` fields, the solution's problem by a kept value. The remaining parameters are explicit.
10. **Front ends and `remake` stay plain and thin,** behind a function barrier, since bounded keywords are limited today (T-48, T-39; `Callable` with keywords Planned; [porting B2](../intro/porting.md#b2-differential-equations)). Their cost is per solve, in microseconds. What a trait declares is rebuilt with `withfields` and `Like{t}` ([§5.6](../reference/traits.md#56-results-declared-types-like-withfields)); the rest by the constructor.
11. **Every move keeps results equal.** The attribute and the mode change speed, never results (G1, [facts §2.1](../reference/facts.md#21-g1-identical-or-error)). A move that changes a digest is a bug, not a design question.

## 4. The shortest route

The few structural moves that buy most, in order. Each keeps the workload's results equal to upstream's, by G1. "Buys" names what the move gives; "measured" names what the port has already measured of it, and against which number.

**Move 0 (done, P3): wrap by facts, nothing else.** `@trait_module` around NetworkDynamics; the SciML core from the bottom up (P6).
- Buys: trait code never invalidated by an unrelated load; strict mode refuses a winning pirate.
- Measured: the next pass after the plotting load recompiles 0.04 s instead of 4.7 s; the first simulation +16 s of facts compilation in the session (E-153). The costs met: Static.jl's promotion ([P3-1](ndport-pushback.md)), the constant-propagation loss at the mode boundary while hot callers stay plain ([P6-1](ndport-pushback.md): 29.2 against 15.0 ms), extensions rewriting facts at load ([P6-3](ndport-pushback.md)).
- What it teaches for the route: wrapping alone gives the guarantees, not the shape. The shape comes from the moves below, and each removes one of the costs met.

**Move 1: the right-hand side as a trait; the function kept at a `Callable` bound.** `ODERHS{T, P}` with `rhs!(…)::Nothing`, `ODEJacobian`, `ODEMassMatrix` as subtraits ([the earlier exploration §4.2](ndport-principled-traits.md#42-oderhs-the-right-hand-side-the-seam-from-networkdynamics)). `ODEFunction` conforms as a family; a user's type (`Network`) conforms by its own `rhs!`. The record's `f` is a struct parameter bounded by `Callable{RHSSig{P, T}, Nothing}` (TDE's `ODEProblem`, `TraitDifferentialEquations/src/ODECore.jl`). `perform_step!` calls `f` as before: a kept function is callable.
- Replaces: `promote_f`, `wrapfun_iip`, `Void`, the specialization levels for `f` (`DiffEqBase/src/solve.jl:1011–1060`, `norecompile.jl`), for the in-place path. `FullSpecialize` becomes `compiled_for(f)` at the constructor.
- Buys: a new function or model compiles nothing in the solver, in every case, with the signature checked; the hand-written wrapper and its exceptions go. The solver's loop is compiled per `(U, T, P, algorithm)` in the solver's image.
- Measured by proxy: P4's step 1 did this at NetworkDynamics' own seam (the component model behind `ComponentDynamics`): new equations compile 0.45 s instead of 15 s (E-152). The crossing from trait code into a family member costs about 390 ns and one allocation after open issue 48's fix ([P4-1](ndport-pushback.md)); a `Callable` call is an indirect call ([other-languages §3](../design/other-languages.md#3-compiled-for-what-the-bound-can-see), 3.95 ns measured on the function-call form). A Tsit5 step makes seven right-hand-side calls, so the per-step cost of this move is in the tens of nanoseconds against a step of microseconds; the port's remaining steady-state gap (33–41 against 15.3 ms) is the three per-batch crossings per right-hand side inside NetworkDynamics, not this seam.
- Needs: the tuple of `Callable`s for the dual signatures of implicit methods (W-29, Planned); Tsit5 first, Rosenbrock after.

**Move 2: callbacks and the integrator view.** `Callback` with `condition` and `affect!`; `IntegratorView{U, T, P}` as a trait of fields, `ODEIntegrator` conforming as a family with field mappings; the integrator keeps `Vector{Callback}`; `DEOptions`' functions as `Callable` fields ([the earlier exploration §4.3](ndport-principled-traits.md#43-integratorview-and-callback)).
- Replaces: `DiscreteCallback{F1…F5}` and `CallbackSet` as axes of the integrator's type; `_despecialize_callbacks!`; `affect!(integrator)` with the whole integrator.
- Buys: a new callback compiles nothing in the solver; `handle_callbacks!` compiled once per `(U, T, P)`; the integrator's type loses the callback and options-function axes. A callback's `affect!` sees declared fields (`integ.u`, `integ.t`, `integ.dt`) and operations (`add_tstop!`, `terminate!`), with the contract checked at `@implement`.
- Measured: not yet. The workload's line trips are events (the meta plan, choice 1), so this move reaches the workload; the cost per step is a split or a table call per callback ([facts §9](../reference/facts.md#9-the-dynamic-split)).
- Pushback met: which of `u`, `uprev` are writable is decided per field ([§3.3](../reference/traits.md#33-fields)); a callback that reads `integ.p` at its own type needs the checked downcast (open issue §2.16), today a plain assertion (porting B2).

**Move 3: the front end's ownership.** The body of `solve`/`init` for `AbstractDEProblem` moves to SciMLBase, the owner of the types; solver packages keep their methods on their own algorithm types (`__init(prob, alg::OrdinaryDiffEqAlgorithm)`, already a stakeholder's); the default algorithm becomes a value of an owned type (`DefaultODEAlgorithm` exists) chosen by the umbrella through a bounded method with a trait it owns (principle 1), not by `__init(prob, ::Nothing)` in NonlinearSolve (G7). Hooks SciMLBase declares and DiffEqBase fills (G3: `wrapfun_iip`, `promote_tspan`) go where move 1 leaves them: most disappear with `promote_f`.
- Replaces: the joint-owner declarations as the way to hold G1, G2, G6, G7, G14–G17; the 1,400 lines of `DiffEqBase/src/solve.jl` split between the owner (the body) and the solver (the typed methods).
- Buys: no pirate by the letter in the core, so strict mode holds without the widened exception that each joint owner adds ([traits §10.1](../reference/traits.md#101-who-may-implement), "What it costs"; the inside-out plan's check J). A checked contract where the front end hands the problem to an algorithm.
- Measured: the census (63; 57 held by joint owners; none avoidable by an implementation under the present structure, [the inside-out plan §2.1](../plans/2026-10-21-ndport-inside-out.md#21-the-classes)). The move is a restructure of SciML, which the port chose not to make (choices 27–28); joint owners are the orthogonal feature that stands in for it. It buys guarantees, not speed, so it comes after moves 1–2.
- Needs: the bounded method on a foreign function of a shape it has no bounded method of yet (lowering L-3, a deviation).

**Move 4: symbolic access as traits; the sugar kept plain.** `IndexProvider` and `ValueProvider` in SymbolicIndexingInterface, with `symbolic_container`'s delegation as `by` forwarding where the container is a field; `:ps` as an operation; the `getproperty` switches kept in the packages' plain modules, on concrete types ([the earlier exploration §4.5](ndport-principled-traits.md#45-indexprovider-and-valueprovider)).
- Replaces: informal method sets joined by fifty methods per provider; the `getproperty` overloads as the API trait code reads.
- Buys: getters compiled per index shape, not per provider; trait callers read declared fields at their offset, so the P6-1 loss falls away on the trait side; plain callers keep plain constant propagation because the sugar is compiled plainly.
- Measured: P6-1 (29.2 against 15.0 ms) is the number this move addresses on the trait side; open issue 50 decides the plain side.
- Pushback met: `observed` returns a closure of an open signature ([the earlier exploration §10.1](ndport-principled-traits.md#101-open-element-types-against-callables-constant-signature)).

**Move 5: the solution as a trajectory.** `Trajectory{U, T}` with `times`, `state`, `at`; `ODESolution` and `DiffEqArray` conform; the solution keeps its problem as a kept value, so its type has no `f` axis ([the earlier exploration §4.4](ndport-principled-traits.md#44-trajectory-a-solution-as-plotting-sees-it)).
- Buys: plotting helpers compiled once per key; the solution's type independent of the model.
- Measured: not needed for the workload after move 1 (the model's type is already cut at the right-hand side).

**What stays plain, and why that is fine.** Algorithms and caches (a closed family, types first); `perform_step!` and the controllers (fully typed over the key, so the facts mode costs them nothing, [facts §1](../reference/facts.md#1-terms)); `remake`, `promote_u0`, `promote_tspan`, `get_concrete_problem`, the keyword front ends (per solve, behind a barrier); the AD-rule extensions (methods on owned functions for the triggers' types); LinearSolve and NonlinearSolve behind their own front ends until move 3 reaches them; ensembles.

**What the route does not change.** Results, by G1 at every move. The abstract type tree of problems and algorithms: it stays as documentation and as the closed families' dispatch; the traits sit beside it, and a typed method still wins over a bound ([§5.5](../reference/traits.md#55-dispatch-types-first-then-traits)).

## 5. Pushback: where the principled form meets the references

None of these proposes a change. Each names the rule, what the principled form would want, and what the design offers instead.

- **PB-A. An algorithm trait generic over the problem.** Rust's `Algorithm<P>` with `type Integrator` per `P` is not expressible: a trait's parameters are associated types with one value per implementation, and input parameters, generic associated types and equations between type functions are not offered ([traits §3.4](../reference/traits.md#34-parameters-and-associated-types)); an operation's declared result names only its own trait's parameters and `Self` ([§3.1](../reference/traits.md#31-operations)). The design's substitute is dispatch on the algorithm's concrete type, a stakeholder's typed method, which fits SciML's closed family and gives no checked contract between `init`'s result and `solve!`. A user-extensible algorithm set with a checked contract would need either `Dynamic{Integrator{U, T, P}}` as `init`'s result (a split per step, acceptable) with the algorithm trait unparametrized, or a feature the design does not have. Recorded, not proposed.
- **PB-B. Associated constants.** `alg_order`, `isadaptive`, a component's dimension: no associated constants ([§3.4](../reference/traits.md#34-parameters-and-associated-types), "Not offered"). The stand-ins are plain methods on concrete types (closed families) and explicit type parameters (open sets; meta plan choice 10, the traits plan's PB-1). Already logged.
- **PB-C. A capability query on a kept value.** `has_jac(f)` on a `Dynamic{ODERHS}` is a trait cast ([§6.9](../reference/traits.md#69-trait-casts), Optional). The substitute, a default operation, covers SciML's uses where the default is a correct fallback (finite differences), and not where the library's behaviour differs by the capability's presence beyond a fallback. Also: a family member's conformance to the subtrait under a constraint on one parameter (`TJ`) relies on parameter-expression checks that are a deviation (T-6).
- **PB-D. The dual signatures.** `promote_f`'s four signatures are a tuple of `Callable`s at a struct parameter ([§3.7](../reference/traits.md#37-tuples-of-traits), [§7.5](../reference/traits.md#75-functions-kept)): Planned (W-29). A bound whose argument types name the method's `where` variables is refused ([§5.8](../reference/traits.md#58-callable-functions-at-a-declared-signature)), so the element type is fixed per implementation and a dual state is a sibling family member ([porting B2](../intro/porting.md#b2-differential-equations)); AD through `solve` with an open chunk stays plain until then.
- **PB-E. `AutoDespecialize`.** Boxing `p` behind a stable type and recovering it at the model's barrier is a checked downcast of a kept value at its own concrete type: open ([open issues §2.16](../open-issues.md#2-design)). Until decided, `P` stays an explicit parameter of the key, which is SciML's default level anyway.
- **PB-F. The extension-trait form.** Move 3 and principle 1 use a bounded method on a function the definer does not own, with a trait it owns ([§5.5](../reference/traits.md#55-dispatch-types-first-then-traits)). TraitWorld lets only the function's owner add a bounded method of a shape the function has no bounded method of yet (lowering L-3). A deviation to retire before move 3, not a design change.
- **PB-G. `getproperty` sugar and constant propagation.** Principle 6 keeps the sugar plain and the contract in the trait. It makes option (a) of [open issue 50](../open-issues.md) workable for a package whose hot callers are trait code; it does not help a plain hot caller of a wrapped package, which is the issue's case. The user decides.
- **PB-H. Keyword-heavy front ends.** T-48, T-39, `Callable` with keywords Planned: the front end stays plain ([the earlier exploration §10.10](ndport-principled-traits.md#1010-keyword-heavy-front-ends)).
- **PB-I. The six-argument limit of a `Dynamic` function** (T-51): `f(du, u, p, t)` has four; NetworkDynamics' edge functions exceed it (already logged, [porting 0.4](../intro/porting.md#04-where-dynamic-where-compiled)).
- **PB-J. The split's four.** A default algorithm as `Vector{Dynamic{…}}` over six solvers puts two beyond the split: a probe and an indirect call per step for those ([other-languages §11](../design/other-languages.md#11-heterogeneous-collections), 9–18 ns per call). Acceptable per step; the author chooses the four by declaring them first ([§6.8](../reference/traits.md#68-costs-and-choosing)).
