**In one paragraph.** Every statically compiled language studied resolves a variadic call **per arity** at compile time. Then it takes one of two roads. Either it compiles **per arity, or per pack of types** (C++ variadic templates, Rust's tuple impls by macro, Swift's parameter packs when specialized, Haskell's instance chains), so the arity is part of the instance's key. Or it **erases the variable part into one sequence value** of a single element type (Java and C# arrays, Scala's `Seq`, Swift's legacy `T...` arrays, C's `va_list`, Haskell `printf`'s argument list), so one body serves every arity. Julia's concrete `Vararg{E}` tail is the second road with a typed element: one compiled body for all arities of one concrete element type. Where a language erases functions to a fixed-arity type, an arity limit appears (Rust's tuple traits to 12, Scala 2's `Function22`, C#'s `Func` to 16, Swift's six tuple comparison overloads, FunctionWrappers.jl's 128). Each limit was lifted the same way: the arguments travel as **one value whose type carries the arity** (Rust's `Fn<Args: Tuple>`, Scala 3's `FunctionXXL` over an array, Swift's packs, Java's signature-polymorphic `MethodHandle` call sites), or the compiler synthesizes the missing type (C#). No system found records a variadic call's dependency specially: the arity is simply in the key of the instance or the call.

## 1. Dispatch and coherence with variadics

| Language | Mechanism | Per concrete arity, or an erased sequence? | Fixed arity against variadic |
|---|---|---|---|
| Rust | no variadic Rust functions; tuples; macros per arity | per arity: each tuple type is its own impl | not applicable |
| Swift | parameter packs; legacy `T...` | packs: per pack (type-checked generically); `T...`: an array | the scalar overload wins |
| C++ | variadic templates, pack expansion | per pack: one specialization per deduced pack | the non-variadic template is more specialized |
| Haskell | type classes over function types; type-level lists | per arity, by an instance chain; `printf` erases arguments into a list | not applicable |
| Scala | `T*` repeated parameters; generic tuples | `T*`: a `Seq[T]`; tuples: per type, as `h *: t` | the non-repeated alternative is more specific |
| Java | `T...` | erased: a `T[]` | phases: fixed arity first, varargs last |
| C# | `params T[]` (and collections) | erased: an array | the normal form beats the expanded form |
| C | `...`, `va_list` | erased: untyped, promoted | not applicable |
| Julia | `Vararg{T}`, `Vararg{T,N}`, splatting | dispatch per call's tuple type; compiled per arity up to a limit, then one widened body | ordinary specificity over tuple types |

### 1.1 Rust

- **No variadic Rust functions.** "Functions within external blocks may be made variadic by specifying `...` as the last parameter." Variadic parameters "can only be specified within `extern` blocks" with C-like ABI strings (`"C"`, `"cdecl"`, `"system"`, and others). *Verified:* [Reference, External blocks, "Variadic functions"](https://doc.rust-lang.org/reference/items/external-blocks.html#variadic-functions) (rules `items.extern.variadic`, `items.extern.variadic.conventions`).
- **Tuple impls up to a fixed arity, by macro.** "Due to a temporary restriction in Rust's type system, the following traits are only implemented on tuples of arity 12 or less. In the future, this may change." *Verified:* [std, primitive `tuple`, "Trait implementations"](https://doc.rust-lang.org/std/primitive.tuple.html#trait-implementations). The impls come from a recursive macro, `tuple_impls!(E D C B A Z Y X W V U T)`, which "will implement everything for (A, B, C), (A, B) and (A,)"; rustdoc shows them as one entry through `#[doc(fake_variadic)]`. *Verified:* [`library/core/src/tuple.rs`](https://github.com/rust-lang/rust/blob/master/library/core/src/tuple.rs), lines 8–20, 167, 231.
- **Functions take their arguments as one tuple.** `pub trait Fn<Args>: FnMut<Args> where Args: Tuple` with `extern "rust-call" fn call(&self, args: Args)`; unstable (`fn_traits`, #29625). *Verified:* [std, `Fn`](https://doc.rust-lang.org/std/ops/trait.Fn.html). So closures and `dyn Fn(A, B, C)` have no arity limit: the compiler builds the impl for each closure *(inference)*.
- **Variadic generics are unresolved.** "A draft for Variadic Generics has existed since ~2013, and there have been multiple postponed RFCs." The use cases listed include `iter::zip`, `futures::join`, "Fix the `Fn` traits, eliminate `"rust-call"` abi", and "Implement traits for tuples". The oldest proposal "proposes the basic idea that all variadic types can be seen as just a tuple with N elements". *Verified:* [lang-team, design notes, "Variadic Generics"](https://github.com/rust-lang/lang-team/blob/master/src/design_notes/variadic_generics.md).
- **Answer:** per concrete arity. A tuple type of arity n is one type; its impl is one impl. Coherence is ordinary coherence over tuple types.

### 1.2 Swift

- **Legacy variadic parameters are arrays.** "The values passed to a variadic parameter are made available within the function's body as an array of the appropriate type." "A function can have multiple variadic parameters." *Verified:* [The Swift Programming Language, Functions, "Variadic Parameters"](https://github.com/swiftlang/swift-book/blob/main/TSPL.docc/LanguageGuide/Functions.md).
- **Parameter packs (SE-0393).** The motivation names three workarounds: "Erasing all of the types involved, e.g. using `Any...`"; "Using a single tuple type argument instead of separate type arguments"; "Overloading for each argument length with an artificial limit". Its example: "the 6 overloads for each tuple comparison operator", "up to 6-element tuples". *Verified:* [SE-0393, "Motivation"](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0393-parameter-packs.md#motivation).
- **Runtime meaning of a pack expansion.** "At runtime, the pattern is repeated for each element in the substituted pack." *Verified:* SE-0393, "Proposed solution".
- **Overload resolution.** A scalar overload whose parameters can be forwarded to the pack overload "is considered a subtype of the parameter pack overload", and "scalar overloads are preferred over parameter pack overloads". The aim: library authors can "introduce new function overloads using parameter packs that generalize existing fixed-arity overloads while preserving the overload resolution behavior of existing code". *Verified:* SE-0393, ["Overload resolution"](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0393-parameter-packs.md#overload-resolution). The review's acceptance asked for this rule: "a fixed-arity overload is intuitively 'more specialized'". *Verified via search snippet:* [Accepted with modifications, Swift Forums](https://forums.swift.org/t/accepted-with-modifications-se-0393-value-and-type-parameter-packs/64382).
- **Packs are not tuples.** "Modeling packs as tuples with abstract elements" was rejected: "There is a fundamental ambiguity between forwarding a tuple with its elements flattened and passing a tuple as a single tuple value." *Verified:* SE-0393, "Alternatives considered". SE-0398 extends packs to generic types; SE-0399 lets a tuple hold a value pack expansion. *Verified:* [SE-0398](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0398-variadic-types.md), [SE-0399](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0399-tuple-of-value-pack-expansion.md).
- **Answer:** packs are type-checked once, generically, and resolved per pack at the call; the legacy form is an erased array.

### 1.3 C++

- **Pack expansion.** "A pattern followed by an ellipsis … is expanded into zero or more instantiations of the pattern, where the name of the pack is replaced by each of the elements from the pack, in order." "The number of elements of a pack is equal to … the number of arguments provided." *Verified:* [cppreference, Parameter pack](https://en.cppreference.com/w/cpp/language/parameter_pack.html), "Pack expansion".
- **Partial ordering prefers the non-variadic template.** "If … F is at least as specialized as G and vice-versa, and if G has a trailing function parameter pack for which F does not have a corresponding parameter, and if F does not have a trailing function parameter pack, then F is more specialized than G." The example: for `f(1, 2)`, "non-variadic template #3 is more specialized than the variadic templates #1 and #2". *Verified:* [[temp.deduct.partial]/11 and /8](https://eel.is/c++draft/temp.deduct.partial).
- **Coherence across instantiations is a rule without a check.** A specialization may have several points of instantiation, the end of the translation unit among them. "If two different points of instantiation give a template specialization different meanings … the program is ill-formed, no diagnostic required." *Verified:* [[temp.point]/7](https://eel.is/c++draft/temp.point).
- **Answer:** per pack. Each deduced pack of types is its own specialization.

### 1.4 Haskell

- **Variadic functions by type classes.** `printf :: PrintfType r => String -> r` formats "a variable number of arguments". The instance `(PrintfArg a, PrintfType r) => PrintfType (a -> r)` adds one argument per arrow. Its method, `spr :: String -> [UPrintf] -> a -> r`, collects the arguments into a list of a single type. *Verified:* [base, `Text.Printf`](https://hackage.haskell.org/package/base/docs/Text-Printf.html), "Implementation Internals".
- So the arity is resolved per call by an instance chain, and the arguments are erased into one sequence *(inference)*.
- **Heterogeneous lists.** HList provides "heterogenous lists (HLists) whose length and element types are known at compile-time". *Verified:* [Hackage, HList](https://hackage.haskell.org/package/HList). Instances over such lists are inductive: one for the empty list, one for a cons *(not verified)*.
- **Tuple instances to a fixed size.** "There is no upper bound on the size of a tuple, but some Haskell implementations may restrict the size of tuples … every Haskell implementation must support tuples up to size 15, together with the instances for Eq, Ord, Bounded, Read, and Show. The Prelude and libraries define tuple functions such as zip for tuples up to a size of 7." *Verified:* [Haskell 2010 Report, §6.1.4 Tuples](https://www.haskell.org/onlinereport/haskell2010/haskellch6.html). GHC's own bound: `mAX_TUPLE_SIZE = 64`, under the comment "All pretty arbitrary". *Verified:* [`compiler/GHC/Settings/Constants.hs`](https://github.com/ghc/ghc/blob/master/compiler/GHC/Settings/Constants.hs).
- **Answer:** per arity, by instance resolution; an inductive instance pair serves every arity.

### 1.5 Scala 3

- **Repeated parameters are a `Seq`.** "The type of such a repeated parameter inside the method is then the sequence type `scala.Seq[T]`." Applied to k arguments, the method "is taken in that application to have type" with "k − n occurrences of type S". *Verified:* [Scala 2.13 spec, Basic Declarations and Definitions, "Repeated Parameters"](https://scala-lang.org/files/archive/spec/2.13/04-basic-declarations-and-definitions.html) (Scala 3 keeps the semantics and changes the splice syntax: [Vararg Splices](https://docs.scala-lang.org/scala3/reference/changed-features/vararg-splices.html), verified).
- **Overloading.** "As specific as" compares the alternatives' parameter types; a repeated last parameter is taken as its element type only when the other alternative's last parameter is repeated too. *Verified:* Scala 2.13 spec, [Expressions, "Overloading Resolution"](https://scala-lang.org/files/archive/spec/2.13/06-expressions.html).
- **Tuples as HLists.** Tuples point "in the direction of a construct called Heterogeneous Lists"; "Scala 3 introduces types `*:`, `EmptyTuple` and `NonEmptyTuple`" to "define recursive operations on tuples"; type-class instances are written for `EmptyTuple` and `H *: T`. *Verified:* [Scala blog, "Tuples bring generic programming to Scala 3"](https://scala-lang.org/2021/02/26/tuples-bring-generic-programming-to-scala-3.html) (2021-02-26).
- **Answer:** `T*` is an erased sequence; tuples are per type, with inductive instances.

### 1.6 Java and C#

- **Java resolves in three phases.** "The first phase performs overload resolution without permitting boxing or unboxing conversion, or the use of variable arity method invocation." The third phase allows variable arity. "This ensures that a method is never chosen through variable arity method invocation if it is applicable through fixed arity method invocation." *Verified:* [JLS SE 21, §15.12.2](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.12.2).
- **A vararg method changes resolution at an arity it covers.** "The declaration of a variable arity method … can change the method chosen for a given method invocation expression, because a variable arity method is treated as a fixed arity method in the first phase. For example, declaring `m(Object...)` in a class which already declares `m(Object)` causes `m(Object)` to no longer be chosen for some invocation expressions (such as `m(null)`)." *Verified:* same section.
- **The variable part is an array.** The argument list "is evaluated as if it were written as `(e1, ..., en-1, new |T[]| { en, ..., ek })`, where `|T[]|` denotes the erasure of `T[]`". *Verified:* [JLS SE 21, §15.12.4.2](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.12.4.2).
- **C# has a normal and an expanded form.** A `params` member not applicable in its normal form may be applicable in its expanded form, "constructed by replacing the parameter array … with zero or more value parameters of the element type". The tie-break: "if `Mᵢ` is applicable in its normal form and `Mₑ` has a params array and is applicable only in its expanded form, then `Mᵢ` is better than `Mₑ`"; between two expanded forms, the one with fewer params elements wins. The expanded call "creates an instance of the parameter array type with a length corresponding to the number of arguments". *Verified:* [C# standard (draft v8), §12.6.2.3 "Run-time evaluation of argument lists", §12.6.4.2 "Applicable function member", §12.6.4.3 "Better function member"](https://github.com/dotnet/csharpstandard/blob/draft-v8/standard/expressions.md).
- **Answer:** both resolve per arity at compile time and pass an erased array.

### 1.7 Julia

- **`Vararg` in tuple types.** "`Vararg{T,N}` corresponds to exactly `N` elements of type `T`. Finally `Vararg{T}` corresponds to zero or more elements of type `T`." *Verified:* `base/docs/basedocs.jl` (docstring of `Vararg`); manual, [Types, "Vararg Tuple Types"](https://docs.julialang.org/en/v1/manual/types/#Vararg-Tuple-Types). `Vararg` itself is a value of the type `Core.TypeofVararg`, not a type (`src/jltypes.c:3152`) *(verified in source; the version that made it so is not verified)*.
- **Dispatch** is over the call's tuple type, by ordinary specificity; a `Vararg{T,N}` method fixes the count (manual, [Methods, "Parametrically-constrained Varargs methods"](https://docs.julialang.org/en/v1/manual/methods/#Parametrically-constrained-Varargs-methods), verified).
- **Splatting.** Inference unrolls `_apply_iterate` over a known tuple up to `max_tuple_splat` (32) elements (`Compiler/src/types.jl:169`; `Compiler/src/abstractinterpretation.jl:1715`, verified). A splat of unknown length goes through the runtime's `jl_apply` ([facts §5](../reference/facts.md#run-time-sites)).
- **Answer:** dispatch per concrete call type; compilation per arity only up to a heuristic limit (§2.1).

## 2. Specialization and monomorphization

### 2.1 Per arity, or per pack, and the limits

- **Julia widens long vararg calls.** `get_max_varargs` computes "the maximum number of times to unroll `Varargs{T}`, based on `m->max_varargs` (if specified) or a heuristic based on the maximum number of non-varargs arguments for the function type". The heuristic is the function type's `max_args` plus 2, minus the method's own arguments, and "`max_args` can increase as new methods are inserted". *Verified:* `src/gf.c:55`–`92`.
  - `max_args` is a per-function count: `update_max_args`, called from `jl_method_table_add`, raises it to the largest argument count of any method of the function (`src/gf.c:2229`–`2243`, `:2985`, verified).
  - Beyond that count, `jl_compilation_sig` specializes an unbounded `Vararg` tail on the common element type: "if all subsequent arguments are subtypes of type_i, specialize on that instead of decl … then specialize as (Symbol...)" (`src/gf.c:1456`, verified).
  - A bounded tail, `Vararg{T,N} where N`, is not widened. The manual: `f_vararg(x::Int...)` "will not specialize", but `g_vararg(x::Vararg{Int, N}) where {N}` "will"; and "One only needs to introduce a single type parameter to force specialization" (`h_vararg(x::Vararg{Any, N}) where {N}`). *Verified:* manual, [Performance Tips, "Be aware of when Julia avoids specializing"](https://docs.julialang.org/en/v1/manual/performance-tips/#Be-aware-of-when-Julia-avoids-specializing) (`doc/src/manual/performance-tips.md:591`–`650`).
  - Our patch keeps the exact specialization when the compileable signature only widens a vararg tail and the exact code is cached ([compiler §6.1](../reference/compiler.md#61-an-invoke-keeps-the-exact-specialization-over-a-widened-varargs-tail); `only_vararg_widened`, `Compiler/src/ssair/inlining.jl:830`).
- **C++ instantiates per pack, under depth limits.** The standard's implementation quantities include "Recursively nested template instantiations, including substitution during template argument deduction [1 024]", "Template parameters in a template declaration [1 024]", and "Arguments in one function call [256]". "The bracketed number following each quantity is a potential minimum value." *Verified:* [[implimits]](https://eel.is/c++draft/implimits). GCC's `-ftemplate-depth` defaults to 900, "as the compiler can run out of stack space before hitting 1024 in some situations". *Verified:* [GCC, C++ Dialect Options](https://gcc.gnu.org/onlinedocs/gcc/C_002b_002b-Dialect-Options.html).
- **Swift compiles generic code once and specializes as an optimization.** "The Swift compiler emits one block of concrete code that can perform `MySwiftFunc<T>` for any T." "If the generic function's definition is visible to the optimizer and the concrete type is known, the Swift compiler will emit a version of the generic function specialized to the specific type." *Verified:* [`docs/OptimizationTips.rst`, "Generics"](https://github.com/swiftlang/swift/blob/main/docs/OptimizationTips.rst). That packs follow the same rule is *(not verified)*; SE-0393 says only that pack code iterates "over each element in the parameter pack at runtime".
- **Rust monomorphizes per instance.** The collector lists items such as `peach::<u64>`; for incremental builds the partitioner makes per module one unit for "non-generic code" and one for "monomorphized/specialized instances". *Verified:* [rustc-dev-guide, "Monomorphization"](https://rustc-dev-guide.rust-lang.org/backend/monomorph.html). A tuple impl of arity n is its own item, so its instances are per arity *(inference)*.
- **Haskell** passes dictionaries; an instance method is compiled once, and an inductive instance builds a dictionary per use *(not verified)*.

### 2.2 How a pack crosses an ABI or dynamic boundary

- **Swift: a pointer and a length.** A type metadata pack is "a flat array of pointers to type metadata with a separately stored length". "When a type pack is passed, a data pointer is always passed … The pack length is also passed, immediately prior to the data pointer", unless another pack fixes it. Witness table packs have the same shape, without a length. *Verified:* John McCall, ["ABI for variadic generics"](https://forums.swift.org/t/abi-for-variadic-generics/55213), Swift Forums, 2022-02-09 (a design post; the shipped ABI may differ). SE-0393: "we anticipate that generic functions with type parameter packs will not require runtime support"; SE-0398: variadic types "make use of new entry points … being added to the Swift runtime", so they do not back-deploy. *Verified:* SE-0393 ["Effect on ABI stability"](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0393-parameter-packs.md#effect-on-abi-stability); SE-0398 "ABI compatibility".
- **C: untyped, promoted.** Each variable argument "undergoes special implicit conversions known as default argument promotions". The callee reads each with `va_arg` at a type it learns elsewhere, in the example from a format string. Since C23, `...` need not follow a named parameter. *Verified:* [cppreference, Variadic arguments (C)](https://en.cppreference.com/w/c/language/variadic.html); [Variadic functions (C)](https://en.cppreference.com/w/c/variadic.html).
- **Java: one native method, typed per call site.** A method is signature polymorphic when it is declared in `MethodHandle` or `VarHandle`, "has a single variable arity parameter … whose declared type is `Object[]`", and is native. For it, "The compile-time parameter types are the types of the actual argument expressions." *Verified:* [JLS SE 21, §15.12.3](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.12.3). The JVM caps a descriptor at 255 parameter slots: "A method descriptor is valid only if it represents method parameters with a total length of 255 or less." *Verified:* [JVMS SE 21, §4.3.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.3.3).
- **Scala 3: an array beyond 22.** "Functions beyond `scala.Function22` are erased to a new trait `scala.runtime.FunctionXXL`"; "Tuples beyond `scala.Tuple22` are erased to a new class `scala.runtime.TupleXXL`"; "Both of these are implemented using arrays." *Verified:* [Scala 3 reference, "Dropped: Limit 22"](https://docs.scala-lang.org/scala3/reference/dropped-features/limit22.html).
- **Rust:** the arguments of an `Fn` call are one tuple, passed by the `"rust-call"` ABI (§1.1).
- **Julia:** a splat of unknown length goes through `jl_apply` with an argument array; the callee runs its default owner's code ([facts §5](../reference/facts.md#run-time-sites)). A `cfunction` pointer has a fixed C signature. FunctionWrappers.jl defines `CallWrapper` methods for each arity from 0 to 128, plus a `Vararg` fallback, and builds a `cfunction` over them (`src/FunctionWrappers.jl:60`–`67`, `:90`, verified locally, version 1.1.3). TraitWorld's `_CallWrap{S}` does the same up to six arguments, with the comment "fixed arities: a varargs callee would not be specialized behind the pointer" (`TraitWorld/src/core.jl:1165`–`1173`); `Erased`'s call refuses more (`:1199`).

## 3. Incremental compilation and dependency tracking for variadic code

No source found treats a variadic call's dependency specially. In each system the arity is part of an ordinary key.

- **rustc.** "Only the steps between `HIR` and `LLVM-IR` are query-fied. That is, lexing, parsing, name resolution, and macro expansion are done all at once for the whole program." *Verified:* [rustc-dev-guide, Overview, "Queries"](https://rustc-dev-guide.rust-lang.org/overview.html) (as of November 2022, by the page's own date). So the tuple impls a macro expands are re-expanded on every build; after expansion each is an ordinary item, tracked by queries like any other *(inference)*. Dependency nodes "are identified by a fingerprint of the query key"; results get "a 128 bit hash value", which gives early cutoff. *Verified:* [rustc-dev-guide, "Incremental compilation in detail"](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html). An instance's key holds its generic arguments, so the tuple type, and so the arity *(inference)*.
- **Swift.** Dependencies are names: top-level names, member names, dynamic lookups. "The 'depends' sets are tracked by instrumenting lookups in the compiler." The grain is the file; a change to an external dependency rebuilds the whole module. The document does not mention generics, specialization or packs. *Verified:* [`docs/DependencyAnalysis.md`](https://github.com/swiftlang/swift/blob/main/docs/DependencyAnalysis.md). How packs enter the fine-grained dependencies is *(not found)*.
- **C++.** The language tracks nothing; it forbids two points of instantiation with different meanings, without a diagnostic ([temp.point]/7, §1.3). With `-fno-implicit-templates`, GCC will "only emit code for explicit instantiations" (GCC manual, verified). How C++20 modules place instantiations of a pack is *(not verified)*; build systems track headers at file grain *(not verified)*.
- **GHC.** Usages record entities with fingerprints; a non-orphan instance is fingerprinted with its class or type ([the precedents research, §1](incremental-precedents-research-2026-10-27.md)). A tuple instance of each arity is its own declaration; an inductive instance pair is two declarations whatever the arity *(inference)*.
- **Julia.** An edge at a signature with a `Vararg` tail is invalidated when a new method intersects that signature, as for any edge ([facts §4.3](../reference/facts.md#edges-and-invalidation)). The compileable signature of a vararg method depends on `max_args`, which any method of the function, of any arity, raises (§2.1). That count changes which specialization serves a call, not what dispatch answers *(inference)*.

## 4. Fixed arity limits as a design choice

| System | Limit | Why | Lifted by |
|---|---|---|---|
| Rust std, tuple traits | 12 | "a temporary restriction in Rust's type system" (std docs) | open: variadic generics, unresolved since ~2013 (lang-team notes) |
| Rust `Fn` | none | the arguments are one tuple type, `Args: Tuple` | — |
| Haskell 2010 | instances to 15, `zip` to 7 | implementations "may restrict the size of tuples" (Report §6.1.4) | GHC: tuples to 64, "pretty arbitrary" |
| Scala 2 | `Function22`, `Tuple22` | one class per arity *(not verified)* | Scala 3: `FunctionXXL`, `TupleXXL` over arrays |
| C# | `Func` to 16 parameters | one delegate type per arity ([`Func<T1,…,T16,TResult>`](https://learn.microsoft.com/en-us/dotnet/api/system.func-17), verified) | C# 10: "The compiler chooses an available `Func` or `Action` delegate, if a suitable one exists. Otherwise, it synthesizes a delegate type." ([Lambda expressions, "Natural type"](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/lambda-expressions#natural-type-of-a-lambda-expression), verified) |
| Swift stdlib, tuple comparison | 6 | "Overloading for each argument length with an artificial limit" (SE-0393) | parameter packs, with scalar overloads still preferred |
| SwiftUI `ViewBuilder` | 10 children *(not verified)* | fixed-arity `buildBlock` overloads *(not verified)* | a `buildBlock<each Content>` overload ([Apple docs](https://developer.apple.com/documentation/swiftui/viewbuilder), seen in search results only) |
| Java | 255 parameter slots | the class-file format (JVMS §4.3.3) | — |
| C++ | ≥ 1 024 nested instantiations, ≥ 256 call arguments (minimums) | compiler resources ([implimits]) | flags (`-ftemplate-depth`) |
| FunctionWrappers.jl | 128, then a `Vararg` fallback | each arity a method, so the `cfunction` is specialized | — |
| TraitWorld `Erased` (T-51) | 6 | as FunctionWrappers, a smaller table | see §5.2 |

**What motivated lifting them.**
- Generality without a table: SE-0393 lists the three workarounds that packs replace (erasure, one tuple argument, overloads to an artificial limit).
- Keeping existing code's resolution: Swift and C++ both rank a fixed-arity candidate above a variadic one, so a pack overload can be added beside existing fixed ones.
- Erasure at the representation, not at the type: Scala 3 keeps the arity in the function type and erases only the storage, into an array, above 22.
- A synthesized type where none fits: C#.

## 5. What this suggests for us

The suggestions are proposals for review. None is in force. Each names the reference section it would touch.

### 5.1 How facts at vararg signatures should be framed

**Finding.** Every language resolves variadics per arity, then either compiles per arity or erases the tail to one sequence of one element type. Julia's concrete `Vararg{E}` tail is the typed form of the second: like Java's `T[]` for a final `T`, it holds values of one concrete type. Java's §15.12.2 note shows the coherence hazard: a vararg method changes resolution at an arity a fixed method covers (`m(Object...)` beside `m(Object)`). Our per-arity stakeholder rule answers that hazard.

**Suggestion.**
- Frame a fact at `Tuple{F, C₁…Cₙ, Vararg{E}}` as a **family of dispatch tuples, one per arity k ≥ 0**, as the union-split form stands for its splits. Each member is a dispatch tuple with the same owners. The family has one edge, at its own signature; Julia's intersection check makes it exact, as for a union in a tuple argument. This is what the facts §3 row says ("Every value's type is a dispatch tuple with the same owners"); the suggestion is to say "family" and "one edge" explicitly.
- State that **which specialization serves the fact is not part of it.** Julia compiles up to `max_args` arities exactly and one widened body beyond; `max_args` grows with any method of the function, so the serving specialization can move. Dispatch, and so the fact, does not.
- Keep a tail of an abstract or kind element, or of a union, a run-time site. No language studied gives a variadic tail of mixed element types one erased body with static dispatch inside it: those are either per pack (C++, Swift) or untyped (C, Java `Object...`).
- Teaching: a pack's counterpart in Julia is `Vararg{Any,N} where N`, a tuple per arity; a homogeneous concrete tail is the erased-array counterpart.
- **Touches:** [facts §3](../reference/facts.md#facts-and-fact-signatures) (the concrete `Vararg` row, its "why" column); [facts §1](../reference/facts.md#1-terms) (stakeholders per arity: cite Java's hazard as the reason, in `design.md` or alternatives, not in the reference); [compiler §1.2](../reference/compiler.md#12-fact-signatures) and [§6.1](../reference/compiler.md#61-an-invoke-keeps-the-exact-specialization-over-a-widened-varargs-tail) (the serving specialization and `max_args`); [intro/porting.md, B4](../intro/porting.md) ("A splat is a fact only with concrete elements": add the `Vararg{Any,N}` idiom).

### 5.2 A principled replacement for T-51's arity limit

**Finding.** T-51 is the third workaround of SE-0393's list, "Overloading for each argument length with an artificial limit". FunctionWrappers.jl takes the same road with 128. Every system that lifted such a limit did it by one of two means: **specialize per arity from one declaration** (Swift's packs, C++ packs, Rust's compiler-built `Fn` impls, C#'s synthesized delegates), or **pass the arguments as one value whose type carries the arity** (Rust's `Args: Tuple`, Scala 3's `FunctionXXL` over an array, Java's per-call-site descriptor, Swift's pack pointer and length).

**Suggestion, two candidates, to measure before choosing.**
- **(i) One declaration, specialized per arity.** Replace the seven `_CallWrap{S}` methods by `(::_CallWrap{S})(o, args::Vararg{Any,N}) where {S,N} = o(args...)::S`. Julia's manual says a `Vararg{Any,N} where N` method specializes; `jl_compilation_sig` widens only an unbounded tail (`src/gf.c:1456`). The `cfunction` stays per `(A, F)` and per arity, with no table. TraitWorld already uses this idiom (`opcall`, `core.jl:1087`; `_certified_call`'s fallback, `certificate.jl:51`). Open points *(inference, untested)*: whether `cfunction` compiles the exact signature for a `Vararg{Any,N}` method; and the `Type{T}` and function elements, which Julia does not specialize when passed through (`certificate.jl:41` notes this widening; today's untyped fixed-arity `_CallWrap` has it too).
- **(ii) One tuple argument.** The pointer takes the arguments as one `Tuple{A...}`, by reference, and the wrapper splats it. The ABI is then arity-independent, like Rust's `"rust-call"` and Scala's `FunctionXXL`. It costs building the tuple per call; for non-bits elements that may allocate *(not verified)*. Scala uses this road only above 22; we could use it only above a threshold.
- Prefer (i): it keeps one declaration and today's calling convention, and it is the Swift and C++ answer. Fall back to (ii) above an arity if (i) fails the check.
- **A related rule for `Callable`.** In every system, an erased function type has a fixed arity: a C# delegate, a Java descriptor, a Rust `Fn<Args>` tuple, a Scala `FunctionN`. So `Callable{A, S}` with an unbounded `Vararg` tail in `A` should be refused, or be an open issue. `Vararg{T,N}` with `N` given is a fixed arity and fine.
- **Touches:** [traits §5.8](../reference/traits.md#58-callable-functions-at-a-declared-signature) (Status line; Rules: `A` without an unbounded `Vararg` tail) and [traits §17, T-51](../reference/traits.md#17-deviations) (retired if (i) or (ii) holds); [lowering §12](../reference/lowering.md#12-callable-and-dynamiccallable) ("the callee is `_CallWrap{S}`, with fixed arities up to six"); [intro/porting.md](../intro/porting.md) (the T-51 lines and NetworkDynamics' seven-argument edge function).
- **An experiment to register first** (the question, and what would change the design): (i)'s `cfunction` at 7 to 12 arguments compiles the exact specialization, boxes no more than today at 1 to 6, and costs the same per call. If it boxes or widens, take (ii) above six.

### 5.3 How a vararg fact should enter a fingerprint

**Finding.** No system found fingerprints a variadic call specially. rustc keys an instance by its generic arguments; GHC fingerprints each instance declaration with its class or type; Swift records names. The arity, or the pack, is simply in the key. Julia's edge at a `Vararg` signature is one edge, invalidated by any method that intersects it.

**Suggestion.**
- **The fact's key is its signature as recorded,** the family `Tuple{F, C₁…Cₙ, Vararg{E}}`, not the arity of the call that produced it. An entry compiled for an exact arity has a dispatch tuple as its fact; an entry compiled at the widened signature has the family. They are different entries.
- **F2 for a family fact** is the stakeholders' methods of `F` whose signatures intersect the family at any arity. This is plan §5b's "narrow F2 to the stakeholders' methods that intersect the fact's signature", applied to a signature with a tail; the type intersection Julia uses for its own invalidation computes it.
  - The stakeholders: the owners of `F`, of each `Cᵢ`, and of `E` (for `E`, at arities with at least one element). A method with a `Vararg` in its own signature intersects many arities and enters every family fact it meets, as GHC's instance enters with its class or type.
- **Leave `max_args` out of the fingerprint.** It decides which specialization serves a call, not what dispatch answers. Its effect on the cache is a miss: after a change, a call may ask for an exact specialization where a widened entry was stored, or the reverse *(inference)*.
- **Splats of unknown length** are run-time sites: no edge, so nothing to fingerprint ([facts §5](../reference/facts.md#run-time-sites)). A splat of a known tuple up to `max_tuple_splat` (32) is a fact at its concrete arity.
- **Touches:** [the plan, §5b](../plans/2026-10-27-facts-keyed-cache.md#5b-an-open-choice-after-e-194-the-identitys-grain) (F2: a sentence on family facts; the narrowing refinement); [facts §4.3](../reference/facts.md#edges-and-invalidation) (one edge per family fact) once the cache's reference section exists; E-195's cases (add a vararg method by a type owner at a fixed arity, and a new method of `F` that only raises `max_args`).
