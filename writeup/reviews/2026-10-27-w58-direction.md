Reviewer: fresh eyes, files read only, nothing run (2026-10-27). Sources:
- `writeup/plans/2026-10-27-ttfx-sciml-makie.md` (§5), `2026-10-27-session-cache.md` (rev. 2), `2026-10-27-port-architecture-ttfx.md` (rev. 2, §2b), at 0c277cf;
- `writeup/open-issues.md` 72–74; `writeup/record/experiments.md` E-168 to E-176; `writeup/design/evidence.md` §3; `writeup/state.md`; `writeup/record/todo.md`; `writeup/record/INDEX.md`;
- `experiments/ttfx/` at ad9ed69: README, `run.sh`, `summarize.py`, `cache/record_cis.jl`, `cache/make_cache.sh`, `probe_floor*.jl`, `probe_external.jl`, the logs `p175`, `p175s`, `p176`;
- TraitWorld 04095fe, 003ce8f, e6d5976; `julia-1.13/base/loading.jl`; Makie 0.24.16 in `ndport/pkgs/Makie.jl`.

Judged against the user's goal (the plan §1) and the user's constraints: quick experiments; a port with upstream's features and API, called the same way; a cache that builds up across sessions.

## Verdict

- **The measurements are sound for what they measured.** The runs agree within 1–2%. The CodeInstance-level emulation fixed the roots-only artefact. The load profiles and E-176's trees are clear.
- **Three conclusions overreach:**
  - "about a second after the load in every setting" holds for a session that replays its own recorded session, and was not measured for C (finding 3);
  - "the load follows the methods" is a five-point correlation with one inversion (finding 8);
  - the estimate of 2.6–2.7 s is a lower bound. With the terms it leaves out, about 3–4 s (finding 5).
- **Lean trees serve the user's goal, but as planned they are a plain packaging change.** No measurement so far shows the trait design buying anything on this workload once a cache exists. The plain twins beat the demonstrators at every step that the cache does not equalize. The note's sentence "a trait core is what makes the split possible" is contradicted by upstream's own split packages (finding 1).
- **The lean tree also collides with "upstream's API, called the same way".** Makie's statistics recipes need their heavy dependencies (finding 2).
- **The harness cannot see stale images** (finding 4).
- **Next build, ranked:**
  1. the cache split by dependency set, with order B and a late-loaded package: the only quick test of a trait-specific claim;
  2. a lean Makie fork, plain first, then compiled by facts;
  3. a lean Rosenbrock fork;
  4. a trait-core plotting slice.
- **The record has nine stale or contradictory places** (finding 10).

## Findings

### 1. The direction has no trait-specific hypothesis, and the data so far favour plain code (blocking for "lean trees first" as the port's aim)

Evidence:
- Port note:29: "A trait core is what makes the split possible: a narrow, declared interface between the core and its recipes, backends and algorithms." No measurement backs this.
- Upstream already splits in plain Julia:
  - OrdinaryDiffEq's sublibraries: `using OrdinaryDiffEqTsit5` takes 0.34 s and 83 packages (`experiments/ttfx/logs/p176/trees.log`);
  - Makie already has an extension (`DynamicQuantities` in `[weakdeps]`, `ndport/pkgs/Makie.jl/Makie/Project.toml`).
- E-176 itself finds "a trait world is not cheap to load by any mechanism of its own" (ttfx README:201). An implementation adds as many methods to a trait's functions as a plain package adds to the core's functions (ScaleL: 1,764 registrations).
- On the user's measure, plain code is at least as fast in every pair measured:
  - with a cache: Dp 0.64 s against D 0.97 s (ttfx README:139, :179);
  - load: Dp 0.16 s against D 0.45 s (README:196–197);
  - at scale: S 3.52 s against C 3.85 s (README:194–195).
  - The traits' one measured gain, the second model (0.056 against 0.33 s), disappears with a cache: Dp 0.04–0.05 s (README:139).
- Order B, the facts mode's protection (C/b again 0.04 s against U/b 0.44 s), is shown without a cache. It comes from invalidations by CairoMakie's large tree. A lean tree removes many of those invalidations, so it may also remove the advantage. At the small scale, Dp/b loses nothing either (again 0.02 s, README:49).
- The user asked exactly this (the plan:13): "why traits don't buy anything for small libraries?"

What a trait core could add, concretely, each testable:
- **(a) Cached code that stays valid when parts of a lean tree load late.** A lean tree turns features into packages loaded on demand, in varying orders. Plain cached code can be invalidated by such a load, and a plain cache must then be keyed by load order (the combination caches). Facts claim one cache per environment.
- **(b) The same API on a lean tree.** A recipe or algorithm declared by a trait in the core, its implementation in a package the core knows by key and loads at first use. This would keep `hist(x)` working without `using StatsBase`. It does not exist. Plain Julia can write lazy stubs too, so the claim must be that the trait version needs no `invokelatest` at the call site, invalidates nothing in the core, and is checked against the bound.
- **(c) Not a load mechanism of its own:** E-176 rules that out.

Fix:
- Port note §2b: replace the sentence with (a) and (b) as hypotheses, each with its experiment.
- The experiment for (a): the same lean tree in plain and trait form (D and Dp are its small form), both with a cache split by dependency set. Three sessions: order A; order B; a feature package loaded mid-session. Count the cached CodeInstances lost and the seconds recompiled after the late load. Prediction: the facts form loses about zero; the plain form loses what the late load invalidates. If the plain form also loses nothing, the claim is dropped for this workload and the plan says so.
- (b) goes to `open-issues.md` §2 as a design question.

### 2. Lean trees against "upstream's features and API, called the same way" (major)

Evidence:
- The user (plan:13): "a full port of either with all features? Called like the upstream packages are?"
- Makie's core recipes use the heavy packages: `src/stats/hist.jl`, `density.jl`, `boxplot.jl`, `violin.jl`, `ecdf.jl`, `hexbin.jl`, `crossbar.jl`, `distributions.jl` (StatsBase, KernelDensity, Distributions); `src/dim-converts/unitful-integration.jl` (Unitful); `src/conversions.jl`. Distributions is the largest single source of external methods (2,248; README:200).
- Port note:29 and :36 move these to "extensions, separate packages". Then `hist(x)` needs `using StatsBase` first: a changed API.

Fix:
- Record the conflict in `open-issues.md` §1 for the user: either (i) the lean port changes how the statistics recipes and units are called, or (ii) the design gains on-demand loading by trait key (finding 1(b)).
- Until decided, the lean fork's measurements say which features they drop.

### 3. "With a cache, the work after the load is about a second in every setting" overreaches (major)

Evidence:
- **Self-replay.** Each cache was recorded from the very session it is measured on: the same script, functions and shapes (`cache/make_cache.sh`:99; `run.sh` `/c`). That is the case of a user who re-runs a script, which is fair. It is not a cache that builds up across varied use.
- **Recurrence across shapes** was measured only with the roots-only cache: S/n matched with a perturbed cache still compiles 6.3 s in the first solve (README:111). It was not repeated at the level of CodeInstances.
- **C has no cache measurement.** The facts-compiled stack is the setting closest to a trait world at scale. The previous review's M9 item 2, an owner-aware record for C, is not done. "Every setting" means S, S/n, D and Dp.
- **The cached S session still compiles most of its time after the load.** From `logs/p175s/S-pc-1.log`: first solve 0.46 s (0.45 compiling), first plot 0.27 s (0.20), second model 0.22 s (0.19). That is 0.84 s compiling of 0.99 s. The share keyed on `Main` (the floor) and the share lost to the 360 refused statements (README:186) are not separated. Python's 1.0 s after its load is work, not compilation.

Fix:
- Qualify the sentence in the plan (:78), the cache note (§2), issue 72, evidence §3 and state.md: "for a session that repeats the recorded call shapes".
- Re-run E-173's recurrence at the level of CodeInstances (S auto-specialized; minutes).
- Record C with an owner-aware cache.
- Split S's remaining 0.84 s into `Main`-keyed and refused statements. The recorder already lists what the cached session creates (`RECORD_LIST`).

### 4. The harness does not detect stale images (major)

Evidence:
- `run.sh`:13 runs with `--compiled-modules=existing`. In `julia-1.13/base/loading.jl`:2777–2781 only mode 3 (`strict`) errors when no valid image exists. Mode 2 (`existing`) falls through and loads the package from source, without a "Precompiling" line.
- `summarize.py`:6 looks for "Precompiling", "Rejecting cache" and "ERROR". "Rejecting cache file" is a debug message, printed only with `JULIA_DEBUG=loading`, which `run.sh` does not set.
- E-176 found C's and ScaleL's images stale after TraitWorld's commits only by magnitude: loads of 33 s and 12 s (`logs/p176/C.log`, `ScaleL.log`). A small stale package (0.1–0.5 s) would pass unseen.
- TraitWorld changed three times in the afternoon (04095fe 13:16, 003ce8f 15:11, e6d5976 15:20). D's three-fix row runs on e6d5976; its comparison row, "matched, no cache", runs on 04095fe (README:179–180).

Fix:
- Use `--compiled-modules=strict` where the build supports it. Otherwise assert after the load step that every loaded module came from an image, and print the TraitWorld commit in each log's header.
- Re-precompile C before any further C measurement.
- Re-run D matched without a cache on e6d5976 (one session pair).

### 5. The estimate of 2.6–2.7 s is a lower bound; about 3–4 s is more credible (major)

The estimate (README:209; port note:32): plotting core 1 s + solver 0.5 s + startup 0.1 s + 1 s after the load. The terms it leaves out:

| Term | In the estimate | From the record |
|---|---|---|
| Makie's own code on the lean tree | about 0.3 s | Makie's image 0.71 s in the full tree, CairoMakie 0.17 s (E-169). A core needs well under half of Makie's own load to reach 1 s. |
| Rosenbrock's own code | 0 | The 0.47 s floor is Tsit5, ForwardDiff and DiffEqBase. Rodas5P needs OrdinaryDiffEqRosenbrock and its differentiation layer, part of the 0.73 s (README:207). |
| TraitWorld and facts at load | 0 | D over Dp +0.29 s; C over S +0.33 s. |
| The cache's own load | 0 | S +0.1–0.15 s (`logs/p175s` load 3.58–3.66 s against 3.52 s). Not measured against size (previous review M4, M9 item 3). |
| Overlap of the two trees | 0 | Shared packages (StaticArrays, ForwardDiff's dependencies): perhaps −0.1 s. |
| Work after the load | 1.0 s (plain S, self-replay) | D's is 0.4 s; C's is unmeasured (finding 3). |
| Strict mode | off | its prototype adds 6.6 s to C's load. |

- Sum with these terms: about 2.9–4.0 s. The target (about 3 s) is reachable at the low end, not shown.
- The estimate's load is at least 1.6 s. That fails the plan's own prediction "load at most 1.2 s" (plan:41), which no document mentions.

Fix:
- State the estimate as a range with the table's terms, strict mode off, for a session that repeats its shapes.
- Record the failed load prediction in the plan's phase 3c outcome.
- Bound Makie's own share from the existing `@time_imports` logs before forking: floor plus Makie's image plus CairoMakie's, about 1.6 s.

### 6. E-176's pre-registered decision rule pointed the other way (major)

Evidence:
- The registry row (experiments.md:261), written before the run: a low trait-world load because of few external methods "makes the port's narrow interfaces a load measure, and the Makie port's first aim; no such relation leaves the load to Julia's loader (open issue 73's other options)."
- The outcome is the second branch: "not by a mechanism of its own".
- The decision (plan:88) takes the first branch's action: lean trees as the port's first aim, and the loader changes "a second lever".

Fix:
- The plan's phase 3c decision says why it departs from the registered rule. "The tree's size" is a third outcome the rule did not foresee.
- Or keep both levers ranked. They compound: activation searches each insertion against a smaller table in a lean tree, and edge validation scales with the edges loaded. A loader probe that remembers validation for an unchanged environment is a Julia change, not a trait change, like the lean tree. Both are plain levers; say so.

### 8. The floors and the methods law are weaker than stated (minor)

Evidence:
- The floors (`probe_floor.jl`, `probe_floor_solver.jl`) are measured alone, each in its own session. They leave out:
  - Makie's `__init__`;
  - the activation of Makie's 1,358 external methods;
  - the other tree's methods already in the table.
- The list of the plot's dependencies is "plausible" (README:205), not derived from the workload's compiled code.
- "The load follows its size in methods" (README:200) rests on five points with one inversion: Dp adds 6,925 methods and loads in 0.16 s; ScaleL adds 5,896 and loads in 0.30 s. Native code size or edges matter as well.

Fix:
- Say "grows with the tree" rather than a law in methods.
- Derive the plot's dependency set from the modules of the CodeInstances the plot creates (the recorder already has them). Measure the solver's and the plot's floors in one session.

### 9. Order effects, the two cores, the warm-up (minor)

- **Order effects:** settings run in sequence, each with its own warm-up and depot. The two measured runs agree within 1–2%. No sign of an order effect.
- **The two cores** (`taskset -c 0-1`, one Julia thread, OpenBLAS at one thread): the load and the first calls are single-threaded in Julia and in Python. Not a confound at this spread. The load average (0.6–1.3) is logged per run.
- **What the warm-up hides:**
  - a cold page cache: the first session after a boot reads the images of 381 packages. That favours Python and lean trees further, and is outside the stated measure. Say so.
  - the first session that records a cache: it pays the full compile, and the builder runs after it.
  - neither changes a conclusion.

Fix: one sentence in the README's harness description.

## Answers to the questions

**1. Do the measurements support the conclusions?**
- Yes for the load profiles, the trees and "the load is what remains".
- With qualification for "about a second after the load": self-replay; not C; mostly still compiling (finding 3).
- The floors are floors, not an estimate of a core (findings 5, 8).
- Stale images are a live risk the harness cannot see (finding 4).
- Order effects and the two cores: no confound (finding 9).

**2. Is "lean trees first" right, and is it a trait question?**
- It is the right lever for the user's number. The load is 3.5 s of a session whose remainder is about 1 s.
- As written it is plain packaging. Upstream does it already (OrdinaryDiffEq's sublibraries), and it would undercut the project's claim if presented as the trait design's result.
- It collides with "called the same way" (finding 2).
- The trait contribution to test: cached code valid across late loads (1a), and the same API with on-demand implementers (1b). The experiment is in finding 1.

**3. Is 2.6–2.7 s credible?** As a lower bound. With the omitted terms, about 3–4 s, strict mode off, for a session that repeats its shapes (finding 5).

**4. The next build, ranked:**
1. **A cache prototype, narrowed: the emulation split by dependency set** (a solver part and a plotting part, each built in a process that loads only its dependencies), run in order B and with a feature package loaded mid-session; D against Dp, then S, then C with an owner-aware record.
   - About an hour of machine time: four cache packages, sessions of seconds.
   - It is the only candidate that tests a trait-specific claim (finding 1a). It also settles the cache's key (environment or load order) and the previous review's M2 and M3.
   - A TraitWorld implementation should wait for its result.
2. **A lean Makie fork, plain:** Makie's own code kept; StatsBase, KernelDensity, Distributions, Unitful, ImageIO, FFMPEG, Downloads, REPL and Pkg (through FileIO) moved to extensions or out of the workload's path.
   - Precompiling Makie and CairoMakie takes perhaps 10–20 minutes, alone; then sessions.
   - It measures the estimate's largest term (2.7 s → ?) and Makie's own share (finding 5). It also lists exactly which API changes (finding 2).
   - Before it, at no machine cost: walk `env_up/Manifest.toml` for which features bring which packages, and sum their `@time_imports` shares from the existing logs.
   - Compile it by facts afterwards, to measure the facts load cost on a lean tree.
3. **A lean Rosenbrock fork:** a bounded gain (at most 0.73 s, likely 0.4–0.5 s). It is plain and upstream-shaped. First read OrdinaryDiffEqRosenbrock's own increment from the existing import logs.
4. **A trait-core plotting slice with Makie's API:** the build that finally tests the claim on the plot, but not small. Scope it after 1 and 2: its load budget is the lean fork's measured core, and its trait contribution is what 1 shows.

**5. Stale or contradictory:** finding 10 (nine places), and the port note's internal contradictions (finding 7).
