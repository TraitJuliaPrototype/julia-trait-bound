# Review: the TTFX plan for SciML and Makie (`writeup/plans/2026-10-27-ttfx-sciml-makie.md`, W-58)

Reviewer: fresh eyes, files read only, nothing run (2026-10-27). Sources: the plan as committed at 88c8942; `experiments/ttfx/` (scripts, `env_up`, `env_core`, `logs/try/py-1.log`, `logs/precompile-*.log`); julia-1.13 checkout at 252edca933, its `usr/lib/julia/sys.so` dated 2026-10-27 11:58; TraitWorld main bbfc130; the ndport clones on their `port` branches.

Judged against the user's goal (plan §1) and the constraint "Remember to design experiments that give feedback quickly. Nothing that runs for hours."

## Verdict

- **The direction is right.** Measure first (phases 1–3), then design (4–5), then build (6). Each measuring phase is minutes of machine time.
- **Phase 1, as scripted, would mislead its own decision.** Two causes:
  - the harness can precompile inside a measured session without saying so (B1);
  - the Julia scripts favour D: D's calls hit TDE's cached keys, while S's calls miss OrdinaryDiffEq's (B2).
- **The premise's main risks are deferred.** Load time, strict mode's load cost and per-session work in TraitWorld are the likeliest ways for a large trait core to lose to Python. Measurements already in the record point that way. The plan reaches them only conditionally in phase 3, and tests scale only in phase 6.
- **Fix before the first run:** B1, B2, M3 and M8. Then add the cheap probes of M2, M5 and M7 to phases 1–2. With those changes the six phases can decide the question in days, with no run longer than minutes.

## Findings

### B1. The harness can precompile inside a measured session, silently (blocking)

**Evidence.**
- S's depot differs between precompiling and running:
  - `experiments/ttfx/precompile.sh:12` precompiles into `$R/ndport/depot-stock`;
  - `experiments/ttfx/run.sh:14` runs with `$H/depot-stock`, that is `experiments/ttfx/depot-stock`, which does not exist.
  - S's first measured run therefore either precompiles CairoMakie and the solvers inside its `load` step, or picks up whatever stock caches `~/.julia` holds. `logs/precompile-S.log` ("precompile s=1.2") says only that the *ndport* depot was ready.
- `JULIA_PKG_PRECOMPILE_AUTO=0` (`run.sh:9`) does not stop `using` from compiling a missing or stale cache. Only Pkg's automatic step is off.
- `timeout 1800` (`run.sh:25`) lets such a run go on for half an hour. That is the "hours" the user ruled out, hidden in one cell.
- The patched build is changing today: `sys.so` was rebuilt at 11:58, and W-57 is waiting for its build. Every rebuild makes every package image of U, C and D stale. The next run then precompiles inside `load`.
- The log header records the source checkout (`git -C julia-1.13 log -1`, `run.sh:24`), not the binary that ran. The Python log shows `julia-1.13=252edca933` (`logs/try/py-1.log:1`), a commit made eight minutes before the last `sys.so` was written.
- `summarize.py` flags nothing of this.
- The ndport harness already guards against it: "refuses to run where a dependency is not precompiled; marks a run that precompiled INVALID" (`ndport/README.md:24`). The ttfx harness lost that guard.

**Fix.**
- Use one depot path per setting in both scripts.
- Run Julia with `--compiled-modules=existing --pkgimages=existing`. A missing cache then shows as a slow, interpreted load instead of a hidden compile. Also set `JULIA_DEBUG=loading` in a separate check run, or grep for "Precompiling" and mark the run INVALID.
- Lower the measured run's timeout to about 300 s.
- In the session, print `Base.GIT_VERSION_INFO.commit_short`, `Base.julia_cmd()`, and the versions or tree hashes of TraitWorld and the clones. Print the same for Python: `sys.version`, numpy, scipy and matplotlib. Plan §4 says "versions in the log", but the log has none.
- Freeze one build for phases 1–3. Rebuild only between phases, and precompile everything again, alone.

### B2. The scripts favour D's cached keys over S's (blocking)

**Evidence.**
- **S, U, A and C** (`workload.jl`):
  - Lorenz's parameters are a `Tuple` (`:30`). Van der Pol's are a `Tuple{Float64}` (`:50`). `saveat` is a `StepRangeLen` (`:28`).
  - OrdinaryDiffEq's workload solves Lorenz with no parameters and with `Float64[]` (`ndport/pkgs/OrdinaryDiffEq.jl/lib/OrdinaryDiffEqTsit5/src/OrdinaryDiffEqTsit5.jl:48-49`).
  - `promote_f` puts the parameters' type into the wrapped function's signature (`DiffEqBase/src/solve.jl:1085-1086`, `sig_p`). So in S, the solver for Lorenz and for Van der Pol is likely compiled in the session. That comes from the script's choice of argument types, not from the library's design.
- **D** (`workload_d.jl`):
  - It passes `Vector` parameters, `nothing`, and `collect`ed `saveat` (`:30`, `:32-33`).
  - Those are exactly the keys in TDE's workload (`TraitDifferentialEquations/src/TraitDifferentialEquations.jl:148-160`, including "no parameters (p::Nothing)").
- Phase 1's decision rule then reads "D near Python, S far → the question is scale" (plan §5, phase 1). That would be an artefact of the scripts.

**Fix.**
- Use the same argument shapes in every language and setting: `Vector{Float64}` parameters and `Vector{Float64}` saving times.
- Add one **perturbed** variant per setting: `Tuple` parameters and a range for `saveat`, everything else equal. It is one more session per setting, and it measures what the user's goal is about: whether the cached core survives the user's ordinary choices.
- Report the difference between the two variants as "keyed on the call's shape" (see M5).

### M1. Phase 1's comparison of D with S does not isolate scale (major)

**Evidence.**
- D differs from S in at least five ways at once:
  - library size;
  - features: TraitMakie has no layout engine, text shaping, log axis or Makie attribute pipeline (`TraitMakie/README.md`, "Scope");
  - output: two PNGs instead of one figure with two axes (`workload_d.jl:43-46`);
  - method: Rodas5 against Rodas5P;
  - traits against plain code.
- The plan reads a D–S gap as "scale" (§5, phase 1).
- A plain control already exists: PlainODE and PlainPlots, the demonstrators' baselines. They have every feature of the trait forms (`TraitDifferentialEquations/README.md:49`; `TraitMakie/README.md`, "baselines/PlainPlots").

**Fix.**
- Add a setting **Dp**: the same workload on PlainODE and PlainPlots. It takes minutes.
  - D ≈ Dp: small libraries are fast whatever the design, and D says nothing about traits.
  - D < Dp on the second model: that is the traits' contribution.
- Replace the phase-1 rule with three questions:
  - **features:** S against Dp;
  - **design:** D against Dp;
  - **facts mode:** U against A.

### M2. Load time is the likeliest premise-killer, and the plan meets it last (major)

**Evidence.** The record already shows a load cost close to the whole 3 s target:
- CairoMakie loads in 1.9 s plain and 4.9 s under `all`, "not diagnosed" (`writeup/design/evidence.md:173`);
- the SciML core wrapped by facts adds about 2 s to the loads (`ndport/README.md:111-118`: "Loads ND" 6.11 s at S0, 8.19–8.64 s from S2);
- each of `using TraitDifferentialEquations` and `using TraitMakie` takes 0.52 s (`evidence.md:95`, `:116`), against Python's whole load of 0.46 s.

The plan raises load time only in phase 3, and only "if load dominates what remains".

The reference names load-time work that grows with the size of the world:
- facts and fold values are validated per CodeInstance at load (`reference/facts.md`, §11, "When it stays valid");
- the image hook runs once per image over its external methods (`reference/compiler.md` §5.1);
- TraitWorld's callback runs after every package load: it registers candidates and reads `__tw_checked__` (`reference/lowering.md` §16);
- keep-compiled puts more external code into each image (`reference/compiler.md` §2.9). That is more to validate at each load.

Caching more code across sessions grows exactly these costs.

**Fix.**
- **Phase 1:** run `@time_imports` in the same session. It is cheap and shows each package's load time and its `__init__`. Write a **load budget** into §3. For a 3 s session with Python's split, load should be about 1–1.2 s.
- **Phase 2:** take one sampling profile of the load step per setting, with C frames. Split it into:
  - file reading and `dlopen`;
  - deserialisation;
  - method insertion;
  - edge and fact validation;
  - TraitWorld's hooks and callbacks;
  - `__init__`.
- **Diagnose `all`'s 4.9 s CairoMakie load in phase 2,** not phase 3. The intended core is facts-compiled, so its images load as facts images.

### M3. Strict mode is missing from the plan (major)

**Evidence.**
- Strict mode is the design's guarantee that trait code is never invalidated (`reference/traits.md` §10.3). That is the property that makes caching across sessions robust.
- Its prototype reads backedges for every image's methods before activation (`reference/facts.md` §10.2, "How it finds the facts").
- E-165 measured the cost: loading Graphs and NetworkDynamics took 2.9 s with strict mode off and 7.9–8.1 s with it on (`ndport/README.md:136`).
- `run.sh` sets no `JULIA_TW_STRICT`. The plan does not name strict mode for any setting. CLAUDE.md rule 5 requires every number to say whether strict mode was on or off.

**Fix.**
- State strict mode per setting.
- Run C, and later the phase-6 prototype, once with strict mode on and once with it off.
- Make strict mode's load cost an explicit input to phase 4. The intended design checks at image validation instead of walking backedges (`facts.md` §10.3). The note should say whether that design is required for the target.

### M4. The attribution tools miss what the plan needs to attribute (major)

**Evidence.**
- `Base.cumulative_compile_time_ns` (`workload.jl:4-7`) counts the compiler's own timing. It does not count:
  - load-time work: method insertion, edge and fact validation, TraitWorld's hooks;
  - possibly, inference that Julia code drives through reflection or a custom interpreter. TraitWorld's checks run that way (`reference/lowering.md` §2, "the keep analysis and the result-type checks"; §16).

  In facts settings, such checks would then show as run time. Verify this once with a probe.
- `--trace-compile` with timing (phase 2) prints the roots of compilation, with their callees' time folded in. It does not print "each method instance compiled" (plan §5, phase 2), nor the owner. "Grouped by package and owner" cannot come from it.
- The plan does not name invalidation as a cause to measure. The ndport harness counts the CodeInstances lost to a load (the `G` line, `ndport/README.md:27`).

**Fix.** In phase 2, use four tools:
- the sampling profile of M2, per step;
- `ndport/scripts/diag.jl` for new CodeInstances by owner and module, as E-168's registry row already promises;
- `JULIA_DEBUG=loading` for rejected images;
- the invalidation log, or the `G` line, around each `using`.

Then classify each piece of compilation in the session as one of:
- (a) not in any image;
- (b) in an image that was rejected;
- (c) in an image but invalidated by a later load;
- (d) cached under the other owner;
- (e) keyed on a type from `Main`, the user's script;
- (f) keyed on the shape of the call (M5).

Only (a)–(d) are "caching failures". Phase 3 can remove only (a), and (c) where the load order allows.

### M5. Phase 2 sorts compilation into two kinds; there is a third (major)

**Evidence.** Phase 2 has two classes: "repeats in every session" and "keyed on the user's model or data". It misses compilation keyed on the **call's shape**:
- keyword `NamedTuple` types: OrdinaryDiffEq's `solve` specialises on its keywords;
- container types such as `saveat`'s;
- the parameters' type (B2);
- Makie's attribute values, such as `xscale = log10`.

This class is cacheable in principle. It is a design question for the core's entry: normalise at the boundary (TDE's `@nospecializeinfer` front end, `TraitDifferentialEquations/README.md:19`), or key on it. Phase 4 needs it.

**Fix.** Add the class to phase 2's "Decides" and to phase 4's list. B2's perturbed variant measures it.

### M6. The workload omits the load order where the design is distinctive (major)

**Evidence.**
- The script loads everything first (`workload.jl:9`), Julia's best case.
- Python's imports do not depend on order. Julia's do: with plotting loaded after the first simulation, upstream recompiled 4.7 s on the next pass, the facts-compiled core nothing (`ndport/README.md:122`; `writeup/design/evidence.md:45`).
- The user's goal is a session that "is not slow". A user who solves first and plots later is the common case.

**Fix.** Add an **order-B** variant per setting: `using CairoMakie` after `solve1`. It is one session each, and it shows the facts mode's protection where users meet it.

### M7. Scale is first tested in phase 6, and phase 6's Makie slice is not at scale (major)

**Evidence.**
- Phases 4 and 5 are design notes with fresh-eye reviews. The first measurement of a trait core larger than the demonstrators comes in phase 6.
- Phase 6's Makie slice ("`Figure`, `Axis`, `lines!`, a PNG") is TraitMakie's size again. It would not test "at scale" unless it carries what makes Makie slow. Phase 2 has to name that first: probably layout, text and ticks, and the attribute pipeline.

**Fix.**
- **Add a scale probe to phase 2 or 3.** It takes minutes. Generate a trait module with N implementations and M bounded functions, at N, M = 10× and 100× TDE's, with a workload. Precompile it, then measure the image size, `using` with strict mode off and on, and one first call at a cached key and one at a new key. If load grows faster than linearly in the size of the image, the premise fails before any porting.
- **Phase 6's Makie slice must include** the components that phase 2 finds expensive in S. If those are layout and text, the slice includes them, or the plan says why the trait design does not reach them.

### M8. Setting C does not isolate what the plan and the registry say it does (major)

**Evidence.**
- **It is not a trait core.** C is P6's trees: "upstream's code … compiled by facts as trait modules: no trait code (neither interop nor idiomatic)" (`ndport/README.md:107`; also `:127` for IP).
  - E-168's registry row says "Measures interop (C)" (`writeup/record/experiments.md:253`). That contradicts the ndport README.
  - Phase 1 groups C with S and U as "far". C's numbers would say nothing about an idiomatic trait core.
- **Its Makie is not the registry's.** `env_core` takes Makie, ComputePipeline and Observables from the ndport clones (`experiments/ttfx/env_core/Project.toml`, `[sources]`). The plan says "upstream CairoMakie" (§4). The code is probably equal to the release. It is still a separate build, in a depot shared with ndport's committed experiments (`ndport/depot-p6`).
- **Its TraitWorld is untested with these trees.** C uses TraitWorld main (bbfc130). P6 and the merge were measured on 3bebf13 and c655dde (`ndport/README.md:107`, `:127`). The forks already fail to precompile on bbfc130 (`evidence.md`, the forks' note).
- **A known cost sits in its solves.** The Rodas5P steady state of facts-compiled SciML is 267.7 ms on the current build (open issue 66), until W-57 is built.
- Strict mode is unspecified (M3).

**Fix.**
- State C's question narrowly: "Does compiling upstream SciML by facts change the solver steps' first use and load?"
- Fix the E-168 row's "interop" wording.
- Pin TraitWorld to the port's revision, or record that C runs on bbfc130 for the first time.
- Use a depot of C's own.
- Run C after W-57's build, or mark its solve steps as carrying open issue 66.

### M9. Single cold runs will measure caches, not the design (major)

**Evidence.**
- The plan runs "one fresh session per setting first" (§5).
- The first session after a precompile or a rebuild reads hundreds of MB of images from disk, under `ionice -c3` (`run.sh:25`). On a shared machine that is the idle I/O class, so other jobs' I/O comes first.
- Other per-run caches start cold too:
  - S's first depot is new, so Makie's scratch spaces are created in the measured run;
  - fontconfig's cache;
  - Python's font cache, which the plan does warm ("warm (the font cache built)", §3).
- The target (§3) rests on one Python run.

**Fix.**
- One discarded warm-up session per setting, Python's included.
- Then two measured sessions, three where a decision hangs on a difference.
- Report the spread, and keep the warm-up's log as the "cold" figure.

### M10. Phase 3's ceiling needs a second point, and cannot replay the user's code (major)

**Evidence.**
- Statements that name `Main`'s functions (`lorenz!`, the broadcast closures) cannot go into a package's workload. Defined inside the package, they become different types with different keys.
- A package-image workload also leaves the load machinery in place: insertion, validation and hooks.

**Fix.**
- Report phase 3 in two parts: what the workload removes, and what stays because it is keyed on `Main` (class (e) of M4). That remainder is the floor the trait design has to address.
- Optionally, one system-image ceiling: PackageCompiler, or `experiments/sysimage`, built alone under the memory guard. It is minutes of building, not hours. The difference between the package-image ceiling and the system-image ceiling is the cost of loading machinery. That decides phase 3's "load or compile" question directly.

### m1. Digests sit inside the timed windows (minor)

**Evidence.** `digest` runs between `mark("solve1")` and `mark("plot1")` (`workload.jl:47`), and after `mark("model2")` but before `mark("again")` (`:53`). The same holds in `workload_d.jl:50`, `:56`. In S, `sol(t)` compiles the interpolation path, and that is charged to "first plot". The ndport harness keeps digests outside the windows (`ndport/README.md:23`).

**Fix.** Print the digests after the last mark, or put marks around them.

### m2. The plotting work is not matched (minor)

**Evidence.**
- matplotlib writes 800×600 pixels (`workload.py:30`, `:34`).
- CairoMakie's default `px_per_unit` for PNGs is above 1 in recent versions. The script does not set it (`workload.jl:43`), so S may write four times the pixels. Check the files.
- D writes two PNGs with linear axes (`workload_d.jl:43-46`); Python writes one figure with a log axis.

**Fix.**
- Pass `px_per_unit = 1`.
- Log each PNG's size in pixels and bytes.
- State D's differences in the results table.

### m3. Python's steps are not comparable one by one (minor)

**Evidence.** Python defers work to first use. matplotlib's backend and font manager load inside "first plot" (0.51 s), not inside "load" (0.46 s). Julia does that work at `using`.

**Fix.** Compare with Python on the whole session and on "load plus first simulation plus first plot". Compare step by step only between Julia settings.

### m4. The digests' tolerance is not stated (minor)

**Evidence.**
- Robertson's second component lies between 1e-5 and 1e-8 (`logs/try/py-1.log`, the `D robertson` line). With `abstol = 1e-8` it is barely resolved.
- RK45 against Tsit5, Radau against Rodas5P (S) or Rodas5 (D) will differ there by much more than in the other components.

**Fix.** Compare per component, with a relative tolerance and an absolute floor tied to `abstol`. Write the rule into the plan §2.

### m5. Registry and plan disagree, and later runs have no rows (minor)

**Evidence.**
- E-168's row (`writeup/record/experiments.md:253`) says "Three sessions per setting". It omits D, and gives phase 2's attribution in another form. The plan §5 says "one fresh session per setting first".
- E-169 and E-170 have no rows. CLAUDE.md requires "The row comes before the run".

**Fix.** Align E-168's row with the plan as revised. Register E-169 and E-170, each with its question and the result that would change the plan, before they run.

### m6. D stacks two environments that were precompiled apart (minor)

**Evidence.**
- `run.sh:18` sets `JULIA_LOAD_PATH` to TDE's environment, then TraitMakie's.
- `precompile.sh:15` precompiles each environment alone.
- If the two manifests resolve a shared dependency differently, such as Cairo's JLLs or ForwardDiff, the stacked session can reject an image, or load another version.

**Fix.** Give D one environment with both packages, as `env_up` does for S. Precompile it once.

### m7. The target needs predictions, and the setup needs its own time budget (minor)

**Evidence.**
- §3 gives one number, 3 s, and a claim: "nothing in the trait design forces it above Python's". Neither says per step what would refute the design.
- §5 promises minutes per experiment. Setting A first needs the facts system image rebuilt (a full build, alone, under the memory guard) and a precompile under `all` (354 s in E-151, `ndport/README.md:45`). The other settings' precompiles took 175–370 s in E-151 and E-165.

**Fix.**
- Before phase 1, write the design's prediction per step:
  - load at most the budget of M2;
  - the second model at most 0.3 s;
  - the order-B penalty about 0 under facts.
  The phases then confirm or refute named numbers.
- List the setup costs separately. Schedule the facts image build alone.

## Question by question

1. **Do the six phases reach the goal?** Yes in order, but phase 1 would mislead without B1 and B2. Missing:
   - the plain control (M1);
   - the load budget and the profile of loading (M2);
   - strict mode (M3);
   - the load-order variant (M6);
   - an early scale probe (M7).

   Redundant as framed: C, unless it is narrowed (M8).
2. **Minutes, and deciding what they claim?** The runs are minutes, once hidden precompiles are excluded (B1) and setup is counted apart (m7). The pitfalls:
   - compile time hiding in load (B1, M2, M4);
   - invalidation and rejected images (M4);
   - the facts mode's checks counted as run time (M4);
   - garbage collection after big loads: logged, keep it;
   - the file-system and font caches (M9);
   - two cores: fair to both, keep it.
3. **Like for like?** Close, after fixes:
   - matched argument shapes (B2);
   - matched pixels and outputs (m2);
   - digests outside the windows (m1);
   - a tolerance rule (m4);
   - totals rather than steps against Python (m3).

   The target of twice Python's is a reasonable first milestone, if it comes with a load budget and per-step predictions (M2, m7).
4. **Do the settings isolate their claims?**
   - C does not: no trait code, cloned Makie, an untested TraitWorld, open issue 66 (M8).
   - D does not separate small size from traits without Dp (M1).
5. **Is the premise sound?** It holds for compilation keyed on the core's own types. It is threatened by:
   - load time that grows with what the images keep, and the facts images' slower load (M2);
   - strict mode's load cost (M3);
   - per-session work: the session stamp makes saved flags stale; the untyped tables are rebuilt; `Callable` pointers are made again at the first call (`reference/lowering.md` §16, §9.3, §12);
   - code keyed on `Main` and on call shapes (M5, M10).

   M2, M3 and M7 detect these within the first two phases.
6. **Contradictions with the references or the record:**
   - C's "interop" label against the ndport README (M8);
   - "upstream CairoMakie" against `env_core`'s `[sources]` (M8);
   - the plan's phase-4 list lacks the per-session costs the references state (lowering §9.3, §12, §16; facts §11). This is an omission, not a contradiction.

   The plan's description of TDE's keys (model `Dynamic`, the solver compiled per state and parameter type) agrees with traits §6.7 and lowering §12.
