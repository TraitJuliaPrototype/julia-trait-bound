## Findings, ranked by damage to the thesis

### A. Claims that are wrong or overclaimed

**A1. Theme 2 is wrong as stated: the two "optimizer habits" are not facts-specific, and they are not "harmless in plain Julia" (verified).**
The note (`5-performance.md` theme 2, and design.md §6 row "Inlining under facts") says the compilesig widening and the no-inlining-within-a-cycle habit are harmless in plain Julia because "plain Julia dispatches at run time anyway", and the two commits gate the fixes on `facts_mode` (`inlining.jl:789`, `typeinfer.jl:279-286`). I built the plain-Julia analogue: an `@inline` varargs wrapper (`wrap(f, r, args...) = f(r, args...)`) on the path of a recursion through an abstract type with two subtypes (the "closed by accident" case), compiled by the runtime path as a program would (`probe3.jl`):

| | plain mode, patched binary | stock 1.13.2 |
|---|---|---|
| recursion through the wrapper, 10^5 children | 22.5 ms, 16.8 MB allocated | 21.1 ms, 16.8 MB |
| the same recursion without the wrapper | 0.40 ms, 0 bytes | 0.41 ms, 0 bytes |
| specializations of `wrap` created | `(…, A, Float64, Vararg{Any})`, `(…, G, Float64, Vararg{Any})` | the same |

That is a 56× slowdown and the same boxing, in plain Julia, from exactly the two habits (the wrapper is a cycle member, so it is not inlined, so it is invoked at the compileable signature with a `Vararg{Any}` tail). Plain code rarely shows it only because plain recursions through abstract types usually have no wrapper in the cycle. TraitWorld's dispatch path puts four varargs wrappers (`Dynamic` operation, `intersect(::TObj)`, `opcall`, `_dispatch`; `core.jl:619-640`) on every `Dynamic` recursion, so it hits the habit every time. The lesson in the note ("each place where Julia relies on 'this will be dispatched dynamically anyway' needs a facts version") is therefore not supported by the evidence; the supported lesson is: Julia's cycle handling penalizes wrappers inside inference cycles in any mode, and the runtime-as-methods design makes that the common case for trait code.

Consequences. (i) Both fixes are general Julia improvements, and gating them on `facts_mode` "so that plain baselines stay stock" is a measurement convenience, not a design principle (decisions.md states this correctly for the cycle one: "it would help plain recursions too"; design.md §6 does not). (ii) The rtopen comparison is still fair as reported, because the plain raytracer has no wrapper in its cycle; but any future "trait vs plain" comparison of code with wrappers in both would be unfair in the trait form's favour. (iii) Upstream value: see D1.

Also a diagnostic caveat found on the way (`probe2.jl` vs `probe3.jl`): `code_typed` run after the code has executed shows the wrapper inlined and a direct `invoke` of `visit(G, Float64, Int)`, because by then the callee is cached; it does not show what the runtime compiled in the cycle. IR-based statements in the log such as "three calls per Group visit" are optimistic unless taken from the CodeInstance the runtime actually compiled (or confirmed by allocation counts, as the raytrace diagnosis itself was).

**A2. The control section's arithmetic is wrong and its attribution is undiagnosed (verified against `control-all.log`).**
The note says "The 270 ms left after the loads under `all` is the same pirate-following as TraitReport's" (992 − 722). But the log gives upstream CSV + DataFrames under `all`: "work: first 721.6 ms, again 0.8 ms; after the loads 991.7 ms". The cost the loads impose is 992 − 0.8 ≈ 990 ms, not 270 ms, with only "2 of 3,340" CodeInstances lost among the counted packages. `lost.jl` counts only the roots CSV, DataFrames, Tables, Parsers, InlineStrings, PooledArrays, WeakRefStrings, SentinelArrays; under `all` the system image compiles Base and the stdlibs by facts too (`experiments/factscompiler/scripts/build_facts_sysimage.sh`), and Base CodeInstances compiled by facts during the work (owner `nothing`, Base's method table) are outside the count. So 990 ms of recompilation is unaccounted for by the log; "the same pirate-following" is a hypothesis, not a diagnosis. The plain row is also understated: 4,009 − 0.6 ≈ 4.0 s. The `all` result is still the strongest evidence of the phase for step 3 (570 → 2 lost; 4.0 s → 1.0 s after loads; 3.6 s → 0.7 s first work on unmodified upstream packages), which makes getting its numbers right worth the effort. Also: PlainTables' first work doubled under `all` (133.0 vs 70.5 ms), not mentioned.
Recommendation: rerun `lost.jl` with the lost count over every module (Base included) and print, for each lost CodeInstance, the method that won at the invalidated fact (`jl_debug_method_invalidation` or the backedge walk `strict.jl` already does); state the 990 ms; update design.md §8, which still lists "The control that separates the facts mode from traits" under "Not shown".

**A3. Theme 4's "the one load-dependent cost left" is overclaimed (verified against `final-rows.log`).**
Load-dependent residues remain outside TraitReport: TDE row 1 (first Tsit5 solve of a plain function) 27.8 ms with loads before vs 10.0 ms without; TDE row 4 "a new callback closure" 170.7 ms with loads after vs 12.4 ms without (one run; 24.0 in the before order); TraitMakie "a new data type: first PNG" 160.6 ms (after) vs 107.3 (none), "recolor to a vector" 231.1 ms (after) vs 102.0 (none) and 83.8 (before). The session log's "other rows as without loads" does not hold for the final run. These are small, but the theme claims there is exactly one such cost and that it is piracy; nothing here was diagnosed. The TraitReport comparison with session 27 is also not like for like: session 27's "66–80 ms in every order" is form (t) (TraitCSV/TraitTables/TraitMakie; `TraitReport/README.md` row 7), while the phase measured forms (a′) and (b) only (`loads.sh` default `FORMS="Plain Trait"`, `report_loads.jl`). Form (t) was not measured under loads in this phase, so "the same regression" and the 620 → 338 ms "before/after" for TraitReport are form (b) numbers compared against a form (t) history.
Recommendation: list the residues as residues; run `loads.sh` with `FORMS="Tables PlainTables"` for the session-27 comparison; diagnose row 4 after loads (one run first).

**A4. A clean-case regression is omitted from the results table (verified: `makie-rows.log` vs `final-rows.log`).**
TraitMakie "a new data type: @implement (forwarding)" without loads was 36.0–36.4 ms before the phase and is 76.7–96.7 ms after; its "first PNG" was 40.4–40.5 ms and is 88.5–160.6 ms. The table's columns ("Before the phase" = with loads, "After", "Baseline: without loads") never show the clean case before the phase, so a 2–4× regression in the common case is invisible. TDE's clean `@implement` improved (242 → 142 ms) but its row 1 is 10 ms against §8's 6.4–8.0 ms. The likely cause is theme 1's own trade: `@machinery` turned the checks into facts code whose type-unstable paths now run through run-time sites into facts copies of Base methods, compiled in the session unless an image holds them (the log records the clean `@implement` going 0.24 → 0.38–0.41 s at the `@machinery` step before the compiler-plain fix recovered part of it).
Recommendation: add a "before the phase, no loads" column; count CodeInstances by owner created during a clean forwarding `@implement`; give TraitWorld's image a workload for the machinery's facts code.

### B. Soundness and design

**B1. Facts code that calls the compiler directly now holds edges to plain CodeInstances, whose validity is plain Julia's (reasoning from code; a documented-nowhere hole).**
c4f7e76a2f makes a facts frame's call to a Compiler method leave to a plain inference and name that CodeInstance with an edge (`facts.jl:69-90`: `leaves_to` → `plain_interp`, `facts_edge` → `return_cached_result`). A plain CodeInstance is inferred under plain rules at the latest world: any definition that changes dispatch at one of its abstract calls invalidates it, and the backedge invalidates the facts caller. So for facts code that calls the compiler directly, the guarantee "invalidated only by stakeholders or pirates" does not hold; it holds for the compiler's validity, which is plain Julia's. This is exactly the class of event that caused the 3.7 s regression (compiler code invalidated by loads), now with a smaller surface. Direct calls from facts frames exist: `checks.jl:97-135` and `defcheck.jl:236-258` (`_CC.argextype`, `_CC.sptypes_from_meth_instance`, `_CC.widenconst`, reached from `@machinery worker_problems`), `concrete.jl:78,340,423,475`, `compiler.jl:57,63` (`CC.NativeInterpreter`, `CC.cached_return_type`), `core.jl:320,387` (`CC.register_dynamic_candidate!`), `trait.jl:314` (`CC.dynamic_call`, see below). Calls through Base reflection are safe: `invoke_in_typeinf_world` is a `ccall` with no method edge (`reflection.jl:290-312`). The practical risk is low (these are concrete-signature CodeInstances of small compiler functions), but 624f742's message claims `@machinery` code is protected "as it protects trait code", and design.md §6's row "The compiler stays plain" does not state the exception.
Recommendation: state the exception in design.md §6 and in `@machinery`'s docstring; where cheap, make the machinery's compiler calls run-time sites (`Base.inferencebarrier`) or route them through `invoke_in_typeinf_world`, so that no facts CodeInstance has a plain edge.

**B1′. "Never by facts" catches `dynamic_call`, a user-facing primitive (verified: `jl_method_is_plain(dynamic_call) == 1`, `probe.jl`).**
`dynamic_call` lives in `Compiler/src/facts.jl:367`, so the module flag marks it plain. Inferred call sites are safe because `abstract_call_known` intercepts `f === dynamic_call` before any method lookup (`abstractinterpretation.jl:2805`) and the inliner rewrites the statement (`inlining.jl:1301-1307`). Any path that reaches the generic method itself (the interpreter, unoptimized code, reflection on it, an `invoke`) now runs `f(x, args...)::RT` compiled by plain rules with plain speculation over the abstract `x`, and from facts code dispatch runs the plain owner (`gf.c`, `facts_callee_owner`). Not a measured problem; a design wart that the flag's granularity created.
Recommendation: give `dynamic_call` an explicit per-method mode (`Expr(:meta, :facts, 1)`) or move it out of Compiler; add an assertion test that the generic method is never dispatched in optimized facts code.

**B2. da4726c5cc trades `@nospecialize`/`max_varargs` discipline for the fact signature, unmeasured (reasoning; the gap verified).**
Under facts, a non-inlined call is invoked at the exact dispatch tuple (`inlining.jl:786-789`), so a method whose author limited codegen specialization (`@nospecialize`, `max_varargs`) is compiled once per concrete signature when called from facts code at a site the inliner does not inline. In trait packages and in `all` this includes Base methods such as `error`, `print`, `string`, `show`. The number of specializations and the image sizes were not measured; design.md §8 already lists "the volume of the explosion" as unmeasured, and this change feeds it. The condition is also inconsistent with the design's own fact definition: `is_fact_sig(Tuple{typeof(+), Vararg{Int}}) == true` but `isdispatchtuple(...) == false` (`probe.jl`), so concrete-`Vararg` facts and closure-at-kinds facts are still widened. Soundness is fine (the edge is to the exact CodeInstance that inference already named; upstream's extra `method.sig` invoke edge is dropped, which is more precise).
Recommendation: the principled, general fix is "prefer an exact specialization that is being compiled anyway": if the exact `mi` has a CodeInstance (in `opt_cache` as a cycle member, or cached), invoke it; otherwise keep the compileable signature. That removes the cycle pathology in plain mode too (A1) without defeating `@nospecialize` elsewhere. Measure specialization counts in the TraitWorld images and under `all` before and after.

**B3. The cycle-inlining change (4102b7a7a7) looks sound; its coverage is incidental (reasoning, with one acceptance check).**
Edges: a member inlined into a later-optimized member adds an edge to the member's CodeInstance (`get_cached_result` → `InferredResult(…, state.opt_cache[mi])`, `inlining.jl:827-830`; `add_inlining_edge!` in `resolve_todo`), and `finish!` stores every member's backedges (`typeinfer.jl:116-118`), so invalidation of a deep member reaches the ones that inlined it transitively. The IR is copied before inlining (`preserve_local_sources = true` in the cached-result branch, `retrieve_ir_for_inlining(mi, ::OptimizationState, true)`), effects are the cycle-merged ones, worlds the cycle's. The `:invoke` resolver returns `nothing` for a cycle member (conservative). G1.15 ("a cycle's callee redefined deep inside") passes on this build and exercises the path, but no acceptance check was written for the new behaviour (a cycle through `Dynamic` whose deepest member is redefined, under facts, result and recompile checked). Compile-time growth is linear in the chain and bounded by the cost model; not measured.
Recommendation: add that check; measure inference time on the raytrace cycle and on BaseBenchmarks with the gate removed (see D1).

**B4. `worker_problems` by facts reflection (93c8a08) weakens the static check's coverage (reasoning from `checks.jl:85-135`).**
The check inspects calls whose argument types are trait-object types (`_hastobj(ats[k])`). Under facts inference a call at a non-fact signature has result `Any`, so a trait object that flows out of a run-time site is `Any` downstream and every later statement on it is skipped (`any(k -> _hastobj(ats[k]), …) || continue`). The plain-rule `_CheckOwner` inference resolved more calls and saw more. The run-time guards (`_noescape` at entries, `_tgetprop`/`_tsetprop!` for undeclared fields, `core.jl:505-511, 331-333`) still hold, so this is a loss of early diagnostics, not of safety; but "the code that runs" in the commit message is only half the story, and `_CheckOwner`'s docstring ("none of their results reaches the code that runs") now describes the definition checks only. The cache sharing itself is sound: `code_typed_by_type(sig; optimize=false)` leaves the entry frame uncached (`:no`) and caches callees as the runtime would, through `leaves_to` to the `:facts` owner.
Recommendation: say so in the docstring; consider taking the first-call check from the certificate's walk (`verify.jl`), which already distinguishes run-time sites.

**B5. In `all` mode the compiler is not "plain whoever calls it" (reasoning).**
`leaves_to` checks `is_plain_method` only for `interp.owner === FACTS_OWNER` (`facts.jl:71-75`); the `all` interpreter has owner `nothing` with `facts = true`, so compiler methods reached inside a user frame are compiled by facts there; only the top-level entry is protected (`typeinf_ext_toplevel`, `typeinfer.jl:1657-1658`, via `is_compiler_code`). Design.md §6's row is unconditional. Minor, since the compiler's own CodeInstances come from the image in the typeinf world; fix by testing `interp.facts` rather than the owner.

**B6. Cross-owner re-entry is handled, not deadlocked (verified in `engine.cpp:73-94`).** c4f7e76a2f adds the facts → plain direction, so facts → compiler → facts recursion is now possible (the compiler printing a trait type, say). `jl_engine_reserve` detects a same-thread wait and returns an unreserved CodeInstance; no deadlock, a pre-existing property of (B).

### C. Methodology and unsupported numbers

**C1. "forks: first `String15` read 1.6 s → 0.046 s" mixes two harnesses, and the second number was unlogged.** The 1.56–1.67 s is the session harness's `3_read_show` step (read plus REPL display, after twenty earlier steps; `forks/scripts/session.jl:39-41`); the 0.046 s is `s15.jl` (a script: imports, one default read, the `String15` read alone). `forks-s15.log` (08:26) predates the extension commit (08:35) and still shows 1.55–1.59 s; the session harness was not rerun after either fix. I reran `s15.jl`: 0.041 s read, 0.004 s show, 14 new CodeInstances (10 Base, 2 CSV, 2 Core, all plain), so the claim holds in that harness. The two fixes' contributions (extension vs reflection by facts) were never separated; the extension alone would explain most of it.
**C2. Load cost of the platform is omitted.** In every `report loads` row the trait form's `using` is 1.09–1.18 s against 0.91–0.99 s for the plain form (+0.18–0.20 s), and the forks' imports are 1.70–2.09 s against upstream's 1.33–1.42 s. The summary headlines work times (41 vs 237 ms) and leaves the load difference out; for a fresh-process user the two nearly cancel in the no-loads case.
**C3. Single runs.** The final run is one process per order (`final-rows.log`); the earlier runs were two. Variance is visible: forks run 2 "read 1.409" against 0.075 in the other runs (the summary's median hides it); `using TraitDifferentialEquations 7.28 s` in a run whose first line reports a 208 s precompile. Fine for a progress log, not for the results table without saying "n = 1".
**C4. rtopen's "plain open" baseline is a `max_methods = 3` artifact.** `Raytracer4` has four `Scene` subtypes, one over plain inference's default split limit; `Base.Experimental.@max_methods 4` on `intersect` would let plain Julia split too. The trait split also caps at four candidates (`MAX_FACT_SPLITS = 4`); with five conformances the fifth takes the dynamic fallback. "2× faster than plain once the set is open" is true at exactly four types and should say so.
**C5. Verified claims.** `_return_type(::NativeInterpreter, ::DataType)` is compiled at the first unfoldable run-time `return_type` on stock 1.13.2: 74.75 ms (`probe4.jl`), 0.19 ms on the patched build, as claimed (note: a foldable `return_type(cos, Tuple{Int})` at top level measures nothing, 0.01 ms on both). `return_type(cos, Tuple{Int})` after e4db37bb48 compiles nothing (consistent). The pre-phase numbers (TDE 2.0/2.1 s, TraitMakie 5.5/2.1 s) are reproducible across two runs. Acceptance 19/19 on the final build (`acc.log`).
**C6. Not re-run:** Python; form (t) under loads; the session harness after the String15 fixes; the BaseBenchmarks row of §3.3, now stale for the current compiler (cycle inlining and compilesig under `all`).

### D. Principled or workaround; what goes upstream

**D1. Upstream as they are:** 40512f64c2 (verified gap in stock, small, no risk); bb82a82bbf (`reflection.jl:307-310`: runs an explicit `NativeInterpreter` in the typeinf world as the default one is; general and small, though upstream's `NativeInterpreter` has no `owner` field, so it is a one-line generalization there); e4db37bb48 is a fix of the phase's own bug. **Upstream after measurement:** 4102b7a7a7 with the gate removed (plain recursions lose 56× to the same habit, A1); the compileable-signature change in the general form of B2. Both are Julia improvements, not facts needs; the honest framing for the notes is "found by the facts build, worth having in stock".
**D2. Needed only because of the facts mode:** module flag 2 on Compiler and `leaves_to` both ways (c4f7e76a2f), `@machinery` (624f742), the checks' `NativeInterpreter(owner = _CheckOwner())` (f79727c), `worker_problems` by facts (93c8a08). All consistent with "every piece of code has an owner", with the caveats B1, B4, B5.
**D3. The three-package extension (forks 9d512a1) is a workaround, and theme 3 overstates what the design gives.** (i) The need is partly self-made: upstream CSV has InlineStrings as a hard dependency (its image carries the `String15` code; 0.19 s), the forks made it a weak dependency. (ii) A workload extension per package combination is combinatorial and hand-written; nothing in the design makes `CSVDataFramesInlineStringsExt` follow from a declaration. (iii) The design's own answer is §4.8 ("AOT follows from declared targets"): a conformance declared in `CSVInlineStringsExt` should compile the reader's declared workers for the key at precompile time, and DataFrames' kernels over a `Vector{String15}` column belong to a DataFrames image, not CSV's. The first `String15` read without the three-way extension, after 93c8a08, was never measured.
**D4. `@machinery` is principled but its cost is not stated.** Facts code is "load-proof but slow where it is type-unstable" (the note's own words); the machinery is type-unstable by nature (`@nospecialize` everywhere, `methods(f)`, string building), so its run-time sites compile facts copies of Base methods per session unless TraitWorld's image holds them. A4 is probably this. The principled completion is a precompile workload for the machinery under its new owner, and a count of what a clean `@implement` compiles by owner.

## Verdict on the four themes

- **Theme 1 (every piece of code has an owner): real, the phase's main lesson, and correctly placed as design rather than detail.** Two corrections. The compiler sitting in a frozen world is Julia's existing design (`jl_call_in_typeinf_world`); the mistake was running compiler code at the latest world through a custom interpreter and compiling compiler code by facts, and the fix restores stock behaviour. And the theme should carry its own costs: facts code that calls the compiler directly has plain edges (B1), and facts machinery pays for its type instability at run-time sites (A4, D4).
- **Theme 2 (the optimizer's heuristics assumed the dynamic case): wrong as stated** (A1). The habits cost plain Julia the same; the trait design's wrapper stack is what makes them bite every time. Reframe as "Julia's cycle handling versus wrappers in recursion cycles", and treat the fixes as upstream improvements.
- **Theme 3 (work an image could have held): the principle is right, the mechanism offered is a workaround** (D3). The three cases from the compiler (checks' cache, custom interpreter, `_return_type` entry) fit the theme; the extension does not fit the design's own AOT story.
- **Theme 4 (what loads still cost is piracy): the direction is supported, the statement is overclaimed and the control's attribution is undiagnosed** (A2, A3). SparseArrays' `vcat(::_DenseConcatGroup...)` winning at `vcat(::Int64, ::Vector{Int64})` is a plausible, well-known pirate and the new CodeInstances listed fit it; the 333–410 ms is the recompiled chain above that fact, not `_parse` alone. One consequence the note does not draw: in strict mode that stdlib method would be *refused* at StatsBase's or Distributions' load, which makes the case against strict mode as a default as much as for it, unless SparseArrays' concatenation piracy is fixed upstream (there is precedent for reducing it).

Overall: the phase fixed real regressions with mostly principled changes and produced the strongest step-3 evidence so far (the `all` control on unmodified upstream packages), but the write-up overclaims in three places (A1–A3), omits a clean-case regression (A4), and leaves one guarantee exception undocumented (B1).

## Most valuable next steps, in order

1. Diagnose the 990 ms after loads under `all` and the 338 ms under TraitReport: list every invalidated CodeInstance (all modules) with the winning method and the fact it won at. This either confirms theme 4 with evidence or finds a second mechanism; it also decides whether strict mode is livable with SparseArrays loaded.
2. Remove the `facts_mode` gate from the cycle inlining and recast the compileable-signature change as "prefer an existing exact specialization" (B2); measure BaseBenchmarks and the specialization counts, then open the two upstream PRs together with 40512f64c2 and bb82a82bbf.
3. Profile the clean forwarding `@implement` (TraitMakie 36 → 77–97 ms) by owner; add a workload for the machinery's facts code to TraitWorld's image; re-measure the TraitMakie and TDE rows with two runs per order and report the clean case before/after the phase.
4. Measure the first `String15` read without `CSVDataFramesInlineStringsExt` (reflection fix alone), then implement the §4.8 mechanism: a conformance's declaration compiles the declared workers for its key in the declaring extension's precompile.
5. Close the B1 hole in the machinery (run-time sites or `invoke_in_typeinf_world` for its direct compiler calls), give `dynamic_call` an explicit mode (B1′), and fix the `all`-mode check in `leaves_to` (B5); state the exception in design.md §6.
6. Add acceptance checks for the phase: a `Dynamic` recursion cycle whose deepest member is redefined (B3); a facts method's invoke keeps the exact signature and the plain baseline does not (so a future regression is caught); a `@machinery` method invalidated only by a stakeholder.
7. Run the like-for-like TraitReport rows (forms (t) and (pt) under loads), the session harness after the String15 fixes, and record the platform's load cost (+0.2 s) beside the work times.
