## Summary

The entry is the right fix and it works as the plan says for the concrete form: the runtime accepts it on the concrete path as a first declaration (probe A), the image keeps it, activation lists it, the sync rebuilds the records (probe 3), and the gate's case 5 flips (`recheck_form.jl`: `tri2 uncovered: ImplementError`, the other cases unchanged). The ambiguity report and strict mode cover the form once `X` is in the member's own entry list (probes E, F). No runtime change is needed for that.

The plan is wrong or silent on four things, two of them worth H:
- **The abstract form is not checked at all today.** `abstract type A <: X end; @implement X A; struct S2 <: A end`: the runtime calls the member hook only for an argument whose chain carries an entry (gf.c:7107, "a declared subtype, or no member at all"), so `S2` is never checked unless `X` happens to have a supertrait entry. Probe D: an incomplete `S2` raises `MethodError` at the operation, with no `_CHECKED` answer; with an entry at `A` it raises `ImplementError` at its first use. The plan's "(unchanged)" is false: the entry starts a check that has never run, which is right, is an unrecorded deviation of lowering §4 and traits §5.2/§5.9, and needs its own gate.
- **A stated instance that disagrees with the declared supertype at an input parameter is accepted as a dead entry**, today and under the plan (probe C, probe 1): `struct CB3 <: Conv{Int}` with `@implement Conv{Float64} CB3` is accepted, `CB3 <: Conv{Float64}` is false (the chain answers, subtype.c:2713), and `CB3` is a candidate of `Conv` with records at `To = Float64`. The plan's "refused as a second instance, which is right" holds only for a non-input parameter. The library must read the declared supertype's parameters.
- Strict mode cannot make the form's membership "not exist": in the order `@implement Y S` then `@implement X S`, the refused `X` entry leaves `S <: X` true and `f(S())` ambiguous (probe F). The reference and the message need the clause; C-78 is the principled fix for that order.
- The plan's sentence on inference edges is wrong in the main case (the chain answers, no edge: subtype.c:2178–2184, probe A), §3 cites a retired C-18 and the wrong section for the cost, the records list misses compiler §4.2 (whose "needs no entry" the plan contradicts), W-131 has no row, and the gates miss the candidates index (a benefit the plan does not name: probe A, `candidates(Shp) = []` today), the parameter cases, the abstract form, and the count gate counts nothing (TraitWorld's own source has no `struct … <: <trait>`).
