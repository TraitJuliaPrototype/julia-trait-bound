# Heterogeneous collections in the facts mode (fresh-eyes review, 2026-10-20)

Scope: `Vector{Any}`, `Vector{Union{…}}`, `Dict{K,Any}`, `Vector{AbstractFoo}` and `Vector{Dynamic{X}}` under the facts rule, in the product setting and under `all`. Sources read: `reference/facts.md`, `traits.md` §9–10, `lowering.md` §13, `compiler.md` §3–4, `design.md`, `state.md`, `design/evidence.md`, `design/performance.md`, the inline-caches plan and review, `julia-1.13/Compiler/src/facts.jl`, `src/gf.c` (the per-site cache), `TraitWorld/src/core.jl` (`Dynamic`), the DataFrames fork's storage, TraitMakie's fields, BaseBenchmarks' collection suite. Experiments: seven scripts in the session scratchpad (paths in §4), run on julia-1.13 at `julia-1.13/julia` (plain and the product setting) and `-J julia-1.13/usr/lib/julia/facts/sys.so` (`all`), one process at a time, `nice -n 19`. Timings are per element over 1,000-element collections, BenchmarkTools minima; treat differences under 10% as noise.

**The four conclusions.**
1. The tails are not a property of the test bed. In the product setting, a trait module that calls Base's `filter!` on a `Vector{Any}` pays 36.8 ns per element against 1.1 ns in plain code, and a `for (k, v) in d::Dict{String,Any}` loop pays 242 ns and 100 bytes per element against 2.2 ns. The mode rule (facts §6.2) compiles every Base method reached from trait code by facts, so the `all` numbers are what trait code sees. No reference says this.
2. The cost is not the dispatch. A run-time site costs the same dynamic dispatch as plain Julia (sum over `Vector{Any}` of `Int`: 17.3 ns under `all`, 16.9 plain). The tails are the lost inlining of callees whose methods are declared at `Any` (one method, plain inlines it) and the cascade of `Any` through results: one `Pair{Any,Any}(k, v)` constructor call at `Any` turns `Dict{Any,Any}` iteration from 7 ns into 112 ns with 64 bytes. The only thing that brings a site back to plain speed is a fact: an `invoke` at the declared signature (0.7 ns, verified) or a guarded direct call at a concrete signature (what (D) does). Everything else is implementation.
3. "The limit of four" is misstated in facts §3, and in both directions. Julia's bound is `unionsplitcost ≤ 4`, which counts the largest union as 2: a single `Union` argument of 8 concrete types splits into 8 facts (1.1 ns under `all`), while two `Union` arguments of 3 types do not split (cost 6): a run-time site at 44 ns and 64 bytes per element, a 45× tail with no `Any` anywhere. The same rule means `Dynamic` beyond four implementations costs one constant, not a mechanism.
4. `Dynamic{X}` keeps its promise for at most four implementations and for an arbitrary four: the split's candidates come from the method table's iteration order after a package load, which differs from the declaration order a package image compiled under. In HShapes, image code splits over H1–H4 while the session's candidate list is H10, H42, H64, H14 (`code_typed` shows the latter, the image runs the former). Elements of any other implementation cost 18–68 ns (Julia's megamorphic path), and making a `Dynamic` costs 157 ns and 32 bytes per element because the constructor scans the candidate registry each time. This is an order-dependent 20× cliff inside trait code, the kind of cliff step 2 was postponed to avoid.

## 1. Findings, ranked by what they change

### F1. Trait code pays the `Any` tails in the product setting (verified; changes the framing of §2 of the brief)

The brief frames the tails as a cost of the test bed ("in the product setting, plain code stays plain"). The mode rule (facts §6.2, table: a neutral method reached from the facts owner is compiled by facts) makes every Base method that trait code calls a facts copy. Measured in the product setting (`hc7_product.jl`, `julia-1.13/julia`, facts default off, a `@trait_module` loaded through TraitWorld):

| Loop | In a trait module | The same code in `Main` |
|---|---|---|
| `filter!(x -> isa(x, Int), v::Vector{Any})` (Base's `filter!`) | 36.8 ns/elt | 1.1 ns/elt |
| `for x in v; n += isa(x, Int); end` (no call on the element) | 0.6 ns/elt | 0.6 ns/elt |
| `for (k, v) in d::Dict{String,Any}; n += v isa Int; end` | 242 ns/elt, 100 B/elt | 2.2 ns/elt, 0 B |
| `f::Callable{Tuple{Any}, Bool}`, `n += f(x)` over `Vector{Any}` | 62.5 ns/elt, 36 B/elt | 0.6 ns/elt (closure inlined) |

So the answer to "does trait code meet heterogeneous collections of non-trait values" is: whenever it touches one, it pays the test bed's numbers. Where it meets them:
- **Base's own internals reached from trait code.** Keyword handling (`Dict{Symbol,Any}` writes were the cold run-time sites in the CSV control), printing through `IOContext`, `string` of mixed arguments, `vcat` of mixed types, `Set{Any}`/`Dict{Any,Any}` in `unique`-like code. Mostly cold; hot when a trait module iterates a `Dict{K,Any}` or filters a `Vector{Any}`.
- **User data that arrives untyped.** `Dict{String,Any}` trees from JSON/TOML/YAML readers, `Vector{Any}` columns, `Vector{Real}`, `Vector{AbstractVector}`. The DataFrames port says `Vector{Any}` columns "needed nothing special" (`explorations/dataframes-port-lessons.md` §3), which is true for correctness and false for speed wherever plain Julia could speculate: `count(ismissing, col)` on a `Vector{Any}` column is a one-method callee at `Any`, inlined plainly and a 16 ns run-time site under facts.
- **What a trait author does today** is restructure: the DataFrames port stores `Vector{Dynamic{Column}}` (one `Dynamic` per column, not per cell) behind a `ColumnVectors` adapter (`forks/DataFrames/src/dataframe/dataframe.jl:181`, `:453`); TraitMakie replaced attribute dictionaries with typed fields `pos::Positions`, `color::ColorSpec`, `marker::MarkerShape` (`TraitMakie/src/PlotCore.jl:209`–`218`). Both follow traits §10 ("a collection of mixed types, or a field whose type changes"). Neither has an answer for data whose heterogeneity is per element and arrives from outside.
- **The `Callable` route is not a remedy** for `Any` elements: a `Callable{Tuple{Any}, Bool}` predicate costs 62.5 ns and 36 bytes per element today (the abstract-argument fallback to the dynamic adapter, the remaining-work plan's item 5), four times the run-time site it replaces.

**What the references should say.** Traits §6.3 ("take arguments of abstract types from plain callers: yes: their uses dispatch when they run") understates it: the Base code those uses reach is compiled by facts too, with Julia's heuristics removed. Facts §13 should carry the product-setting numbers above, not only the test bed's geomean.

### F2. The mechanism: no inlining without a fact, and the cascade of `Any` (verified)

**A run-time site itself costs what plain Julia's dynamic dispatch costs.** Controls (`hc4_dict.jl`):

| Loop | plain | `all` |
|---|---|---|
| `s += x` over `Vector{Any}` of `Int` (`+` has hundreds of methods; plain cannot speculate) | 16.9 ns/elt | 17.3 ns/elt |
| the same over `Float64` | 15.3 | 15.3 |
| `s += Float64(x)` over `Vector{Real}` | 95.5 | 111.7 |

Where plain Julia already dispatches at run time, the facts mode adds nothing (the per-site cache's exact-type and wildcard entries, compiler §3.2, did their job: the dispatch profiler shows every call in the `filter!` loop served by the site cache).

**The tails are two things plain inference gives at an abstract call and the facts rule withholds:**
1. **Inlining of a callee whose method is declared at `Any`.** `filter!` on `Vector{Any}` makes exactly two dynamic calls per element under `all` (dispatch profiler, `hc5_profile.jl`: 99,900 calls each to `setindex!(::Array{Any}, @nospecialize(x), ::Int)` at `essentials.jl:978` and to the predicate closure): 16.6 ns each, 33 ns together, against 1.2 ns plain where both are inlined. Each callee has exactly one method, at `Any`; plain infers it at the abstract signature with a method-table edge and inlines it. The facts rule refuses that edge (any owner of a type may add `setindex!(::Vector{Any}, ::Mine, ::Int)` and would change dispatch there), so the call is dynamic.
2. **The cascade.** A run-time site's result is `Any`, so every call on it is a run-time site, and every intermediate is boxed. `iterate(::Dict{Any,Any}, i)` has one such call: `(Pair{Any,Any})(k, v)` (the constructor at `Tuple{Type{Pair{Any,Any}}, Any, Any}` is not a dispatch tuple). Its `Any` result makes the destructuring `indexed_iterate` two more run-time sites and the `getfield`s untyped: 7 ns and 32 bytes become 112 ns and 64 bytes for `iterate`, and 2.1 ns become 223 ns with 104 bytes per element for `for (k, v) in d` (`hc4_dict.jl`, `code_typed` under both modes).

**Inherent against implementation.**
- *Inherent to the rule as stated:* a run-time site cannot be inlined and cannot type its result. A dynamic call through the per-site cache costs 16–17 ns here; a codegen-emitted cache with direct calls (plan §5) would save the `jl_apply_generic` entry and the four-slot probe, perhaps down to 5–8 ns, but the boxed ABI and the `Any` result remain. The gap to 0.5–1 ns is closed only by a fact.
- *Two facts the references already admit close it:*
  - **`invoke` at the declared signature** (facts §3, last row). `invoke(setindex!, Tuple{Array{Any}, Any, Int}, a, x, j)` in the `filter!` loop runs at 0.7 ns under `all` (`store_invoke`, `hc1_filter.jl`), equal to plain. The semantics differ from a generic call only if a more specific method appears later, so this is for explicit code (Base's `Vector{Any}` internals, a trait module's own loops), not for the compiler to insert.
  - **A guarded direct call at a concrete signature,** with a dynamic fallback: (D)'s shape. Each guard's target is a dispatch tuple with an edge; the choice of guards has none. See F6.
- *Implementation, fixable without touching the rule:* the lookup (fixed, stage 1), capped world ranges (plan §3, item 1), the four-slot per-site cache that thrashes beyond four types (F4), `Dynamic` construction (F4), the `Callable` abstract-argument adapter (F1).

### F3. "At most four" is not Julia's rule, and the references are wrong about it in both directions (verified)

facts §3 says a fact signature includes "its union splits, at most four", lists "a union with more than four splits" as a run-time site, and says "the limit of four is Julia's own bound on union splitting … a call may stand for up to sixteen concrete signatures". The code says otherwise. `is_union_split_eligible` (`abstractinterpretation.jl:377`) requires `1 < unionsplitcost ≤ 4`, and `unionsplitcost` (`typeutils.jl:201`) multiplies the union lengths with the *largest union counted as 2*. Measured (`hc6_unionsplit.jl`; the facts mode's `facts_find_method_matches` uses the same test, `facts.jl:211`):

| Signature | `unionsplitcost` | splits | `all` | plain |
|---|---|---|---|---|
| `ar(::Union{8 structs})` | 2 | 8, all facts | 1.14 ns/elt, 0 generic calls | 0.91 |
| `two(::Union{2}, ::Union{3})` | 4 | 6 | 1.6 ns/elt | 1.49 |
| `two(::Union{3}, ::Union{3})` | 6 | none: a run-time site | **43.8 ns/elt, 64 B/elt** | 0.98 |
| `two(::Union{4}, ::Union{4})` | 8 | none | **47.7 ns/elt, 64 B/elt** | 0.91 |

So:
- a single union argument of any size is a fact signature (8 splits are 8 facts; G1 and G2 hold at each, since each is a dispatch tuple);
- two union arguments of three members each are a run-time site, a 45× tail from a `Union` of 3, which the reference's wording ("more than four splits") would not lead a reader to expect; plain Julia infers the single matching method at the abstract signature and inlines it;
- the "sixteen" composition rule is not what runs. Three different limits exist: Julia's cost rule for top-level unions, `fact_splits_ok`'s count of at most `MAX_FACT_SPLITS = 4` concrete tuple types for unions inside tuple arguments, and `concrete_splits`' limit of 4 for folded `return_type` answers.

**Consequence for `Dynamic`.** `abstract_split_call` builds one `Union` of the candidates and hands it to `abstract_call` (`facts.jl`, `abstract_split_call`). Under Julia's own rule that union costs 2 whatever its length. "The first four registered" (`dynamic_candidates`, `MAX_FACT_SPLITS`) is therefore a constant the facts code chose, not a limit Julia imposes; `dynamic_candidates` returning 8 or 16 would split that many ways with no change to inference or the inliner. The cost of a longer split is code size (each case inlines the implementation) and a linear `isa` chain; see E3 below for where that stops paying.

**Fix in the references:** state Julia's cost rule for top-level unions, the separate `MAX_FACT_SPLITS` for tuple-argument unions and `return_type`, and that the limits are code-size heuristics, not conditions of G1 or G2.

### F4. `Dynamic{X}` beyond four: an arbitrary four, Julia's megamorphic cost beyond, and 157 ns to make one (verified)

`hc3_dynamic.jl`, HShapes (64 implementations in its image, the workload compiled `total` for n = 2, 4, 16, 64), product setting:

| n implementations cycling | `Vector{Dynamic{Shape}}` | plain twin (`PShape`, 64 methods) |
|---|---|---|
| 1–4 | 0.91–0.94 ns/elt, 0 B | 32–35 ns, 32 B |
| 5 | 4.41 ns, 3.2 B | 73.5 |
| 8 | 10.6 ns, 8 B | 75.4 |
| 16 | 47.8 ns, 12 B | 77.7 |
| 64 | 65.2 ns, 15 B | 89.1 |
| only H1 / only H4 / only H5 / only H64 | 0.91 / 1.01 / 19.5 / 21.9 ns | |

- **Which four.** The session's candidate list (`Compiler.dynamic_candidates`) is H10, H42, H64, H14: `_note_conformances!` (`core.jl:397`) registers in the order `methods(implementation)` iterates, the method table's order, when the package loads. `total` from the image runs fast for H1–H4 and slow for H5 and H64, so it was compiled over H1–H4 (registered in declaration order during precompilation, one `@implement` at a time). `code_typed(total, …)` in the session shows four `isa` checks over the session's list, not the code that runs (facts §7.2 "reflection shows the code that runs" is about the mode; the candidate set is a time-dependent input nobody shows). A function the user writes in the session splits over H10, H42, H64, H14. The reference promises "the first four registered" and defines no order; in practice the author cannot know, and `evidence.md`'s "near plain speed" rows are for the lucky four.
- **Beyond the four**, each other element costs 18–22 ns at n = 5 and about 68 ns at n = 64: the fallback is a dynamic call whose per-site cache has four slots (`N_CALL_CACHE` indexing in `gf.c`), so with more than four trait-object types at one site it thrashes into the leaf cache with argument hashing. That is plain Julia's megamorphic path; the plain twin shows the same growth. Not a correctness issue; a 20–70× cliff on the fifth implementation, decided by load order.
- **Construction.** `Dynamic{Shape}(H1(1.0))` costs 156.6 ns and 32 bytes. The constructor (`core.jl:348`) calls `register_dynamic_candidate!` on every construction, which loads the registry, looks up the family and scans the candidate vector linearly (64 entries here). The design's remedy for a user's heterogeneous collection is per-element conversion, so this is on the critical path of F5. It is an implementation cost: a per-type "registered" flag, or registering only at declarations, removes it.
- **Memory** is fine: a `Dynamic{Shape}` element is one pointer plus a 16-byte kept object, the same as a boxed plain element (`summarysize` 16.04 B/elt both).

The plain twin in HShapes and in `evidence.md`'s "plain with four types" rows is a function with more methods than `max_methods`, that is, always dynamic; the fair plain baseline for n ≤ 3 is 0.9 ns (E2 below). The evidence should say which baseline it uses, and carry the n ≥ 5 rows.

### F5. For heterogeneous user data the design's answer is a copy, and the copy needs a trait (reasoning, with F4's numbers)

A `Vector{Any}`, `Vector{AbstractFoo}` or `Dict{String,Any}` crosses into trait code as what it is (a concrete container type), and every operation on an element is a run-time site (F1). To recover, the author must (1) have a trait `X` whose operations cover what the loop does, implemented for every element type (the trait's owner may implement it for `Int`, `String`, …, traits §12.1), and (2) convert the collection to `Vector{Dynamic{X}}`: an O(n) copy at 157 ns per element today (F4), which also breaks aliasing (writes no longer reach the user's vector). Open issue 11 ("how `Vector{<:ColTable}` takes a user's vector: element by element into a new vector of trait objects, or as a whole") is exactly this question and is unresolved; traits §10 does not link it. Rust (`Vec<Box<dyn Trait>>`) and Swift (`[any P]`) have the same shape, but there the user never had an untyped vector to begin with; in Julia `Dict{String,Any}` and `Vector{Any}` are the lingua franca of readers and configuration, and plain Julia's heuristics made them tolerable.

The references' rule "a slowdown is acceptable where traits can recover it" (facts §13, design §2 step 4) is satisfied in letter for these collections and not in practice: the recovery is a data-structure change at the boundary, not a rewrite of the function.

### F6. A reference-consistent recovery without declarations: the method table as (D)'s candidate source (reasoning; one measurement supports it)

Step 2 of the speed plan ("guarded devirtualization") was postponed because "a failed guard is a cliff: that site turns dynamic for good". That describes the version-guard form (a validity check against the method table, CPython's tags). A different form already exists in the compiler: `split_call`. At a run-time site whose callee has, today, methods at concrete signatures (`pa(::P1)`, `pa(::P2)`), emit (D)'s split over those signatures: `isa` guards, direct calls that inline, the dynamic call last, never fully covered. Each direct call is a fact (a dispatch tuple) with its edge; the choice of guards records nothing, as `Dynamic`'s candidate list records nothing. G1 holds as for (D) (the fallback is the real dispatch, so a type outside the set computes plain Julia's result); G2 holds (a stakeholder's method at `(pa, P1)` invalidates the fact, as in plain; an unrelated load changes nothing). There is no "turned dynamic for good": a type outside the set takes the fallback on every visit, which is today's cost.

What it recovers: the `Vector{AbstractFoo}` tail where the subtypes have their own methods (E2: `Vector{Sh}` with two or three methods, 32 ns and 32 B per element under `all` against 0.9 ns plain; expected to return to about 1 ns). What it cannot recover: callees whose only methods are at `Any` or abstract types (`pred(::Any)`, `setindex!(::Vector{Any}, ::Any, ::Int)`, `Pair{Any,Any}(::Any, ::Any)`, `ismissing(::Any)`): there is no concrete signature to guard. Those need type feedback (the types the site cache has seen, fed to a recompilation: Self and V8's gain came from this, as the inline-caches review notes), or an explicit `invoke` where the code is Base's own.

Load-order dependence of *speed* remains, as in plain Julia and as in (D) ("which candidates a caller splits over is fixed when the caller is compiled", compiler §4.2). The design accepted that for (D); the same acceptance covers this.

### F7. Smaller gaps in the references

- facts §5 "A run-time site costs a dynamic dispatch, as in plain Julia" is true and misleading: say "plus a result typed `Any`, so each call on that result is a run-time site too and intermediates are boxed; where plain Julia inlines a one-method callee the difference is 15–30× per call" (F2).
- facts §3.7 (traits): whether `Vector{Any}` or `Dict{String,Any}` as a declared field counts as "concrete with concrete parameters, all the way down" is not stated; `Vector{Dynamic{X}}` presumably does. The `@error_on_abstract` example `cold(t::ColTable, k::Vector{Any})` suggests `Vector{Any}` is treated as abstract. State it.
- traits §10 should say what a user's existing `Vector{AbstractFoo}` or `Vector{Any}` costs to use and to convert (F5), and link open issue 11.
- traits §9: a `Callable` at an abstract argument type (`Callable{Tuple{Any}, …}`) is 62.5 ns and allocates today (F1); the reference promises "called through a pointer" without this caveat.
- evidence §2: add n = 5, 8, 16, 64 for `Dynamic`, and name the plain baseline (a 64-method function) for the "plain with four types" rows.
- compiler §4.2 / lowering §13: state the registration order (declaration order during precompilation, method-table order after a load), or fix it (F4).

## 2. The options compared

"Cost" is per element where measured in this review (M) or expected (E). "Needs" is what the compiler or language must add. "References" says whether the option is consistent with the four references as written.

|---|---|---|---|---|---|---|

## 3. Proposed experiments

Each names what to build or run, what to measure, and the result that would change the design.

1. **The tails in the product setting, on the demonstrators** (no build). Run the forks' session, TraitReport and TraitMakie's suite with `JULIA_FACTS_DISPATCH_PROFILE=1`, product setting, and classify the top 40 call sites: Base internal on `Any` containers, user data, machinery. Decides whether F1 is a theoretical or a measured cost on real trait code. A result that would change the design: a hot site in Base reached from every demonstrator (then Base's `Vector{Any}` internals need invokes or F6/feedback before traits can claim plain speed on real workloads).
2. **`Dynamic` beyond four by one constant** (a one-line build). Set `dynamic_candidates` to return 8, 16 and 64 candidates; rerun `hc3_dynamic.jl`; record per-element time at n = 5, 8, 16, 64, the size of `total`'s native code and the compile time of `total`. Decides where the split stops paying (expected: flat at about 1 ns to 8, rising linearly beyond; code size linear). A result that would change the design: 16-way splits within 2 ns and acceptable code size make "four" a tuning constant, and traits §10 drops the sentence.
3. **A flat cost beyond the split** (a small C change). Give facts fallbacks, or every dynamic site, an 8- or 16-way associative per-site cache (`N_CALL_CACHE` indexing and `pick_which` in `gf.c`); rerun n = 16 and 64. Decides whether the 47–68 ns megamorphic cost becomes 15–20 ns flat. This is the compiler §3.3 Optional item in its cheapest form.
4. **Deterministic candidates** (TraitWorld). Register candidates in declaration order after a load (sort `methods(implementation)` by the `@implement`'s line, or keep an ordered list in the image), and add a check that an image's split and the session's split agree. Then measure "only H5" again. Decides F4's cliff; a result that would change the design: none expected, but the reference then has a rule to state. Also consider an explicit author's list (`@dynamic_fast Shape (H1, H2, H3, H4)`): it is the only way an author can choose.
5. **`Dynamic` construction at a few nanoseconds** (TraitWorld). Register at declarations only, or keep a per-type flag; measure `Dynamic{Shape}(H1(1.0))` (now 157 ns, 32 B) and the conversion of a 10⁶-element `Vector{Any}` of two conforming types to `Vector{Dynamic{X}}`. Then prototype a lazy view (`DynamicView{X}(v)` whose `getindex` makes a `Dynamic{X}` per read) and compare a sum over it with the copied vector and with plain's dynamic dispatch.
