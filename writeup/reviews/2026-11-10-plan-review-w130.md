## Summary

The rule (§2) is right and is the principled form: the entry and the contract are the record, the dictionaries a cache. The lazy sync in the hooks is the right time: the package callback runs only after a whole chain (loading.jl:2230), and the image hook runs before the image's own entries are in force (staticdata.c:4533 before 4544). Three things are wrong or missing, and one of them is a runtime bug the plan would inherit:

- **Where the list is appended.** The entries of an image's own types, the main case, take the `present` path of `jl_activate_memberships` (datatype.c:734–739), which skips `index_entry` today. Probe `index3` shows the consequence: a pattern that gives a type a second instance of `Indexable` through TraitWorld's image-loaded `MutableIndexable{T} in Indexable{T}` is accepted, where the same shape through a session entry or an external image entry is refused. The plan's append must not sit in that branch, and the missing index is a C- deviation to retire in the same commit.
- **`struct S <: X` members have no entry** (implement.jl:133–134; probe B). The rebuild's source does not see them. The plan does not say so.
- **The gate's case 3 cannot flip the way §6 says.** With the records rebuilt in TE's precompile session, TE's method is refused at its definition and TE fails to build, as TD does. No "left inactive" image exists to load.

Beside these: `check_member(…; infer = false)` is the wrong tool (it still infers at a custom `getproperty`, warns again, walks `methods(f)` on every problem, and drops a record where it finds a problem); the rebuild must be idempotent (TraitWorld's own image already carries records for its two concrete memberships); two images can leave two live entries for one member; the runtime list's design is left open on two points; and §7's list is short.

## Findings, by severity

### H1. Append before the `present` test; the entries index misses an image's own types today — verified

- `jl_activate_memberships` (datatype.c:718–747): for each live, unrefused entry it sets `min_world`, then looks whether the entry is already on its home TypeName (734–737). If it is, `continue` (738–739): no append, and **no `index_entry`** (746). An image's own TypeNames are serialized with their `memberships` field, so every entry of the image's own types is "present" (TraitWorld's `MutableIndexable in Indexable`, `Resizable in HasLength`, probe A), and only entries on other modules' TypeNames (`BitVector`, `AbstractArray`, `Dynamic`) go through the append and the index.
- Probe `index3`: with `MutableIndexable{T} in Indexable{T}` from TraitWorld's image and a session `Fm2{T} in MutableIndexable{T}`, `_declare!(Fm2{S} where S <: AbstractFloat, Indexable{Int})` is **accepted**; afterwards `Fm2{Float64} <: Indexable{Int}` and `<: Indexable{Float64}` are both true, two instances of one set for one type (compiler §4.6's rule broken). The control through a session chain (`Sub{T} in Sup{T}`) is refused "at another instance already"; the control through an external image entry (`AbstractVector{T} in Indexable{T}`, appended at activation) is refused too. `pattern_second_instance` reads `jl_set_entries` (datatype.c:1054) and follows a set's own membership only from the index (1060–1067). `set_entries_meet` (833) reads the same index: an intersection whose only members come through a package's own types is unmet there.
- For the plan: "appends each entry it activates" placed next to `index_entry` would miss the image's own types, which is the whole case (TraitCSV's five `Vector{…}` members are external, TraitMakie's 26 are mostly its own).
- **Change:** in `jl_activate_memberships`, after `activation_conflicts`, append the entry to the session list and call `index_entry(en)` whether or not it is present on its TypeName; keep the `present` test only for the TypeName's svec. A compiler deviation row (the next C- ID) retired by the same commit, naming the probe's case; a gate line in `n12_image_instances` (a pattern's second instance through an image's own-type entry refused) and one for `All{…}` met through such an entry. Compiler §9's "An image writes the entries it declares on other modules' typenames in a list of its own" is then wrong about the list's contents (the writer takes every entry not in an image, staticdata.c:3524): say the list holds all the image's entries and activation indexes all of them.

### H2. `struct S <: X` members are not in the source — verified

- `_implement_one!` makes no entry for a declared subtype (implement.jl:133–134: "needs no entry"); probe B: `struct Sq <: Shp; @implement Shp Sq` leaves 0 entries on `Sq`'s TypeName and 1 record in the session. The runtime refuses the entry for a parameterized trait (the concrete path's `in_set && !in_instance`, datatype.c:1196–1211), which is why none is made.
- So a package's `struct S <: X` members from its image keep no check after this plan, and nothing in the plan or the references says so. None of the four ports uses the form (grep); TraitWorld's tests and the references do (traits §5.2).
- **Change:** either make the record the runtime keeps for `struct S <: X` (lowering §3's own step 6 substitute: the receiver on `S`'s `TypeName`, L-52) carry what the rebuild needs, and read it in the sync; or an entry after all (the runtime's refusal is only for `X{p…}` against the bare `X`, and the library knows the instance). Until one is built: the coverage statement in traits §5.10's status and L-55's narrowed row name the form, and the gate asserts it (`@test_broken` or a fourth case). Do not leave it unstated.

### H3. §6's case 3 flips to a precompile failure, not to a method left inactive — reasoning, certain from the code

- TE's precompile session loads TA's image (entries activated) with TraitWorld's hooks installed (its `__init__` runs for a dependency; case 2's TD proves the hook refuses in precompile). TE's `area(::Square, ::Int) = 1` enters `_definition_hook` → `_check_membership_calls` → the sync rebuilds `Square`'s record `Tuple{typeof(area), Square, Int}` → `_would_win` (TA's `area(::Square, ::Integer)` is less specific) → not ambiguous → `_infer_new_method` gives `Int`, outside `Float64` → `ImplementError` → TE fails to build. The plan's "TE's method left inactive with a warning" needs an image of TE that no session with this TraitWorld can build.
- **Change:** case 3 asserts `!ok` and `ImplementError` for TE's precompile, as case 2 does for TD, and the fresh session's `using TA` then a session definition of the same method refused. The image hook's "left inactive" path is exercised by case 1 (TC at a pattern member); for a concrete image member it can be produced only with a stale image, which needs a test-only switch (`JULIA_TW_LOAD_RECORDS=0` while TE is built) or is dropped. I would drop it and say why in the gate's header.

### M1. `check_member(…; infer = false)` is the wrong tool; make the records one function — verified (code), reasoning on the fix

- What `check_member` runs beside the operations walk: `_check_fields!` infers `getproperty` at a member with its own `getproperty` (check.jl:334–336; probe E: `_has_own_getproperty(PN)` true and the check passes through inference; TraitMakie's source has one `getproperty` definition); `_check_concrete!` warns per session (check.jl:54–55), so a `@warn_on_abstract` member warns again at every load; `_agree!`, `_hidden_method`; and on every problem `_near` walks `methods(f)` with `typeintersect` (0.19 ms each for `length`, `getindex`, `iterate`, probe D).
- What it records wrongly: an operation with a problem gets no record (check.jl:177–191: `continue` before the record). A pirate with an untyped receiver loaded earlier, or a serving method left inactive by an earlier record or by strict mode, removes the operation's record silently; a later definition at that operation is then judged by nothing.
- The shape is the same at `@implement`, at a first use and at the rebuild once the check has passed: a checked result for each served, non-open operation; a fixed call for each defaulted, unserved one; the forwarders' signatures for a `by` member. `_check_contract!` interleaves them with the check today (check.jl:176, 203).
- **Change:** one `_records_at(X, inst, S, how)` that does `_params_at` and the operations walk of `_check_contract!` (the contract and its supertraits', check.jl:26–33) without inference, no fields, no concreteness, no `_near`; it records a checked result for every served non-open operation whatever the serving method, a fixed call for every defaulted unserved one, and nothing else. `_implement_one!` and `_check_pattern_member` call it after a passed check; the sync calls it on an entry. For a `by` member it computes the forwarders' signatures with the code `_define_fwd!` uses (one `done` set per operation and arity). Then the session's records and the rebuilt ones cannot differ in shape, only in what the method table holds now (M4).

### M2. Idempotence: TraitWorld's own image already carries records; the cursor is serialized — verified

- Probe A: TraitWorld's image activates two concrete entries, `BitVector in MutableIndexable{Bool}` and `in Resizable{Bool}`. Probe I: after `using TraitWorld` from its image, `_CHECKED_RESULTS` has 7 keys and `_PATTERNS` 32 entries: TraitWorld's own globals come back with the image, so its own build's records are already in the session. The sync from a cursor at 0 records them again. Two threads defining methods, or a hook re-entered, would double-record too.
- The cursor (a `Ref` in TraitWorld) is written into TraitWorld's image with the value at the end of its build (0 by luck: nothing with memberships loads before TraitWorld there).
- **Change:** the rebuild forgets the member's records for the trait first (`_forget_records!(X, S)`, implement.jl:208) and records anew: idempotent, and the same as a redeclaration's path. `__init__` sets the cursor to 0. The sync is wrapped so that no exception of its own refuses a method or fails a load (a `@warn` and the cursor still advanced).

### M3. Two images can leave two live entries for one member — verified by reading, not probed

- `jl_declare_membership` ends the older entries of the same member and inputs (datatype.c:1230–1245). `jl_activate_memberships` ends nothing (711–755): a concrete entry at the same instance passes `activation_conflicts` (`in_set && in_instance`, 704–708) and is appended beside the older one. So package Q's image redeclaring `@implement X S by f` for P's `S` (a joint owner) leaves P's `:self` entry and Q's `:field` entry both live in a fresh session. The rebuild would record both: `S`'s own methods' calls as checked results and the forwarders as fixed calls, and refuse a method either way.
- **Change:** the runtime ends the older live entry of the same member, set and inputs at activation as at a declaration (the principled fix; a C- row if not now). The rebuild takes, per (member, set, inputs), the live entry with the greatest `min_world`. One sentence in compiler §9.

### M4. The rebuilt record is the build's claim, not the session's state: say it — reasoning

- The plan's §4 names a pirate loaded earlier. The class is wider: any method defined in the session before the load, a method of an earlier image left inactive, a serving method deleted. In each the rebuilt record says "checked at `tt`, within `declared`" although the current serving method may not be. That is the right reference (the first review's L4: the record, not the state), and M1's walk records whatever method serves. But where the walk finds no serving method and no default, the operation is broken now, and nothing says so.
- **Change:** traits §5.10's status states the limit in one sentence; under strict mode, `_strict_at_load!` (strict.jl:300) reports an entry whose operation has no serving method, as it reports a pirate loaded before an image (facts §11.3). Whether to infer each checked call at load under strict mode is a choice for the user (open issues §1), not a default: the cost is the full check per entry (probe D: 18 µs to 1.1 ms cached, more uncached).

### M5. The list's design: decide the two open points; what the image writer does — verified

- The plan offers an svec replaced copy-on-write or an array appended under the lock. The readers are the hooks, which run outside the world-counter lock (compiler §10.1; the image hook at staticdata.c:4533 before the lock at 4536), so either works; an array appended under the lock and read without it is not safe across a reallocation. **Change:** an svec replaced copy-on-write with a release store and an acquire load, as `tn->memberships` (datatype.c:192–199), returned by the accessor as it is (immutable): no copy and no lock on the read path. `jl_activated_memberships_since(k)` then needs no C loop; `count` is `jl_svec_len`.
- Roots: `JL_GLOBALLY_ROOTED`, pushed in `gc-stock.c` (2922–2924) and `gc-mmtk.c` (549–551), and the heap snapshot (2930), as the three sibling lists.
- Images: tags are written for the system image only (staticdata.c:3095); the list is not a tag and is reachable from no serialized object, so no package image holds it. The declared list's filter `jl_object_in_image(en) || jl_object_in_image(en->declarer)` (3524) would exclude activated entries even if they were in one list. Say in compiler §9 that the session list is never written.

## The questions, answered

1. **Sound and complete for §1's cases?** The mechanism is sound where its source is complete, and the source has two holes: the append point (H1, which would miss the image's own types) and `struct S <: X` (H2). The order: the image hook before activation is right only because the sync is lazy; an image's own entries meet the next definition or the next image's hook (L2). A chain in one `using`: covered, the sync runs in each image's hook (loading.jl:2230 is why the callback would not). Revise: a session definition, covered, `delete_method` then define judged by the record. An extension: an image like any other, covered. Refused at activation: skipped. Redeclared: a session redeclaration ends the entry and forgets the records (implement.jl:91); across images the runtime ends nothing (M3). No contract: skipped (L6). Before TraitWorld loads: only TraitWorld's own image, whose records come back with its globals (M2).
2. **`check_member(…; infer = false)`?** No: a dedicated walk shared with `@implement` and the first use (M1). It records the same shape as the original check once the check passed; the differences are only the method table's (M4), which is the right reference. Supertraits' contracts: included as at `@implement` (check.jl:26–33). `_open_further`: no record, as now. An untyped receiver: a record anyway (M1). `struct S <: X`: no entry (H2).
3. **Threads, GC, the writer.** M5: an svec copy-on-write with release/acquire, rooted in both collectors; never written (not a tag, not reachable; the declared list's own filter would exclude it anyway).
4. **Cost.** L3: nothing per definition, under 1 ms per session for the ports' memberships.
5. **Forgotten; simpler.** §6: H3's case 3, a `struct S <: X` case, a redefinition within the result accepted, the count of `BitVector`'s records after the sync (M2), strict mode on across a load, H1's gate; TraitWorld's suite and the battery as listed. §7: L4. Simpler and principled: M1's one function for the records, and H1's one index for the entries; the entry-carried record (L2) is the reference's own design and the alternative to record.
