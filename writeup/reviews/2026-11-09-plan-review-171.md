## Summary

The plan's diagnosis is right and its fix at `IO` is right. Two things it does not see:

- **The head miscompiles the case the plan is about** (verified, `eraser_ir.jl`): a closure `() -> wb(IOContext{IO}(S()), 0x01)`, with `S` a user stream whose `write` returns a `UInt`, is typed `Int64` by inference and compiled to `return 0x01` (a `UInt64`); run, it reaches `unreachable` and the process dies with `signal 4`. The cause is the plan's own thesis one level up: the regular inference of the eraser's forwarder claims the declared `Int`, constant propagation through the eraser's constructor reaches the stream's own method and gets `UInt`, and `handle1` inlines the second with the first's type. 2.1 removes it at `IO`. 2.2 keeps the class at every set: an escaped member's `T ⋢ R` meets the same two paths. The plan needs a compiler guard and a library check it does not have.
- **The plan's list of conversion sites misses the one every branch not inlined goes through** (verified): `Base._SplitTarget`'s call in `base/splittarget.jl` is `convert(R, (f::F)(x::T, …))::R`. With the listed edits alone, the pointer branches and the table still convert.

Beside these: the set gate as written would raise `ImplementError` at `@implement`, not the `TypeError` it is meant to show; the `--compile=min` run has no place in the gate runner; and alternative (d) can be dropped, not deferred, since vanilla infers `Any` for every operation in a caller at `IO` (verified).

## Findings, by severity

### H1. The head miscompiles a `UInt`-count stream through the eraser built in the frame; 2.1 fixes it at `IO`, 2.2 leaves the class open at sets — verified

- The run (`eraser_ir.jl`, head 8c4b93f867):

  ```
  struct V <: IO end; Base.write(::V, x::UInt8) = UInt(x)
  wbs(io::IO, x::UInt8) = write(io, x)
  f = () -> wbs(IOContext{IO}(V()), 0x01)
  ```

  `Base.return_types(write, (IOContext{IO}, UInt8))` is `Int64`; `code_typed(f)` is `return 0x0000000000000001` with the closure's result `Int64`; `f()` dies: "Unreachable reached", `signal 4`. The same with `wb(@nospecialize(io::IO), …)` (`eraser_head.jl`), the same with the count not a constant (`eraser_variants2.jl`, `nofold`). Not with a stream whose count is an `Int` (`int-closure`), not with the eraser built outside the closure (`outside`: `Int64 7`, converted), not at an `IOBuffer`, not at `Core.stderr`.
- The mechanism (verified in the IR; the acceptance rule read at `abstractinterpretation.jl:419–449`): the regular inference of `write(::IOContext{IO}, ::UInt8)` is `write(pipe_writer(io)::IO, byte)` at a receiver typed `IO`, the split, the declared `Int`. Constant propagation into the same method with the constructor's `PartialStruct` knows `io.io` as `V`, infers `write(::V, ::UInt8)` directly (a concrete receiver: no split, no conversion) as `UInt`. Line 427 refuses the wider type, but line 438 (`is_better_effects`) and line 445 (a narrower exception type) take the constant-propagation IR anyway, with the regular type. Vanilla may do that because both inferences over-approximate the same executions. A declared result enforced at the call site, only where inference sees the trait type, is not an over-approximation of the member's executions, so the two inferences disagree, and codegen emits `unreachable` where the `UInt` meets the `Int`.
- This is open issue 171's pattern, "a rule applied only where inference applies it", at its worst: not a different value but a crash. It is on B-display's path (8c4b93f867: `show_limited` and `TextDisplay` build `IOContext{IO}(io)` in their own frames). Whether the REPL's `LimitIO` (`unsafe_write` `Union{Int, UInt}`) meets the "better effects" branch there I did not test; E-338's REPL suite passed, so probably not, but the gate below should say.
- **With 2.1** the regular result at `IO` is `Any`, every constant-propagation result is `⊑ Any`, and line 427 takes it with its own type: the class is gone at `IO`. Reasoning, not verified: my in-session probe cannot show it, because the system image's CodeInstance of the forwarder keeps `Int` (the first `plan_2_1_probe.jl` run crashed at the same line with `Any` set in session). The gate must.
- **With 2.2 as written** the class stays at every set. A member whose serving method infers outside `R` (a method redefined after its check; an operation with an abstract further argument, which §5.10 exempts from the check; a member of an abstract type or a pattern before its first use) gives the same two inferences: the split's `R`, asserted, and constant propagation's `T` at the concrete member, through a struct built in the frame (`g(h::H) = op(h.x)` called as `() -> g(H(S()))`). The assertion lives in the regular IR, which is the one not inlined. So "assert, don't convert" alone does not make 2.2 sound.
- **Proposal, both parts:**
  1. **The compiler's guard** (`abstractinterpretation.jl:438–447`): a constant-propagation result is inlined only with a statement type that covers it. Where the IR is taken for its effects or its exception type and `this_const_rt ⋢ this_rt`, set `this_rt = this_rt ⊔ this_const_rt` (the join), or discard the result (simpler, loses vanilla's rare gain). With the join, the statement's type always covers the inlined return, whatever the library checks. This is the fix at the rule: inference may use a declared result only as what it is, a claim the call asserts, never as a bound on code inferred without it.
  2. **The library's invariant** (finding 3): every member's serving method is checked by inference to infer within `R` at its membership, at its first use, and again when a serving method is redefined; the exemption at an abstract further argument is kept only with the guard in place. Then the two inferences agree for every checked member, and the assertion fires only for the escapes the check cannot close.
  3. **Gates:** `n19 (2)` gains the closure forms, which must return the stream's own `UInt(7)` at `IO` and through `IOContext{IO}(S())` built in the closure, and must not crash; a set gate with the `PartialStruct` form after a redefinition (finding 3), which must raise `TypeError` or return the member's value, never miscompile; a REPL line in the forks' transcript gate that displays through a `LimitIO` after a `UInt`-count stream is defined.

### M4. The statement of the rule at sets: what G1 permits, and what the references must say — reasoning

- G1 (facts §2.1) compares code compiled by facts with plainly compiled code. Compiler §7.1 applies the split in both policies, so the assertion is the same on both sides and G1 holds trivially there. The difference 2.2 creates is between a call compiled with the receiver typed by the trait and a dynamic call, or the interpreter. G1 does not speak about that; facts §13.1 does only for plain code at `IO`, which 2.1 settles.
- A `TypeError` only compiled code raises is acceptable at a set on one condition: that it is a backstop, not a semantics. For every checked member the check (inference, `rt <: R`) makes the member's result `⊑ R` on every path, so the assertion never fires and the dynamic call returns the same value. It fires only for an escape of the check. That is the rule to write: "the result of a call through the trait is the declared result; a member's serving method is checked to return it; a call compiled with the receiver typed by the trait asserts it, as a check of the library's own invariant; a call that dispatches on the member's type, and the interpreter, run the member's method and return its result".
- The better rule the task asks about, checking at the redefinition, is part of the invariant, not a replacement for the assertion (finding 3). Alternative (c), conversion in the member, is rightly rejected: the library does not own the member's method.
- **Changes:** facts §2.1's "or raises" bullet names the escapes and the interpreter; traits §7.9 and §11.1's row say "asserted" and name `TypeError` only (the `MethodError` "a result that does not convert" goes, as planned); facts §9's sentence "the conversion and the assertion catch a member checked only at its first use, a member by its declared supertype, or one whose method was redefined" becomes the invariant plus the backstop; facts §14's bullet on 171 goes.

## The questions, answered
