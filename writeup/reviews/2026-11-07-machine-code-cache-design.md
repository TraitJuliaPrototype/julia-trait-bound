**The goal, as judged here.** A fresh Julia process on a precompiled environment runs one script: load the DataFrames port and the Makie port, read a CSV, select, sort, group and summarize, join, apply a user function by row, draw a figure, save a PNG, exit. Against the same script in Python (pandas, matplotlib), both measured from process start to exit on the same machine. "First" means the first run of that workload in a fresh session, not the first session after an install: no cache across sessions can serve the latter (L1). The project has no measurement of this workload on any build (M3); the nearest are E-233 (the DataFrames port alone, a 26-step REPL session, 4.71–4.83 s against pandas' 0.54 s), E-228 (the Makie demonstrator's plotting session, 0.68–0.69 s against matplotlib's 0.98–0.99 s) and E-233's TraitReport (a CSV→PNG script on small trait cores, 0.63 s against Python's 0.61–0.62 s).

**In one paragraph.** The cache is not the lever for this goal, and the proposed order spends its first weeks on the two parts that serve the goal least. The project's own estimate (E-234) says a *perfect* cache of a session's machine code, plain code included, takes the DataFrames session from 3.9–4.1 s to 3.0–3.2 s, still 5.5–6 times pandas; a cache keyed on facts, as decided on 2026-10-27, keeps about a tenth of that saving, because 1,083 of the 1,175 kept types are plain code (H1, H2). What remains after a perfect cache is the load (1.4 s against pandas' 0.2 s), the REPL's start (0.36–0.61 s, which a script does not pay), code that names the session, and the run time, which already matches pandas'. Step 3 as described ("keyed on facts" on "today's loader") is not possible: today's loader validates by build ids, so a generated image per dependency set is keyed on the environment by construction; it is E-180's retired cache under another name, and for this goal that form is the right one (H3). Step 1 (C-52) serves only step 4, which the goal does not need, and the record §9 specifies is not complete for step 4 anyway (H4, M1). SciML first serves a port that already beats SciPy (H4). The work that serves the goal, in order: the DataFrames port and the Makie port on the unified library, a gate script with its Python twin, package-image workloads for the goal's shapes, the compiler's invalidation by the library's own interpreter (E-281: 1,070 instances per load) removed by building C-40 as the reference says, a measured breakdown of the load's validation on the unified build, and then the environment-keyed session cache admitting all code, its entries' survival improved by the slot once C-65 is fixed. The slot stays as built (M2).

## Findings, by severity

### H1. The cache cannot reach the goal by itself: a perfect one leaves the DataFrames session at 5.5–6 times pandas — verified

- **The session today** (E-233, the old build julia-1.13 bfca89decc, TraitWorld ca92f22, forks 115c208; a REPL on a pty, the REPL's typing hints off; `experiments/phase2-round/README.md`): the REPL's start 0.36 or 0.61 s (Python 0.01 s); imports 1.38 s (pandas 0.20 s), of it validation of the images' edges about 0.6 s (`verify_method_graph` and `insert_backedges` are 24 % and 25 % of the load profile's samples, `logs/forks-load-profile-coarse.log`), TraitWorld's member records about 0.15 s and its image hook 0.05 s; the steps 2.03 s, of it compiling 1.55 s and a run time of about 0.3 s, which is pandas' 0.30 s; exit 0.12 s (0.03 s). Wall 3.89–4.14 s against 0.54 s.
- **With a cache of every CodeInstance the session compiled, of every owner** (E-234, E-175's emulation): the steps' compilation 1.55 → 0.58 s, the session 2.99–3.22 s. What is left: the load 1.4 s, the REPL's start, 0.58 s of compilation no image keeps (signatures with a type value, compiler §9's rule; the compiler's own code invalidated again, 115 ms; the user's closures), the run time, GC and exit. The registry row's own verdict: "the load and the code no cache keeps are the lever (the row's second branch)".
- **So the cache's whole ceiling on this session is about 1.0 s of a 3.4 s gap.** The load alone is 1.2 s above pandas'. A design that addresses only the cache cannot meet the goal; the order of work must put the load and the session-keyed code before or beside it.
- **The counter-example that shows the goal's shape is reachable:** TraitReport's form (t), a script over TraitCSV, TraitTables and TraitMakie, 0.63 s against Python's 0.61–0.62 s (E-233), with a load of 0.36 s and 0.034 s of compilation after it; E-234's cache would take 0.04 s off it. It is small cores with a workload in their images, a small dependency tree and a script, not a cache, that put it at Python's time.

### H2. The facts-keyed scope aims at a tenth of the saving; the admission rule should be the G2 bit, on code of either policy — verified (E-234, E-273, `staticdata_utils.c:557`)

- **The decision** (the user, 2026-10-27, decisions §5): "the cache across sessions keyed on facts and their origins is the direction: facts code only". The store note's §1 (rev. 2): entries of the facts owner only, none with an edge to another owner's code.
- **The evidence against it for this goal** (E-234): of the forks' 1,175 kept types, 1,083 are plain and 92 the facts owner's; TraitReport's 447 are all plain. "A store keyed on facts alone (W-66) would keep about a tenth of what saved the 0.9 s here." PE-13 records the plain-code cache as "not enabled by facts or traits" and parks it. The goal's sessions are plain-heavy because a port's users call Base, DataFrames' API, display and closures, and that will stay so on the unified build: the test bed `all` is not a product setting (facts §13.2), and the product setting compiles neutral methods plainly (compiler §2.3).
- **What the unified build changed, and the decision has not followed:** G2 is now a predicate on every CodeInstance of either policy (compiler §3.2, "Computed for plain code too", `Compiler/src/typeinfer.jl:330`), 62 % of a workload's plain code satisfies it (E-273), and the image writer already admits plain code reached only dynamically where the bit is set (`src/staticdata_utils.c:552–560`, commit 823754556f). A plain CodeInstance with the G2 bit is invalidated only by a stakeholder or a winning pirate, exactly as facts code is: it is as cacheable as facts code and validated the same way. The trade-offs review §1.4 said this: "a store that keeps plain code too needs the same record and the same G2 bit, with no second owner to relink."
- **Caveats to measure, not assume:** (a) 38 % of plain code is not G2, and E-234 did not split the 1.0 s by the bit; a census of the goal's session on the unified build (CodeInstances made after the load, by policy and G2 bit, with their compile time) decides how much a G2-scoped store keeps; (b) C-46: the bit does not consult an inlined callee's own record, so it is an over-approximation for any rule that would *skip* validation (H5), though not for a store validated by `verify_method_graph`, since the inliner adds the callee's edges to the caller's (reasoned).
- **Recommendation:** revisit the 2026-10-27 decision: the store admits code of either policy; its two tiers are the G2 bit (valid wherever its edges verify, shareable across environments once step 4 exists) and the environment (build ids, for the rest). Put it to the user as a decision row; the reference's §9 then says "code whose record satisfies G2", not "code compiled by facts".

### H3. Step 3 as described is not possible: "keyed on facts" on "today's loader" is keyed on build ids, and that is E-180's retired cache — verified (`loading.jl:4277–4345`, `staticdata.c:161–175, 342–347`, open issue 95)

- **Today's loader.** `stale_cachefile` rejects a cache file unless every required module's build id matches the one recorded ("different dependency build identifier", `base/loading.jl:4290–4345`), and an image's references to other images' objects are resolved through `jl_linkage_blobs` indexed by build id (`src/staticdata.c:161–175`, `:342–347`). A generated package image per dependency set therefore goes stale whenever any package of that set is precompiled again, whatever its facts: the cascade E-194 measured (86–90 % of C's entries lost on an update of one foundational package). Its key is the environment, by construction. "W-66's fingerprints ported" cannot change that on today's loader: they can index the store, not decide validity.
- **So step 3 is the environment-keyed cache the user retired on 2026-10-27** ("Let's retire the experimental cache and add this cache to the Todo list"), with the reasons given in the alternatives: "the environment key empties the cache at any manifest change, the store is per environment and unbounded, the parts cost about 8 ms each at load, and nothing in it rests on the facts rule." The first two are true and acceptable for the goal, which is one environment used again and again; the third is small at the goal's size (the forks' session loads one set, E-234: "one cache"; C's 45 parts cost 0.45 s, E-180); the fourth is a matter of story, not of speed.
- **What "keyed on facts" actually requires is step 4:** a loader that validates an entry by its edges and content, not by build ids, and relinks its code by stable names (open issue 95's option (b), the user's chosen vehicle). That is the cross-environment property. Nothing in the goal asks for it: the Python user the goal compares against also pays again after `pip install`.
- **Recommendation:** say what step 3 is: the environment-keyed session cache of E-180 (a recorder at exit, a builder in the background, one generated image per dependency set, loaded after the set's last package), admitting all code (H2), on today's loader. Revisit the retirement of 2026-10-27: it was decided for a different goal (reuse across environments) and against the cost model of a 45-part SciML session. Open issue 95's option (c), two layers, is the form that serves both goals; it was not taken then and should be the plan now. Step 4 stays "only on evidence", and the evidence is named (M4).

### H4. The order spends its first weeks where the goal is not: C-52 serves only step 4, and SciML is not in the goal — reasoned, with E-228, E-231, E-233

- **C-52 is not needed for step 3.** On today's loader an entry's validity is decided by build ids and by `verify_method_graph` (`Compiler/src/reinfer.jl:95`), which checks dispatch at every edge exactly, bindings, folds and `invoke` signatures (the store review M1). Images already carry edges, roots and relocations. Digests of lowered code, layouts and names by path are what a loader that *ignores* build ids needs: step 4. Building them first produces a record with no consumer and no gate for weeks, against the project's own rule that a stage has a gate.
- **"A few days, compiler-only" is optimistic and incomplete.** The names by path are read by the image writer and reader (`staticdata.c`), not the compiler; the digest of a generated function's lowered code is per specialization (the store review m3); layout identities need a canonical name for types of anonymous modules and closures; and the record §9 lists is missing what a cross-environment entry must also fix (M1).
- **SciML first contradicts the goal.** The goal names Makie and DataFrames. The SciML port already beats SciPy (E-231: 1.19–1.20 s against 1.43 s); the Makie demonstrator beats matplotlib (E-228: 0.68–0.69 s against 0.98–0.99 s); the DataFrames port is 7–9 times pandas (E-233). The first slice of W-104 that produces "real sessions" for the goal is the forks (Tables, CSV, DataFrames) on the unified library, then TraitMakie's `PlotCore`, then the joint script. If SciML is first because its port is the simplest to move, say so and accept that it delays the only measurement that matters by that slice.
- **Nothing is measured on the unified build.** Every number above is from the old build with the second owner. The unified build changes the session's composition in both directions: no facts copies of Base in the session (open issue 125's 0.24–0.34 s goes by construction, the trade-offs review); one dispatch removes the subtrait encoding that rejected 237 of DataFrames' image CodeInstances at load (E-238); G2's narrower scope costs 0.2–0.3 s with the slot (E-265, the loss in CSV's own plain methods); the library's load invalidates 1,070 instances of the compiler's own code (E-281); the memberships' activation walk and ambiguity report at load (compiler §9, mine, 2026-11-07) are unmeasured. The first act of W-120 is a measurement, not a mechanism.

### H5. The load is the largest term and the design does nothing for it; the cache adds to it — verified (E-233's profile, E-180, PE-1, PE-8, E-281, E-176)

- **The numbers.** Imports 1.38 s against 0.20 s (E-233): validation about 0.6 s, member records 0.15 s, the image hook 0.05 s, `stale_cachefile` 0.04 s, GC 0.05 s, the rest restoring images. `@time_imports`: CSV 323 ms, DataFrames 310, PrettyTables 89, TraitWorld 87, Parsers 48, Tables 40, CSV's extensions 76.
- **What the design has for it:** memberships activated before validation and the member hook's answers kept in images (compiler §9, §10.4; W-84's records cut the SciML load from 1.18 to 0.57 s, E-231). Nothing for validation itself. PE-1 (validation remembered, 0.6–0.8 s of a 3.7 s load, E-186) was set aside by the rule for performance work as "not enabled by facts or traits"; PE-8 (facts code valid without the edge walk unless a method intersects its facts) was bounded at 0.1–0.15 s because facts code was 11 % of what C loads.
- **The unified build changes PE-8's arithmetic.** With the G2 bit on all code, the code that needs no edge walk is every G2 CodeInstance of either policy, 62 % of plain code (E-273), whose dispatch edges are all at fact signatures, where `verify_call` takes its fast path anyway (`reinfer.jl:485`). What costs in validation is the abstract edges of non-G2 code. A breakdown of validation time by the G2 bit on the goal's session, on the unified build, decides whether a rule "G2 code skips the walk unless a method inserted since the image's build intersects one of its facts" is worth a loader change. That rule *is* enabled by facts, so it is inside the rule for performance work. C-46 must be closed before such a rule is sound (H2).
- **The compiler's own code invalidated by the library** (E-281: "1,070 of the compiler's own code by the library's interpreter methods, present without BaseTraits too"; E-234: 115 ms compiled again; E-238: 136 ms). The reference wants the classification as "one inference of the method at the erased signature, under a check flag of the native interpreter" (compiler §6.7); the library infers with an interpreter of its own instead (C-40, `TraitWorld.ClassifyInterp`). Every package that defines an `AbstractInterpreter` breaks the compiler's abstract edges (closed open issue 3 says exactly this of REPL's). Building C-40 as the reference says removes the library's interpreter and the 1,070 invalidations with it: a principled fix that reduces code, on the goal's path.
- **The cache adds to the load:** about 8 ms per part (E-180) plus the validation of its entries. At the goal's size (one or a few sets) that is 0.01–0.05 s; it must be counted against the saving in the gate.
- **The dependency tree is the ceiling no cache moves** (E-176: `using CairoMakie` alone 2.7 s and 261 packages; a plotting core's plausible dependencies 0.51–0.72 s and 66–83 packages). The Makie port must keep its tree at the core's size; the DataFrames port's script path should not load PrettyTables (about 450 of its image CodeInstances are rejected at load by plain dependencies, E-238) unless it displays.

### M1. The record §9 asks for is not complete for a cross-environment cache: embedded values, flags and the Julia build are missing — verified (compiler §3.1, §9, C-52; facts §12; the store review B2)

- Compiler §3.1 lists dispatch, result, code (method and a digest of its lowered code), binding edges, layout identities, cells and positive memberships; §9 names a method, a type and a membership by stable identities; C-52 asks for the digests, the layouts and the names. None mentions **the values the optimized code embeds**: the values of `const` bindings it folded (preferences, artifact paths, values computed from a dependency), `rettype_const`, split tables, any object with identity. Facts §12 does say "the values it embeds", so the two references disagree. The store review's B2 and the store note's rev. 2 §1 (content: F1, F3, embedded values, `CacheFlags`, the module options inference reads) had the full list; the unified reference dropped it.
- Also missing: the optimizer's flags (`CacheFlags`: check-bounds, inline, optimization level, debug level) and the Julia build, which decide the code's shape; generated functions and opaque closures, whose lowered code is per specialization (m3).
- **Fix** before C-52 is built, or the "complete record" is rebuilt once: §3.1 gains "embedded values: a digest of each constant the code folds, or the entry is not storable where the value has identity"; §9's list gains the flags and the build; C-52's text follows.

### M2. The code slot: keep it as built; the +8.5 % is one run, and `core` moved 7 % the other way — verified (`experiments/unification/stack/logs/e283-basetests.log`)

- **The log:** `e283-slot1 precompile 251.6 s`, `e283-slot0 precompile 231.8 s` (+8.5 %); `e283-slot1 core 69.1 s`, `e283-slot0 core 74.6 s` (−7.4 %). One run each, on a shared host at load 2.5–4.5. A difference of this size in both directions on single runs is noise until three alternating runs say otherwise. The claim "+8.5 % on precompile" is not established.
- **Narrowing to facts→plain calls would give up what matters for the goal.** E-261 (A), all code: the slot keeps 341 of 1,233 invalidated CodeInstances in the forks' session (28 %) and 1,622 of 6,430 in the ten-load session (25 %); (B), facts callers of plain code only: 67 of 120 and 91 of 100. The goal's sessions are plain-heavy (H2); the all-code slot is the one that would keep their callers. The runtime cost, 0.08 ns per independent call and nothing where calls wait on each other (E-283), is below any session's noise.
- **"No observed benefit" is a property of the workloads, not of the slot:** W-106's workloads load nothing after work (E-283: "a callee behind a slot is compiled at its first call, not with its callers. They keep nothing"). W-119 is the right check, with the ports.
- **What matters for the cache is C-65, not the cost:** "Validation at load does not mark: such a caller is dropped and compiled again." A stored entry whose plain callee was recompiled to an equal result is exactly the case the slot exists for (rustc's red-green keeps a dependent green when a changed input's result is unchanged; .NET R2R routes every cross-module call through an indirection cell so the caller survives the callee's change). Fix C-65 before any store is measured, or the store's survival rate understates the design.
- **Recommendation:** keep the slot; rerun `precompile` three times alternating before recording a cost; close C-65 before step 3; decide narrowing only on W-119's numbers.

### M3. "A first Makie + DataFrames workload" has no definition and no gate script; E-233's session is not it — verified (`forks/scripts/session.jl`, `session.py`; `TraitReport/scripts/measure.sh`)

- E-233's workload is a 26-step REPL session fed on a pty, with `show`, `describe` and display at every step, the REPL's start (0.36 or 0.61 s, bimodal, PE-14) and its typing hints (0.45–0.55 s compiled in the background while input is pasted). The goal's workload is a script: Julia's process start is 0.10 s (TraitReport), display is not on its path, and the hints do not exist. So E-233 overstates the goal's gap by about 0.8–1.1 s and understates nothing. The DataFrames + Makie combination has never been timed together on any build.
- **Recommendation: define the gate now, before any cache code.** `goal.jl` and `goal.py`, in `experiments/`, registered as an E- row before the run: load the DataFrames port and the Makie port; read `people.csv` and `orders.csv` (the forks' data); `select`/`subset`, `sort`, `groupby`/`combine` with `mean ∘ skipmissing`, a `ByRow` user function, `innerjoin`; a figure with two axes (`lines!`, `scatter!`) saved to PNG; exit. Fresh processes, `--startup-file=no`, a warm-up and three runs, marks for start, imports, read, transform, plot and exit, the load average logged, the PNG's and the frames' digests compared between Julia and Python's outputs where they can be. The one number each step of W-120 is gated on is the wall-time ratio to Python's; counts of CodeInstances kept are diagnostics. Keep E-233's REPL session as a second, secondary measure. TraitReport's `measure.sh` is the template.

### M4. Step 4 is a new linker, "weeks" is optimistic, and its two known corrections are not in the plan — reasoned (`staticdata.c:2290–2330, 2366–2392`; the synthesis plan §1, review M8; E-205)

- An image's machine code reaches other images' objects through `jl_update_all_fptrs` and `jl_update_all_gvars`, with every external reference resolved by (build id, offset) through `link_ids_*` (`staticdata.c:342–347`). Relinking by stable names means: object code generated again at exit, since the JIT's object code is not written out (the synthesis plan's M8); a symbol table of every external reference by (module path, name, signature, digest) for functions, global variables, types, methods and bindings; resolution against the session's objects at load with a miss making the entry fail; then `verify_method_graph`. The store review's B1 already found that no existing writer does this; it is a loader of its own, with its own soundness cases (the store note §6, E-0's eight).
- **Prior art chooses the environment key.** JEP 483's AOT cache is made from a training run and "if any of these constraints are violated then HotSpot, by default, issues a warning and ignores the cache": same JDK, same class path (appending only), same module options. .NET ReadyToRun allows inlining only inside a "version bubble", "a set of DLLs that we are willing to update as a set", and makes cross-bubble calls version-resilient through indirection cells. rustc's incremental cache is per crate and per compilation session directory. None reuses compiled code by content across environments. The cross-environment property is rare because it is expensive; the design should not take it on for a goal that does not need it.
- **Name the evidence that would justify step 4:** the environment-keyed cache (step 3) measured empty, on the user's real manifest churn, often enough that the goal's session misses it by a stated margin. Without that measurement step 4 stays a direction, as decision 10 of the synthesis plan says.

### M5. E-265's +0.2–0.3 s and the compiler's recompilation are costs of the unified build on the goal's path that no cache removes — reasoned (E-265, E-234, E-281)

- E-265: with the slot, a session of the forks' loads pays 0.2–0.3 s of compile for facts callers of invalidated plain code; "the loss is CSV's facts code resting on CSV's own plain methods (`CSV._parse`)". A port fixes this by giving those methods the facts policy (a port's choice, not Base's flag; E-279 found no plain callee missing G2, so the choice of no boundary flag on Base stands). A cache does not: the entries are invalidated in the session by the loads.
- The compiler's own code compiled again after the library's load (H5) is also outside any cache's reach, since the cache's copies are invalidated too (E-234: "the compiler's own code was compiled again although the cache held it").

### L1. Package-image workloads are the cheapest cache and the only one that serves the first session after an install — verified (E-227/E-228, E-175, `gf.c:6031`, `staticdata_utils.c:334`)

- The Makie demonstrator's first figure takes 158–163 ms with its image's workload and 1,135–1,137 ms without (E-227/E-228). A `precompile` statement in a package's workload marks its MethodInstance (`JL_MI_FLAGS_MASK_PRECOMPILED`, `gf.c:6031`) and the image keeps the external code so reached (`staticdata_utils.c:334`), validated at load exactly as a cache image would be. So a workload in the DataFrames port's image covering the goal's shapes (read with the goal's column types, `combine` with `mean ∘ skipmissing`, `innerjoin` on an `Int` key) keeps the same code a cross-session cache would, needs no mechanism, and is there in the first session after install, which no cross-session cache is. E-175: "with a cache every setting's work after the load is about a second or less; the load remains."
- What no image keeps stays for the session in either form: code at signatures with a type value (compiler §9's rule, 0.2 s in E-234), the user's closures, the compiler's code.

### L2. "A store on today's loader, about a week" needs the writer's side stated — reasoned (the cache design review §3, §7)

## Answers to the seven questions

1. **Is the cache the right lever?** No, not first and not alone. E-234: a perfect cache of all code saves about 1.0 s of a 3.4 s gap on the DataFrames session; the load (1.2 s above pandas') and the REPL (0.26–0.5 s above a script's start) are larger and untouched by it; the run time already matches. What no cache provides: the load's validation and the library's hooks, the library's invalidation of the compiler, code keyed on the session, the dependency tree, and the first session after an install (package-image workloads do that).
2. **Scope.** A facts-keyed cache is aimed at the wrong code for this goal (a tenth of the saving, E-234). Revisit: "facts code only" → code of either policy, admitted by the G2 bit (H2); "the environment-keyed cache retired" → it is the right first form for this goal (H3); the vehicle "relinked by stable names" → kept as the cross-environment layer, on evidence (M4). Keep: validity by Julia's validation (2026-10-28; it is exact and exists), the product setting's policy, no boundary flag on Base (E-279; E-265's loss is a port's own methods).
3. **The vehicle.** For the goal: generated images per dependency set on today's loader, environment-keyed, admitting all code; the slot with C-65 fixed so stored callers survive equal-result recompiles. Extending Julia's own package images with session code changes their build ids and cascades (the cache design review §3), so a sidecar per set is right. Relinking by stable names is the cross-environment layer: a loader of its own, weeks at least, justified only by measured manifest churn.
4. **C-52 first?** Not necessary for step 3, not sufficient for step 4 (M1: embedded values, flags, the build are missing). Build first: the ports' slices for the goal and the gate script (M3); then C-40 as the reference says, which removes the library's interpreter and its 1,070 invalidations per load.
5. **Load-time costs.** Not addressed; the cache adds a little (8 ms per part). The unified build's G2 bit on all code makes a validation shortcut for G2 code a facts-enabled change inside the rule for performance work; measure validation by the bit on the goal's session first (H5). C-46 must close before any skip.
6. **The slot.** Stay as built. The +8.5 % is one run against a `core` that moved −7 %; rerun three times alternating. Narrowing to facts→plain would drop most of E-261's kept callers in plain-heavy sessions. W-119 decides; C-65 matters more for the store than the cost does.
7. **The order and the gate.** The DataFrames port first (the forks on the unified library), then TraitMakie's core, then the joint script; SciML last of the three. One gate: the wall-time ratio of `goal.jl` to `goal.py`, fresh processes, a warm-up and three runs, with the breakdown by marks; each step of W-120 is accepted when the ratio moves and its part of the breakdown shrinks.
